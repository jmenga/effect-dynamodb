DynamoDB uses **expressions** — string-based mini-languages — to describe conditions, filters, updates, and projections. effect-dynamodb provides two ways to build them:

1. **Callback API** — Type-safe, composable, supports nested paths and all DynamoDB operators
2. **Shorthand syntax** — Concise object literals for common AND-equality patterns

Both compile to the same DynamoDB expression strings with properly aliased `ExpressionAttributeNames` and `ExpressionAttributeValues`.

## Expression Types at a Glance

| DynamoDB Expression | Purpose | effect-dynamodb API |
|---|---|---|
| `ConditionExpression` | Guard writes — fail if condition is false | `Entity.condition()` on put/update/delete |
| `FilterExpression` | Narrow reads — remove non-matching items from results | `Entity.filter()` on query/scan |
| `UpdateExpression` | Describe mutations — SET, REMOVE, ADD, DELETE clauses | `Entity.set()`, `remove()`, `add()`, etc. |
| `KeyConditionExpression` | Select partition + sort key range | `db.entities.Entity.indexName()`, `.where()` |
| `ProjectionExpression` | Select attributes to return | `Entity.select()` |

## Condition Expressions

Condition expressions guard write operations. DynamoDB evaluates the condition atomically — if it fails, the write is rejected with `ConditionalCheckFailed`.

### Callback API

The callback receives two arguments:

- `t` — a `PathBuilder` proxy for type-safe attribute access
- `ops` — comparison and logical operators that return `Expr` nodes

```typescript region="condition-callback" example="guide-expressions.ts"
// Single comparison
Products.condition((t, { eq }) => eq(t.status, "active"))

// Multiple conditions with AND
Products.condition((t, { eq, gt, and }) => and(eq(t.status, "active"), gt(t.stock, 0)))

// Nested path
Products.condition((t, { eq }) => eq(t.address.city, "NYC"))

// Size comparison
Products.condition((t, { gt }) => gt(t.tags.size(), 5))

// Attribute existence
Products.condition((t, { exists }) => exists(t.email))

// OR + NOT composition
Products.condition((t, { or, not, eq }) =>
  or(eq(t.status, "active"), not(eq(t.status, "archived"))),
)
```

Apply the condition as a combinator on put, update, or delete:

```typescript region="condition-on-operations" example="guide-expressions.ts"
  // #region condition-on-operations
  // On put
  yield* db.entities.Products.put({
    ...baseProduct,
    productId: "p-5",
    name: "New Product",
    category: "electronics",
    price: 49.99,
    stock: 10,
  }).condition((t, { notExists }) => notExists(t.productId))

  // On update (ANDed with optimistic lock)
  yield* db.entities.Products.update({ productId: "p-1" })
    .set({ name: "Widget Pro" })
    .expectedVersion(1)
    .condition((t, { gt }) => gt(t.stock, 0))

  // On delete
  yield* db.entities.Products.delete({ productId: "p-4" }).condition((t, { eq }) => eq(t.stock, 0))
```

### Shorthand Syntax

For simple equality-only conditions, pass a plain object. Each key-value pair becomes an `=` comparison, all ANDed together:

```typescript region="condition-shorthand" example="guide-expressions.ts"
// Equivalent to: eq(t.status, "active") AND eq(t.role, "admin")
Products.condition({ status: "active", role: "admin" })
```

<Aside type="tip">
  Discrimination is automatic — if the first argument is a function, the callback API is used; if it's an object, the shorthand is used.
</Aside>

### Handling a Rejected Condition

`.condition()` widens the operation's error channel with `ConditionalCheckFailed`, so a rejection is catchable by tag — the exhaustiveness of `catchTag` / `catchTags` is preserved, and a new failure introduced by an upgrade cannot silently fall into the same branch:

```typescript region="condition-catch" example="guide-expressions.ts"
  // #region condition-catch
  // `.condition()` adds ConditionalCheckFailed to the error channel, so the
  // rejection is catchable by tag — no `catchAll` + `_tag` inspection needed.
  const outcome = yield* db.entities.Products.put({
    ...baseProduct,
    productId: "p-5",
    name: "Duplicate",
    category: "electronics",
    price: 49.99,
    stock: 10,
  })
    .condition((t, { notExists }) => notExists(t.productId))
    .asEffect()
    .pipe(
      Effect.as("written"),
      Effect.catchTag("ConditionalCheckFailed", () => Effect.succeed("already exists")),
    )
```

<Aside type="note">
  `ConditionalCheckFailed` appears **only after** `.condition()` is applied — an
  unconditional `put` / `update` / `delete` cannot fail that way, and its channel
  stays narrow.

  One exception on updates: when a version CAS is also in play (`.expectedVersion(...)`,
  or the automatic CAS on the `versioned` / unique-constraint transaction path), both
  predicates ride the same `ConditionExpression` and DynamoDB does not say which half
  failed. The rejection is attributed to the CAS and reported as `OptimisticLockError`.
  With no version attribute the user condition is the only predicate, so the rejection
  is reported as `ConditionalCheckFailed`.

  On `delete`, the guard reaches DynamoDB on every path — the simple `DeleteItem`, the
  soft-delete transaction, and the unique-constraint transaction. On the two transaction
  paths it rides the current item's own `Delete`, so a rejection rolls the whole
  transaction back: no tombstone, no released sentinel. The sentinel releases carry
  only their own condition — that the item still owns the sentinel — and one that fails
  is a `ConcurrentModification`, never your condition.
  `purge()` is the one operation that refuses a condition (`ValidationError`, `EDD-9047`)
  — it deletes a whole partition across batched writes, so no single `ConditionExpression`
  could guard it atomically.
</Aside>

### Condition Operators Reference

| Operator | Callback | DynamoDB |
|---|---|---|
| Equals | `eq(t.field, value)` | `#field = :val` |
| Not equals | `ne(t.field, value)` | `#field <> :val` |
| Less than | `lt(t.field, value)` | `#field < :val` |
| Less or equal | `lte(t.field, value)` | `#field <= :val` |
| Greater than | `gt(t.field, value)` | `#field > :val` |
| Greater or equal | `gte(t.field, value)` | `#field >= :val` |
| Between | `between(t.field, low, high)` | `#field BETWEEN :lo AND :hi` |
| In list | `isIn(t.field, [a, b, c])` | `#field IN (:a, :b, :c)` |
| Begins with | `beginsWith(t.field, prefix)` | `begins_with(#field, :prefix)` |
| Contains | `contains(t.field, substr)` | `contains(#field, :substr)` |
| Exists | `exists(t.field)` | `attribute_exists(#field)` |
| Not exists | `notExists(t.field)` | `attribute_not_exists(#field)` |
| Attribute type | `attributeType(t.field, "S")` | `attribute_type(#field, :type)` |
| Size | `gt(t.field.size(), 5)` | `size(#field) > :val` |

An `isIn` with no values compiles to `#field IN ()`, which DynamoDB rejects as a syntax error. The library sends it rather than refusing it, and fails with a `ValidationError` naming the `isIn()` and its attribute, with DynamoDB's error as its `cause` — in a condition (nothing is written) and in a filter (`operation: "query.filter"`) alike. Give `isIn` at least one value, or leave the condition out.

### Logical Composition

| Combinator | Callback | DynamoDB |
|---|---|---|
| AND | `and(exprA, exprB, ...)` | `(exprA) AND (exprB)` |
| OR | `or(exprA, exprB, ...)` | `(exprA) OR (exprB)` |
| NOT | `not(expr)` | `NOT (expr)` |

## Filter Expressions

Filter expressions narrow query and scan results **after** items are read from disk. They use the same grammar as condition expressions but apply to reads instead of writes.

<Aside type="caution">
  Filters do **not** reduce read capacity — you pay for all items matched by `KeyConditionExpression`. The 1 MB per-page limit also applies before filtering. Use sort key conditions for efficient pre-read narrowing.
</Aside>

### Callback API

`Entity.filter()` works identically to `Entity.condition()` but returns a `Query` combinator:

```typescript region="filter-callback" example="guide-expressions.ts"
// Filter on entity index query — shorthand for equality
const activeElectronics = yield* db.entities.Products.byCategory({ category: "electronics" })
  .filter({ status: "active" })
  .collect()

// Filter on scan — callback with typed PathBuilder
const withWidget = yield* db.entities.Products.scan()
  .filter((t, { contains }) => contains(t.name, "Widget"))
  .collect()

// Complex filter with OR
const activeOrPending = yield* db.entities.Products.scan()
  .filter((t, { or, eq }) => or(eq(t.status, "active"), eq(t.status, "pending")))
  .collect()
```

### Shorthand Syntax

```typescript region="filter-shorthand" example="guide-expressions.ts"
Products.filter({ status: "active" })
Products.filter({ category: "electronics", inStock: true })
```

## Update Expressions

Update expressions describe how to modify item attributes. DynamoDB supports four clause types, all composable in a single atomic operation.

### Record-Based Combinators

These accept plain objects with field names — good for top-level attribute updates:

```typescript region="update-record" example="guide-expressions.ts"
  // #region update-record
  // SET — assign values
  yield* db.entities.Products.update({ productId: "p-1" }).set({
    name: "Widget Deluxe",
    price: 34.99,
  })

  // REMOVE — delete attributes
  yield* db.entities.Products.update({ productId: "p-4" }).remove(["description", "temporaryFlag"])

  // ADD — atomic increment (numbers) or union (sets)
  yield* db.entities.Products.update({ productId: "p-1" }).add({ viewCount: 1, stock: 50 })

  // Subtract — SET field = field - value
  yield* db.entities.Products.update({ productId: "p-1" }).subtract({ stock: 3 })

  // Append — SET field = list_append(field, value)
  yield* db.entities.Products.update({ productId: "p-1" }).append({
    tags: ["on-sale", "featured"],
  })

  // DELETE — remove elements from a set
  yield* db.entities.Products.update({ productId: "p-4" }).deleteFromSet({
    categories: new Set(["obsolete"]),
  })
```

### Composing Multiple Update Types

All combinators chain as methods on the `BoundUpdate` builder. They compile to a single `UpdateExpression` with the appropriate SET, REMOVE, ADD, and DELETE clauses:

```typescript region="update-composed" example="guide-expressions.ts"
  // #region update-composed
  yield* db.entities.Products.update({ productId: "p-1" })
    .set({ name: "Updated Widget", price: 24.99 })
    .add({ viewCount: 1 })
    .subtract({ stock: 3 })
    .append({ tags: ["clearance"] })
    .remove(["temporaryFlag"])
    .expectedVersion(6)
```

### Clearing a Field

`.remove(["field"])` and `.set({ field: undefined })` are one operation. The attribute goes, any index key built from it goes (see [Index Policy](/effect-dynamodb/guides/index-policy/)), and a unique value it held is released. A value that encodes to nothing clears the same way, such as `Option.none()` on a `Schema.OptionFromOptional` field.

```typescript region="update-clear" example="guide-expressions.ts"
  // One operation, two spellings: the attribute goes, any index key built from it goes,
  // and a unique value it held is released.
  yield* db.entities.Products.update({ productId: "p-4" }).remove(["description"])
  yield* db.entities.Products.update({ productId: "p-4" }).set({ description: undefined })

  // A field no row can be without doesn't compile, and is refused before anything is sent:
  // the row would no longer be readable.
  const refusal = yield* db.entities.Products.update({ productId: "p-4" })
    // @ts-expect-error `name` is required
    .remove(["name"])
    .asEffect()
    .pipe(Effect.flip)

  // An attribute the model no longer declares is cleaned up with a path.
  yield* db.entities.Products.update({ productId: "p-4" }).pathRemove(["retiredAttribute"])
```

A row can lack a field if its schema reads one without it: `Schema.optional`, `Schema.optionalKey`, the `Schema.OptionFromOptional` family, or a decoding default, which is what the field reads back as. Where a decoding default, a step or a middleware of your own, a `Schema.suspend` or a check takes part in reading a row without the field, the write that clears it reads the absence once to find out, and nothing runs when the entity is defined. It can also lack a field holding a [value DynamoDB can't store](#values-dynamodb-cant-store). Anything else is refused with a `ValidationError`, for `.remove`, `.set({ field: undefined })`, a `pathRemove`, and the `.remove` on a time-series `.append`. So is a required property below a field, such as `pathRemove(["address", "city"])` when `city` is required, even if `address` itself is optional, or below a sparse map's entry, such as `pathRemove(["data#2026-01", "views"])`; and a list position whose removal leaves a list nothing reads, such as either position of a `[string, string]`, the first of a `[string, number?]` (the number would move into the string's place), or one a tag beside the list rules out. That's judged from the schema only where every value it reads would break: below a `Schema.Unknown` member, a transformed or checked node, or a record keyed by anything but strings and template literals of strings, the removal is sent, as is one a union's other member may read what's left of.

`Schema.NullOr` requires the key and allows an empty value, so `.set({ field: null })` stores a `null` rather than clearing it. On an optional field, `null` clears as `undefined` does.

Every update operation names model fields, never what the library stores. These are refused the same way, for `.remove`, `.add`, `.subtract`, `.append`, `.deleteFromSet` and every path operation:

| Name | Why, and what to do instead |
|---|---|
| Another field's stored name (`g` for `configure(M, { region: { field: "g" } })`) | Name the model field, `region` |
| A secondary index's key attribute (`gsi1pk`) | The library composes it. Clear the composite it's built from |
| `__edd_e__` and any other `__edd_*` attribute | The library manages them |
| The version attribute, `createdAt`, `updatedAt`, `deletedAt`, the TTL attribute | The library manages them, on an entity configured to use them |
| A primary-key composite, or `pk` / `sk` | It identifies the item |
| An immutable field | It can't change after creation |
| A sparse map, or one of its entries by stored name | Use `.removeEntries` or `.clearMap` |

An attribute the model simply doesn't know stays allowed at run time, because that's the only way to clean up one it no longer declares. The types only offer the model's own names to `.remove`, so use `.pathRemove(["attribute"])` for it.

### Values DynamoDB Can't Store

DynamoDB has no form for `undefined` or an empty set. On a field whose type includes one, that value is stored as an absent attribute, and an absent attribute reads back as that value.

```typescript region="model-no-stored-form" example="guide-expressions.ts"
class Device extends Schema.Class<Device>("Device")({
  deviceId: Schema.String,
  // Required, and both can hold a value DynamoDB can't store.
  labels: Schema.ReadonlySet(Schema.String),
  lastError: Schema.UndefinedOr(Schema.String),
}) {}
```

```typescript region="update-no-stored-form" example="guide-expressions.ts"
  // Stored as a row without either attribute. Every read gives the values back.
  const device = yield* db.entities.Devices.put({
    deviceId: "d-1",
    labels: new Set(),
    lastError: undefined,
  })

  // The ordinary operations, then. Emptying the set takes the attribute away.
  yield* db.entities.Devices.update({ deviceId: "d-1" }).add({ labels: new Set(["indoor"]) })
  yield* db.entities.Devices.update({ deviceId: "d-1" }).deleteFromSet({
    labels: new Set(["indoor"]),
  })

  // So these are clears as well, and the field can be cleared by name.
  yield* db.entities.Devices.update({ deviceId: "d-1" }).set({ labels: new Set() })
  yield* db.entities.Devices.update({ deviceId: "d-1" }).remove(["lastError"])

  const read = yield* db.entities.Devices.get({ deviceId: "d-1" })
  // read.labels is an empty Set, and read.lastError is undefined

  // A condition or a filter comparing with an empty set asks whether the attribute is there.
  const unlabelled = yield* db.entities.Devices.scan()
    .filter({ labels: new Set() })
    .collect()
```

This holds at any depth (a struct, a class, the elements of a list, what a `Schema.suspend` or a transformation holds, and what's inside an `Option`, a `Result`, an `Exit` or a `Cause`), and on every path that writes or reads an item: `put`, `update`, `upsert`, `append`, `Batch`, `Transaction`, version snapshots, soft delete and restore, aggregates, and the events and snapshots of an event stream. Any other value is stored exactly as before. A field left `Schema.optional` keeps its own reading: an empty set stored there reads back as no field.

| The field | Stored | Reads back |
|---|---|---|
| `Schema.ReadonlySet(...)` holding nothing | No attribute | An empty set |
| `Schema.UndefinedOr(...)` holding `undefined` | No attribute | `undefined` |
| `Schema.NullOr(Schema.ReadonlySet(...))` holding `null` | `NULL` | `null` |
| `Schema.NullOr(Schema.ReadonlySet(...))` holding nothing | No attribute | An empty set |
| `Schema.UndefinedOr(Schema.ReadonlySet(...))` holding nothing | No attribute | `undefined`, the one value an absent attribute can mean there |
| `Schema.optional(Schema.ReadonlySet(...))` holding nothing | No attribute | No field |
| `Schema.Option(Schema.ReadonlySet(...))` holding `Option.some` of nothing | An `Option` with no value | `Option.some` of an empty set |
| A set with `.check(Schema.isMinSize(1))` | Refused: the schema says it can't hold nothing | |

Some places have no attribute to leave out, or no way to say so:

- **An empty set in a list or a tuple.** Leaving it out moves the elements after it, so it's refused with a `ValidationError` naming where it is, such as `"pair[1]"`, before anything is sent. That goes for a `Schema.Array` of sets, a `Schema.Tuple`, an `.append` or `pathSet` operand, a list in a `Schema.Unknown` field, and a list in an event, its metadata, a snapshot's state or an outbox effect. Use `pathRemove` to remove an element.
- **`undefined` in a tuple position.** A stored list closes up, so the values after it would move, or the row couldn't be read. It's refused the same way, unless no value follows it in an optional position or it encodes to something else. The check looks at the domain value, so a position only its encoding makes `undefined` (`Option.none()` under `Schema.OptionFromUndefinedOr`) isn't seen, and closes up. Use `Schema.OptionFromNullOr` there.
- **`undefined` in a list.** It closes up: `["a", undefined, "b"]` in a `Schema.Array(Schema.UndefinedOr(...))` or a `Schema.Unknown` field is stored, and reads back, as `["a", "b"]`. So does the rest of a `Schema.TupleWithRest`. Use `Schema.NullOr` for a position that has to hold nothing.
- **A record entry.** An entry holding an empty set isn't stored, so the record reads back without that key.
- **A `.select()`.** A projection returns what's stored, undecoded, so the attribute stays absent.
- **A comparison.** Only `eq` and `ne` have a meaning for an empty set, as `attribute_not_exists` and `attribute_exists`. Any other comparison with one is refused. `eq(t.field, undefined)` is left as it is, since an `undefined` there is more often a mistake, and `.filter({ field: undefined })` still means no filter.

`Schema.Unknown`, `Schema.Any` and `Schema.Void` fields count as holding `undefined`, since they can.

Anything else the marshaller won't take is refused the same way, naming the field: `NaN`, `Infinity`, a number past `Number.MAX_SAFE_INTEGER` (use `Schema.BigInt`), and a set of anything but strings, numbers or binary. With `escapeKeys`, a `NaN` feeding a key is `EDD-9096` instead. A `DynamoModel.Packed` field is judged by its own form, so it holds a number that large and refuses `NaN`, because JSON does.

The marshaller lets a few things past. DynamoDB rejects a set mixing strings and numbers, as a `DynamoError`. A function in a map is dropped, and a class with no enumerable fields, such as a plain `Date`, is stored as an empty map. A `Schema.HashSet` can't be stored: a non-empty one is refused, and an empty one is stored as a map of its internals, reading back empty.

The rule has limits a value can run into:

- **Schemas it can't walk.** `Schema.suspend` and a class built with `.check()` or `.annotate()` aren't looked into, and nor is what's beneath a container's decoding default. An absent attribute inside them is a decode failure, and a tuple inside them isn't checked. `oneOf` union members stay strict, because a lenient copy would make two members match.
- **A transform that won't round trip.** A transform encoding a value to an empty set that doesn't decode one back can't read back what it stored. `.set` of that value is refused, naming the field, and `put` fails with `EDD-9050` as a defect, writing nothing.
- **The `Expression` builders.** `Expression.condition` and the other builders are plain functions that build their expression when called, so a value they can't marshal throws there, as `UnstorableValue`. Inside `Effect.gen` that's a defect, and it's how a `Transaction.check` gets its condition. `.condition()` and `.filter()` take the same input and refuse it with a `ValidationError`.
- **Reads that come first.** An aggregate `update` and a `commandHandler` read before they decide what to write, so a refused value there has cost a read, though nothing is written.

### Relative Updates Aren't Checked Against the Model

`.set` is checked before anything is sent, because the value is in hand. `.add`, `.subtract`, `.append`, `.deleteFromSet` and most path operations change a value only DynamoDB holds, so a `.check()` on the field can't be judged without reading the row first, and an update doesn't read. Guard them with `.condition()`, which DynamoDB judges against the stored value.

```typescript region="update-relative" example="guide-expressions.ts"
  // DynamoDB applies `.subtract` to a value only it holds, so the model can't judge the result
  // first. A condition can: refused, it writes nothing.
  const refusedByCondition = yield* db.entities.Products.update({ productId: "p-5" })
    .subtract({ stock: 3 })
    .condition((t, { gte }) => gte(t.stock, 3))
    .asEffect()
    .pipe(Effect.flip)
  // ConditionalCheckFailed, and the stock is still 2

  // Without one the write lands, and the ValidationError says so: "The update WAS applied, and
  // the stored row no longer matches the model: ..."
  const landed = yield* db.entities.Products.update({ productId: "p-5" })
    .subtract({ stock: 3 })
    .asEffect()
    .pipe(Effect.flip)
```

An unguarded update that breaks a `.check()` fails with a `ValidationError` that says the update was applied and names the field, and reads of that row then fail until it's repaired. `.returnValues("none")` decodes nothing, so it doesn't report the problem at all, and neither does a `Transaction.transactWrite`, which returns no row.

### Path-Based Combinators

For nested attributes, array elements, and attribute-to-attribute operations, use the path-based combinators. These take the update operation as the first argument, so wrap them in a lambda when passing as a combinator to `update()`:

```typescript region="update-path" example="guide-expressions.ts"
  // #region update-path
  // SET nested path
  yield* db.entities.Products.update({ productId: "p-1" }).pathSet({
    segments: ["address", "city"],
    value: "NYC",
    isPath: false,
  })

  // SET array element
  yield* db.entities.Products.update({ productId: "p-1" }).pathSet({
    segments: ["roster", 0, "position"],
    value: "captain",
    isPath: false,
  })

  // Copy attribute to attribute
  yield* db.entities.Products.update({ productId: "p-1" }).pathSet({
    segments: ["backup_email"],
    value: undefined,
    isPath: true,
    valueSegments: ["email"],
  })

  // REMOVE nested attribute
  yield* db.entities.Products.update({ productId: "p-1" }).pathRemove(["metadata", "temporary"])

  // PREPEND to list
  yield* db.entities.Products.update({ productId: "p-1" }).pathPrepend({
    segments: ["tags"],
    value: ["URGENT"],
  })

  // if_not_exists — set only if the attribute doesn't exist
  yield* db.entities.Products.update({ productId: "p-1" }).pathIfNotExists({
    segments: ["createdBy"],
    value: "system",
  })
```

### Update Expression Reference

| Operation | Record Combinator | Path Combinator | DynamoDB |
|---|---|---|---|
| Set value | `Entity.set({ field: value })` | `Entity.pathSet(...)` | `SET #f = :v` |
| Remove attribute a row can lack | `Entity.remove(["field"])` | `Entity.pathRemove(segs)` | `REMOVE #f` |
| Atomic add | `Entity.add({ field: n })` | `Entity.pathAdd(...)` | `ADD #f :v` |
| Subtract | `Entity.subtract({ field: n })` | `Entity.pathSubtract(...)` | `SET #f = #f - :v` |
| Append to list | `Entity.append({ field: [...] })` | `Entity.pathAppend(...)` | `SET #f = list_append(#f, :v)` |
| Prepend to list | — | `Entity.pathPrepend(...)` | `SET #f = list_append(:v, #f)` |
| Default value | — | `Entity.pathIfNotExists(...)` | `SET #f = if_not_exists(#f, :v)` |
| Delete from set | `Entity.deleteFromSet({ f: set })` | `Entity.pathDelete(...)` | `DELETE #f :v` |
| Copy attribute | — | `Entity.pathSet({ isPath: true })` | `SET #a = #b` |

On an attribute or a sparse map's entry the row doesn't hold, `subtract` and `append` end differently depending on the update, and so does any record operation on an attribute holding `null`. A plain update sends `#f - :v` or `list_append(#f, :v)`, which DynamoDB refuses (`DynamoValidationError`, nothing written). An update that reads the row first (a `versioned: { retain: true }` entity's, one changing a unique field, or one computing an index composite) starts the attribute from nothing, storing `-v`, `v` or the operand alone.

#### Values are encoded through the schema at the path

`pathSet`, `pathAppend`, `pathPrepend`, `pathIfNotExists` and the record-based `append` encode their value through the model schema at the path they address, the same way `set` does:

- A `DateTime` set at `["days", 0]` is stored as its ISO string, or as a number under `storedAs`.
- A `Schema.NumberFromString` value is stored as a string.
- A plain object set on a class-typed field is encoded as that class.
- A class instance is always encoded as a whole, since its constructor took domain values.
- A plain object or array that mixes wire and domain parts, such as `{ b64: "hi", at: DateTime, n: "5" }`, is encoded part by part, by the schema at each position. Every `DateTime`, `Date` and `Redacted` inside it is stored in its wire form.
- Appended and prepended lists are encoded element by element.

A value already in wire form is normalised the way `.set()` normalises it. A `NumberFromString` value of `"05"` is stored as `"5"`, a `DateTimeUtcFromString` value of `"2000-01-01"` as `"2000-01-01T00:00:00.000Z"`, and a `Schema.Trim` field stores its trimmed form. The value read back is the same either way; only the stored bytes differ, which matters to filters and DynamoDB Streams consumers.

One kind of value is stored exactly as given: a value that is genuinely valid wire for a leaf transform with a primitive wire form, and also a valid domain value. Examples are `"aGk="` on a `Schema.StringFromBase64` field, or a JSON string on a `Schema.fromJsonString` field. Encoding such a value again would double-encode it. A plain string that isn't valid wire, such as `"hi"` on a `StringFromBase64` field, is a domain value and is encoded (`"aGk="`). The same rule applies to such leaves inside arrays and plain objects.

A `pathSet` into a member of a union is checked against every member that holds the path, not only the first. With `tag: Schema.Union([A, B])`, where `A` is `{ kind: "a", x: string }` and `B` is `{ kind: "b", y: number }`, `pathSet(["tag", "kind"], "b")` beside `pathSet(["tag", "y"], 2)` is written as `B` stores it. Through 1.40.0 it was refused with `Expected "a"`. A path write reads nothing of the row, so a value only another member takes is written only where what the update leaves reads whatever the row holds, at every union the paths pass through or end at: every member there reads it, or the update writes every property of one member that does. A property holding a struct counts as written when it's set whole or every property of it is written. `tag.kind = "b"` alone is still refused: on a row holding `A` it would leave `{ kind: "b", x }`, which `B` can't read without `y`. So is `pathSet(["pass", "inner", "v"], "str")` on `Union([{ kind: "a", inner: { v: number } }, { kind: "b", inner: { v: string } }])`, where both members hold `inner`: on a row holding the first it would leave `kind: "a"` beside a string. The update's path writes and removals in the field are judged together: `tag.kind = "b"` beside `pathRemove(["tag", "y"])` is refused, since `B` requires `y`, and so is `tag.kind = "a"` beside `pathRemove(["tag", "x"])`, which 1.40.0 applied, leaving a row no read could decode. To switch a row from one member to another, set the field whole, or write every property the new member declares in the same update.

Paths into and under a top-level `DynamoModel.ref` field are encoded through the ref target's model, like any other path: `pathSet` at `["author", "born"]` stores the author's date as an ISO string. Only a path no schema describes, such as one under a dynamic key of an untyped value, is written as given.

A value set by path into a class that has lost its fields is written as given, in the same form `put` stores it, so the item stays readable. A class loses its fields when it is built with `.check()` or `.annotate()`, or when it is a `DynamoModel.ref` nested inside a ref target. Known limitation: plain dates inside such a class are still stored as maps, as on 1.22.0, and read back as plain objects. That applies to whole-value `put`, `.set()` and `pathSet` of the class too.

On entities with `versioned: { retain: true }`, path operations were silently ignored before this release: they returned success and wrote nothing. They are now sent to DynamoDB as the same update expression other entities use, in one transaction with the version snapshot, so they follow DynamoDB's own semantics: list indexes refer to the item before the update, overlapping paths and appends to a missing list are rejected, and a rejected update writes no snapshot. `expectedVersion` and `.condition()` apply.

#### Path operations on index composites and unique fields

A path operation on a field that feeds an index key or a unique constraint is handled like the matching record operation. A top-level `pathSet` of a value or `pathRemove` works like `.set()` or `.remove()`, and a numeric `pathAdd` or `pathSubtract` works like `.add()` or `.subtract()`. The index keys are recomposed and the unique sentinels rotated, exactly as those operations do. `.add()`, `.subtract()`, `.append()` and `.deleteFromSet()` on an index composite also recompose the index key, on every entity.

A `.remove()` (or top-level `pathRemove`) of an index composite that has a `Schema.withDecodingDefault` doesn't drop the item from the index. It stores the default instead and keeps the item indexed under it, so the keys agree with the value the item reads back with. On a unique field, the old value's sentinel is released and none is created for the default (see [Defaults and Unique Constraints](/effect-dynamodb/guides/data-integrity/#defaults-and-unique-constraints)).

These are rejected with a `ValidationError` that names the field:

- operations whose result DynamoDB computes at write time on such a field: a copy from another attribute, `pathIfNotExists`, and list or set operations;
- a path below such a field;
- any path operation on a primary-key composite or an immutable field;
- more than one operation on the same such field.

An update can't combine path operations with a change to a unique-constraint field, or with a computed change (`.add()`, `.append()`, …) to an index composite. Split it into two updates.

Path values are also validated the way `.set()` validates its payload. A value the schema rejects, such as a literal outside its set, a string under its `minLength`, or a container that breaks its `.check()`, fails with a `ValidationError` instead of being stored. A key whose value is `undefined` is dropped before validation, as it is when the item is stored. List `append` and `prepend` validate each element, but can't enforce list-level checks such as `maxLength`, because DynamoDB builds the list server-side.

:::caution[Appends can break a list-level check]
An append or prepend can take a list past a list-level check such as `maxLength`, and DynamoDB stores the result. For a list whose check is also enforced on read (any array that holds no date or other substituted value), the item then fails to decode with a `ValidationError`, both on the update's returned item and on every later read. Guard such a list with a condition on its size. For example, when appending one element to a list capped at 2:

```typescript
db.entities.Items.update({ id: "1" })
  .pathAppend({ segments: ["tags"], value: ["new"] })
  .condition((t, { lt }) => lt(t.tags.size(), 2))
```

The update then fails with `ConditionalCheckFailed` instead of writing. Alternatively, use `.set()` with the full list, which is validated before it is written. This is not new in this release.
:::

`ADD`, `DELETE` and `SUBTRACT` are unchanged.

:::note[Upgrading from 1.22.0 or earlier]
Earlier versions wrote path and `append` values unencoded: a `DateTime` became a marshalled map even on a plain date field, and a `NumberFromString` value was stored as a number. Those values now read back. A map is rebuilt into a real `DateTime`, a number on a `NumberFromString` field reads as that number, and a safe-integer number on a `BigIntFromString` field reads as a `bigint`. Until old values are rewritten, a filter on the attribute can match old and new items differently, and DynamoDB Streams consumers see the type change.
:::

## Key Condition Expressions

Key conditions select which items DynamoDB reads from disk. They are the most efficient way to narrow results because they reduce consumed read capacity.

### Entity Query Accessors

Each non-primary index defined on an entity generates a named query accessor:

```typescript
const Tasks = Entity.make({
  model: Task,
  entityType: "Task",
  primaryKey: {
    pk: { field: "pk", composite: ["taskId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    byProject: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["projectId"] },
      sk: { field: "gsi1sk", composite: ["status", "createdAt"] },
    },
  },
})

// Access via entity index accessor on the typed client
db.entities.Tasks.byProject({ projectId: "proj-alpha" })

// Partial SK composites narrow with begins_with automatically
db.entities.Tasks.byProject({ projectId: "proj-alpha", status: "active" })
```

### Sort Key Conditions with `.where()`

`.where()` on a `BoundQuery` adds a typed sort key condition to the `KeyConditionExpression`, using the SK composites that have not yet been provided in the query accessor input. It is only available when remaining SK composites exist, and can only be called once per query.

The callback receives a typed accessor for the remaining SK composites plus a set of SK comparison ops:

```typescript
// byProject SK composite: ["status", "createdAt"]

// Provide the PK + no SK composites → .where() sees both { status, createdAt }
db.entities.Tasks.byProject({ projectId: "p-1" })
  .where((t, { eq }) => eq(t.status, "active"))

// Provide a leading SK composite → .where() sees only remaining { createdAt }
db.entities.Tasks.byProject({ projectId: "p-1", status: "active" })
  .where((t, { between }) => between(t.createdAt, "2025-01", "2025-03"))

// Range comparisons
db.entities.Tasks.byProject({ projectId: "p-1" })
  .where((t, { gt }) => gt(t.status, "active"))

// Prefix match
db.entities.Tasks.byProject({ projectId: "p-1" })
  .where((t, { beginsWith }) => beginsWith(t.status, "a"))
```

| Operator | Callback | DynamoDB |
|---|---|---|
| Equals | `eq(t.field, value)` | `#sk = :sk` |
| Less than | `lt(t.field, value)` | `#sk < :sk` |
| Less or equal | `lte(t.field, value)` | `#sk <= :sk` |
| Greater than | `gt(t.field, value)` | `#sk > :sk` |
| Greater or equal | `gte(t.field, value)` | `#sk >= :sk` |
| Between | `between(t.field, lo, hi)` | `#sk BETWEEN :lo AND :hi` |
| Begins with | `beginsWith(t.field, prefix)` | `begins_with(#sk, :prefix)` |

<Aside type="note">
  The `.where()` callback operates on domain-level SK composites — you never construct raw composed sort key strings yourself. effect-dynamodb composes the schema prefix, entity type, and preceding composite values automatically.
</Aside>

## Projection Expressions

Projections select which attributes DynamoDB returns, reducing network transfer.

### Callback API with `Entity.select()`

`Entity.select()` uses the same `PathBuilder` proxy as condition/filter expressions:

```typescript region="select-callback" example="guide-expressions.ts"
// Top-level fields
Products.select((t) => [t.name, t.status])

// Nested map paths
Products.select((t) => [t.name, t.address.city])

// Array elements
Products.select((t) => [t.name, t.roster.at(0).name])

// Mixed
Products.select((t) => [t.name, t.address.city, t.tags.at(0)])
```

Apply as a combinator on queries and scans:

```typescript region="select-on-queries" example="guide-expressions.ts"
// Project on scan — callback
const projected = yield* db.entities.Products.scan()
  .select((t) => [t.name, t.price])
  .collect()

// Project on scan — string array shorthand
const scanned = yield* db.entities.Products.scan().select(["name", "status"]).collect()
```

### String Array Shorthand

For top-level-only projections:

```typescript region="select-shorthand" example="guide-expressions.ts"
Products.select(["name", "status", "price"])
```

<Aside type="caution">
  When projection is active, results are returned as `Record<string, unknown>` instead of typed model instances, since projected items may be partial. DynamoDB still reads the full item from disk — projections reduce network transfer, not read capacity.
</Aside>

## PathBuilder

The `PathBuilder` is a recursive `Proxy` that tracks attribute path segments as you access properties. It is the first argument in all callback-style expression builders.

```typescript region="pathbuilder" example="guide-expressions.ts"
// t is PathBuilder<Product, Product>
Products.condition((t, ops) => {
  // t.name        → Path with segments ["name"]
  // t.address.city → Path with segments ["address", "city"]
  // t.roster.at(0) → Path with segments ["roster", 0]
  // t.roster.at(0).name → Path with segments ["roster", 0, "name"]
  // t.tags.size() → SizeOperand with segments ["tags"]
  return ops.eq(t.status, "active")
})
```

### Supported Path Types

| Access | Type | Segments | DynamoDB Path |
|---|---|---|---|
| `t.name` | Top-level attribute | `["name"]` | `#name` |
| `t.address.city` | Nested map | `["address", "city"]` | `#address.#city` |
| `t.items.at(0)` | Array element | `["items", 0]` | `#items[0]` |
| `t.items.at(0).name` | Nested in array | `["items", 0, "name"]` | `#items[0].#name` |
| `t.tags.size()` | Size function | `["tags"]` | `size(#tags)` |

A field your model names `size`, `at` or `entry` is reached like any other: `t.size` and `t.box.size` are paths to that field. Called, the name is still the accessor on the path before it, so `t.box.size()` is the size of `box`.

All string segments are automatically aliased through `ExpressionAttributeNames` to handle DynamoDB reserved words.

A `field:` rename from `DynamoModel.configure` names a top-level attribute, so it applies to a path's first segment only. Below it a value is stored whole, under its own property names. With `count` stored as `renamed`, `t.count` is `#renamed`, and `t.meta.count` is `#meta.#count`, which is where `put` stored it. That holds for an update's path operations, a condition, a filter and a projection alike.

A path below a struct that renames its own keys (`Schema.encodeKeys`) names them as they're stored. With `meta: Schema.Struct({ amount: Schema.Number }).pipe(Schema.encodeKeys({ amount: "am" }))`, `t.meta.amount` names `meta.am`, where `put` stored it. A segment already spelled by its stored name (`t.meta.am`) is sent as written. Where the members of a union on the way store a property under different names, the path is sent as written.
