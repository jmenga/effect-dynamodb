[Projections from DynamoDB Streams](/effect-dynamodb/guides/projections/) folds one stream into a read model. This page covers what builds on it:

- **[Several sources per row](#several-sources-per-row):** one row that several streams contribute to, each instance with its own checkpoint.
- **[`revision`](#revision-one-guard-for-every-writer):** one guard that serialises every writer of a row.
- **[Removing rows](#removing-rows):** tombstones that keep the checkpoints.
- **[An outbox](#an-ordered-outbox):** side effects committed with the row and delivered in order, at least once.

## Setup

Three streams feed one shipment summary. An order feeds several shipments. A scan stream carries each shipment's whole location, and a scale reports weights:

```typescript region="streams" example="guide-projections-advanced.ts"
class ParcelAdded extends Schema.TaggedClass<ParcelAdded>()("ParcelAdded", {
  shipmentId: Schema.String,
  parcels: Schema.Number,
}) {}
class OrderCancelled extends Schema.TaggedClass<OrderCancelled>()("OrderCancelled", {
  shipmentId: Schema.String,
}) {}
class Scanned extends Schema.TaggedClass<Scanned>()("Scanned", {
  location: Schema.String,
}) {}
class Weighed extends Schema.TaggedClass<Weighed>()("Weighed", {
  shipmentId: Schema.String,
  kg: Schema.Number,
}) {}

const AppSchema = DynamoSchema.make({ name: "freight", version: 1 })
const EventsTable = Table.make({ schema: AppSchema, entities: {} })

// One order feeds several shipments
const OrderEvents = EventStore.makeStream({
  table: EventsTable,
  streamName: "Order",
  events: [ParcelAdded, OrderCancelled],
  streamId: { composite: ["orderId"] },
})
// One scan stream per shipment: each event carries the whole location
const ScanEvents = EventStore.makeStream({
  table: EventsTable,
  streamName: "Scan",
  events: [Scanned],
  streamId: { composite: ["shipmentId"] },
})
// Weighings arrive from a scale, one stream per weighing session
const WeighEvents = EventStore.makeStream({
  table: EventsTable,
  streamName: "Weigh",
  events: [Weighed],
  streamId: { composite: ["sessionId"] },
})
```

The read model keeps a checkpoint per source instance in a map field, and a `revision` that every write increments:

```typescript region="read-model" example="guide-projections-advanced.ts"
const ShipmentSummary = Schema.Struct({
  shipmentId: Schema.String,
  parcels: Schema.Number,
  location: Schema.String,
  kg: Schema.Number,
  checkpoints: Schema.Record(Schema.String, Schema.Number), // one per source instance
  revision: Schema.Number, // incremented by every write, and its guard
})

const ShipmentSummaries = Entity.make({
  model: ShipmentSummary,
  entityType: "ShipmentSummary",
  primaryKey: {
    pk: { field: "pk", composite: ["shipmentId"] },
    sk: { field: "sk", composite: [] },
  },
})

const ReadTable = Table.make({ schema: AppSchema, entities: { ShipmentSummaries } })
```

## Several sources per row

```typescript region="projection" example="guide-projections-advanced.ts"
const ShipmentNotice = Schema.Struct({ shipmentId: Schema.String, kind: Schema.String })

const ShipmentProjection = EventStore.multiProjection({
  readModel: ShipmentSummaries,
  initial: (key) => ({
    shipmentId: key.shipmentId,
    parcels: 0,
    location: "",
    kg: 0,
    checkpoints: {},
    revision: 0,
  }),
  sources: (source) => ({
    order: source(OrderEvents, {
      key: (_orderId, event) => ({ shipmentId: event.data.shipmentId }),
      evolve: (state, event) =>
        Effect.succeed(
          event.data._tag === "OrderCancelled"
            ? EventStore.removeRow
            : { ...state, parcels: state.parcels + event.data.parcels },
        ),
    }),
    scan: source(ScanEvents, {
      key: (streamId) => ({ shipmentId: streamId.shipmentId }),
      evolve: (state, event) => Effect.succeed({ ...state, location: event.data.location }),
      mode: "latest", // each scan carries the whole location: only the newest matters
    }),
    weigh: source(WeighEvents, {
      key: (_sessionId, event) => ({ shipmentId: event.data.shipmentId }),
      // A tare reading changes nothing: skip it, so the row isn't written
      evolve: (state, event) =>
        Effect.succeed(
          event.data.kg === 0 ? EventStore.skipEvent : { ...state, kg: state.kg + event.data.kg },
        ),
    }),
  }),
  checkpoints: { field: "checkpoints" },
  revision: "revision",
  removal: {},
  outbox: {
    schema: ShipmentNotice,
    effects: (event, next) =>
      event.eventType === "Scanned" && next !== undefined
        ? [{ shipmentId: next.shipmentId, kind: `at ${next.location}` }]
        : [],
  },
})
```

- **Sources** are declared through the `source` helper. Each call infers its own stream's event types, against the row's key and state.
- **`key(streamId, event)`** names the row an event contributes to, as in a single-source projection. `Option.none()` means no row. One instance can feed many rows (one order, many shipments).
- **`evolve(state, event, { source, streamId })`** folds into the **whole** row, so one source's part can depend on another's. Sources interleave in any order across writes, so a source's `evolve` must not assume another's has run first. Within one write, sources are folded in declaration order, then by stream id, then by version.
- **`mode`:**
  - `"fold"` (the default) applies every event in version order and fills gaps from the store. Use it for events that change a few fields, where skipping one would lose data.
  - `"latest"` applies only the newest event of each instance in a batch, and nothing is read. Use it for events that carry the source's whole part. Events are tried newest first: one that `terminal` rejects falls back to the next older event. The events older than the one accepted are reported as `superseded`.
- **`terminal`** is per source.
- **One instance's failure is its own.** A failure `terminal` doesn't accept leaves that instance's events out of the write, with its checkpoint unmoved, and reports them as a `Failed` outcome. The row's other instances still apply in the same write. The row fails only when every instance does.

### Checkpoints per source instance

A row keeps one checkpoint per **source instance** (`<source>#<streamId>` in the `checkpoints` map). Each one means "every version up to here has been considered for this row". A second instance of the same source, such as an entity re-identified mid-stream that starts again at version 1, gets its own entry, so its early events are never mistaken for stale ones.

Rows that already keep one numeric field per source can map them instead:

```typescript
checkpoints: {
  field: "checkpoints", // optional: where a second instance goes
  sources: { weigh: { field: "weighVersion", offset: -1, instanceField: "weighSession" } },
}
```

- **`instanceField`** records which stream instance owns the scalar. An empty one (a new row, or a legacy one) is adopted by the first instance that arrives.
- **Another instance** goes to the map when one is declared. Without a map, it fails with `ProjectionSourceConflict` and nothing is written.
- **Adoption is a guess.** A legacy row is adopted by whichever instance arrives first. If that's the wrong one, `rebuild` repairs it ([below](#repair)).

### Rows written before the projection

A read model that already has rows lacks the projection's fields on every one of them, so it declares them optional. Each position accepts an optional field: `checkpoints.field`, a source's `field` and `instanceField`, and `revision` (and `checkpoint` on `projection`).

```typescript region="adoption" example="guide-projections-advanced.ts"
const WeightLog = Schema.Struct({
  shipmentId: Schema.String,
  kg: Schema.Number,
  // Absent on rows written before the projection
  weighVersion: Schema.optional(Schema.Number),
  weighSession: Schema.optional(Schema.String),
  checkpoints: Schema.optional(Schema.Record(Schema.String, Schema.Number)),
  revision: Schema.optional(Schema.Number),
})

const WeightLogs = Entity.make({
  model: WeightLog,
  entityType: "WeightLog",
  primaryKey: {
    pk: { field: "pk", composite: ["shipmentId"] },
    sk: { field: "sk", composite: [] },
  },
})

const WeightProjection = EventStore.multiProjection({
  readModel: WeightLogs,
  initial: (key) => ({ shipmentId: key.shipmentId, kg: 0 }),
  sources: (source) => ({
    weigh: source(WeighEvents, {
      key: (_sessionId, event) => ({ shipmentId: event.data.shipmentId }),
      evolve: (state, event) => Effect.succeed({ ...state, kg: state.kg + event.data.kg }),
    }),
  }),
  checkpoints: {
    field: "checkpoints",
    sources: { weigh: { field: "weighVersion", offset: -1, instanceField: "weighSession" } },
  },
  revision: "revision",
})
```

An absent field reads as empty:

- **A checkpoint** reads as none, so every event applies. On `projection` without a `revision`, the first write is conditioned on `attribute_not_exists` on the checkpoint field.
- **An `instanceField`** reads as unowned, so the first instance to arrive adopts it.
- **The map** reads as having no entries. It is written only once an instance lands in it, so a row whose instances all have their own fields keeps it absent.
- **The revision** reads as none: the write is conditioned on `attribute_not_exists`. A row written before the projection gets `initial` on its first projection write, like a new row, not `initial + 1`.

The write is the row `evolve` returns plus the fields the projection set, so an optional field the row didn't have, and the projection didn't set, stays absent.

## `revision`: one guard for every writer

Every write sets `revision` one higher and is conditioned on the value it read: `attribute_not_exists` when the row has none, which covers legacy rows.
- **Different sources serialise.** A writer that loses the race re-reads and retries with a jittered backoff, and no source's part is overwritten.
- **An existing write counter** that readers already use can serve as the revision. `revision: { field, initial: 0 }` sets the value of a row's first write, so a counter readers see from 0 keeps its numbering (the default is 1). An existing row without a revision also gets `initial` on its first write.
- **It is required** by multi-source projections and by the outbox, and is optional on `projection`. There it also makes `rebuild` safe to run alongside live delivery.

## Handling a batch

`EventStore.processBatch` takes multi-source projections next to single-source ones. Each record is decoded once and routed to every projection that reads its stream:

```typescript region="handler" example="guide-projections-advanced.ts"
type StreamBatch = { readonly Records: ReadonlyArray<EventStore.StreamRecord> }

const makeHandler = Effect.gen(function* () {
  const shipments = yield* EventStore.bindProjection(ShipmentProjection)
  return (batch: StreamBatch) =>
    EventStore.processBatch(batch.Records, {
      projections: { shipments },
      source: "lambda",
      // Deliver each written row's effects, in order, right after its write
      deliver: (effect, meta) => deliver(effect as typeof ShipmentNotice.Type, meta),
    }).pipe(Effect.map((result) => result.response))
})
```

Each row's outcome lists its instances: `{ source, streamId, applied, alreadyApplied, rejected, superseded, skipped, version }`. It also has the row's `state`, `removed`, `revision` and `enqueued`.

## Skipping an event

`evolve` may return `EventStore.skipEvent` for an event that should leave the row alone. No option enables it.

```typescript region="skip" example="guide-projections-advanced.ts"
const skip = yield* ShipmentProjection.applyBatch([{ stream: "weigh", event: tare! }])
```

- **Nothing is written** when a row's events are all skipped (or already applied). The outcome is `Applied`, with `applied: []`, the row as read, and the revision unchanged. Skipped events alone never create a row.
- **Reported in `skipped`, never in `applied`.** A skipped event produces no outbox effects. The fold carries on with the state from before it.
- **A mixed write is still one write.** When other events of the row apply (from the same instance or another), the row is written once, with the revision bumped once.
- **The checkpoint stops at the last applied or rejected event.** Skipped events below it are covered. A skipped event above it is not: it is read and decided again by the instance's next gap-fill, a redelivery, or `catchUp`, against the row as it is then. Keep the decision deterministic, as with `terminal`. An instance whose events keep being skipped re-reads them on every delivery.
- **Per instance.** When all of an instance's events were skipped, its map entry is not added and its field-mapped checkpoint and instance field are not written. An unowned field goes to the first instance of its source that writes it.
- **In `"latest"` mode**, a skipped newest event falls back to the next older one, as a rejection does.
- **Compared with the alternatives:**
  - Returning the state unchanged counts as a fold step: the row is written, the revision moves and the event is in `applied`.
  - A `terminal` rejection writes an existing row, and moves the checkpoint past the event.
  - A skip does neither.

## Removing rows

With `removal`, `evolve` may return `EventStore.removeRow`:

```typescript region="removal" example="guide-projections-advanced.ts"
const removed = yield* ShipmentProjection.applyBatch([{ stream: "order", event: cancelled! }])
```

- **A tombstone, not a deletion.** The row's key keeps a tombstone (`__edd_e__: "<entityType>#tombstone"`) with the checkpoints and revision and nothing else. A redelivery can't recreate the row.
- **Every entity read by key reports it as absent:** `get`, `Batch.get` and `Transaction.transactGet`. Queries filter it out, and it carries no index keys. Likewise, the read model's `create` (also in a transaction) may write where a tombstone is. It carries the tombstone's checkpoints over (with the revision one higher), so a late redelivery is still recognised as applied and can't undo the created row. With several projections on one read model, `create` carries the checkpoints the tombstone keeps, those of the projection that removed the row and of the others that wrote it.
- **Several projections on one read model.** Its rows carry a row token (`__edd_rt__`): random bits and a tag for each projection that has written the row. Every projection write is conditioned on the token it read, so a write that read the row before another projection's write fails and retries instead of replacing it. A tombstone keeps the other projections' checkpoints and revision, and a row written over it keeps them too, so their redeliveries are still recognised. A read model with one projection carries no token. Define every projection of a read model in each program that writes its rows: a program that defines only one of them writes no token, checks none and keeps nothing of the others.
- **One role per attribute in a projection.** When a projection on the read model has `removal`, a projection can't keep one stored attribute in two roles (its checkpoint stored as its revision, say): that's refused by whichever definition completes the conflict, its own or the first `removal` (`EDD-9133`). Without `removal`, rows are never tombstones and nothing is refused. Two projections may keep one attribute in different roles, such as two writing disjoint rows: each writes only its own attributes, so on its rows they keep their roles. Projections that share rows and swap an attribute's roles are broken, as on 1.39.0, and can't be detected. The table's TTL attribute is checked too when a projection's tombstones set it (`removal: { ttl }`): a checkpoint or revision stored there refuses the projections' writes with a `ValidationError` before any of them sends a request.
- **A checkpoint map stored as a sparse map can't be written.** Its keys hold `#`, so a write that adds one is refused with a `ValidationError`, and the tombstone write is refused the same way.
- **A later event** starts the row again from `initial`, from the tombstone's checkpoints.
- **`removal: { ttl }`** lets DynamoDB expire tombstones. Choose more than the change feed's 24 hours plus any redelivery or replay window: once a tombstone expires, a very late event recreates the row.
- **Refused** for read models with `unique` constraints, whose sentinels a tombstone write can't release.

## An ordered outbox

Side effects driven from `applied` are at most once: a crash after the write loses them. An outbox commits them **with** the row.

- **Commit:** `outbox.effects(event, next, context)` returns the effects an applied event produces. They are encoded through `outbox.schema` and written as outbox items in the same `TransactWriteItems` as the row (or tombstone). What can't be read back on that schema's stored side is refused at load (`EDD-9125`), naming the replacement: a `Schema.ReadonlyMap`, a `Schema.Date`, a `Schema.Redacted`, and [the rest in the modeling guide](/effect-dynamodb/guides/modeling/#types-that-cant-be-read-back). A value of a declaration of your own that wouldn't read back fails the write (`EDD-9126`). A write without effects stays a single `PutItem`.
- **Delivery:** `drain(rowKey, deliver)`, or `deliver` on `applyBatch` / `processBatch`, hands them over strictly in order per row. It claims the head item, delivers it, deletes it, and repeats.
  - A `deliver` failure leaves the effect at the head for the next drain, and is reported as `undelivered`. It never fails the record, because the effects are committed.
  - A crash leaves a claim that expires (`claimFor`, 30 s by default), so the effect is delivered again: **at least once**. Each effect carries its event's stream id and version, so consumers can deduplicate.
  - A successful delivery removes the effect, even if its claim expired meanwhile and another drainer took it over. So drainers never re-claim one another's heads in turn.
  - **Duplicates may interleave.** A drainer whose claim expired mid-delivery can still be delivering effect *n* when the next drainer has moved on to *n + 1*. So a duplicate of *n* can land after *n + 1*. Effects reach consumers in order, at least once, with possible duplicates out of order: deduplicate on `(streamId, version)`.
- **Order** is one sequence per row, across all its sources.
- **Where the items live:**
  - By default, in the row's own partition (`__edd_e__: "<entityType>#outbox"`). They show in the read model table's change stream and in full-table scans, but not in entity reads.
  - With `table` (keyed `keys`, default `pk` / `sk`) they go to another table, still in the same transaction. That keeps them out of the read model table's stream altogether.
  - An item is keyed by its row's key, so on a shared table each read model needs its own key space: a primary key (schema name and version, primary collection, entity type, and its composites' names) whose keys no other read model's whose outbox is on that table can be.
    - `DynamoClient.make` and `EventStore.processBatch` refuse two read models whose keys can be the same (`EDD-9134`): their items would overwrite each other. A composite's value is what its type can compose. A number's key text has no letters but `e` and those of `Infinity`, so a read model keyed by the number `n` (`n_0000000000000007`) and one keyed by the string `n_x` (`n_x_q`) bind. A date the library encodes as a string (a `DynamoModel` date schema, or `Schema.DateTimeUtc`, `Schema.Date` or `Schema.DateTimeZoned`, which the entity stores by its own encoding) is its ISO text, which starts with its year, so one keyed by the date `at` (`at_2026-11-11t08:00:00.000z`) and one keyed by `at_x` bind too, as long as no key one writes can be the other's even through a string holding `#`: after a string composite (`shop` then `at`, beside `shop` then `at_x`) they're refused. A date with a codec of its own (a transform to a date, `Schema.DateTimeUtcFromString` included) writes text the library doesn't know, so it's any text, as on 1.40.0. A literal union is one of its members, and a string any text.
    - Two that share only a prefix, such as one led by `shop` and one by `shop` then `branch`, bind and run: their keys meet only through a value holding `#` (`shop` = `north#branch_b1`). Each outbox item names its read model (see Sweeping), so `drainPending` and the outbox table's `rekey` tell their items apart. Writing at one revision, their items have one key, and the second is written beside the first (see Items at one key), so both are delivered. `escapeKeys: true` keeps the two read models' keys apart. An item written before 1.41.0 names none: `rekey` moves it by the read model whose key it can be when only one can have written it, or when each would move it to the same key. Otherwise it reads the row the item names from each read model's table and moves the item by the one whose own row is there. When none has the row, or a row tombstone or more than one row is there, the item is left where it is and counted in `skipped.ambiguousOwner`, with the reason in `ambiguous`; a rerun leaves it again. 1.40.0's `rekey` refused such read models, and a member of the outbox table that could read a read model's items as its own.
    - The outbox table's `rekey` refuses a member of that table with the read model's entity type whose items would overwrite the read model's, unless its primary key is the read model's: an entity claims its entity type's outbox items on its own table. Its composites may be limited to literals where the read model's aren't (a literal union beside a string): it reads and composes a value as one of its kind, so it moves the items where the read model would.
    - `rekey` also checks projections defined after the client was made. Tables are compared by the physical name requests go to, so two `Table.make` handles your layer gives one name are one table. Read models that never meet at any of these, bound separately or in different programs, can't be checked, so keep them apart yourself.
- **Items at one key:** from 1.41.0 each outbox item carries a mark, `__edd_rm__`: its read model's tag, then a hash of its projection and its event. An item's `Put` is conditioned on its key holding nothing or the item of the same effect, which it replaces (a redelivery or a retry). Any other item there keeps its place, and the new one is written beside it, at its key followed by `#` and its mark, which sorts right after it: both are delivered, in order. Items beside one key go in their marks' order: two of one projection's own effects are beside one key only after its revision started again (its row lost, or rebuilt by another projection) while its items were pending, and those two are delivered in their marks' order, which need not be the order they were applied in (1.40.0 kept only the later). Items meet at one key when two read models' row keys are the same text (above), when two projections of one read model, each with its own revision, write at one revision, and when a projection's revision starts again (its row deleted outside the projection, or its tombstone expired) with an item of another event still pending there. On 1.40.0 the second replaced the first, and its effect was never delivered. Nothing is read first: a collision costs one cancelled transaction, then the one sent. **A read model with several projections writing outbox items pays that on every write where two of them reach one revision, which is the ordinary course.** An item written before 1.41.0 carries no mark. One of the same event is replaced, as on 1.40.0, where nothing else can have written at its key: no other read model's keys can be this one's, and no other projection of it writes outbox items. Anywhere else it is kept and the new one written beside it, so **where it was this projection's own, rewritten after its row was lost, its effect is delivered twice.** **Where it is replaced, it can be delivered twice too: when its event is applied again after its row was lost, a drainer that delivers and deletes it between the cancelled transaction and the one sent next lets that one write it again.** Both need an item pending from before the upgrade; the outbox delivers at least once. Should the key beside be held too, the write fails (`EDD-9145`), and nothing is written.
- **Limit, one physical table under two `Table.make` handles:** these decisions read the `Table.make` definitions, so a second handle on the same physical table isn't seen. Read models whose row keys meet only through such handles count as apart, so an unmarked item of the same event at the key is replaced, as on 1.40.0, even where it is the other read model's (its effect is lost, as on 1.40.0). An index attribute named `__edd_rm__` declared only through the other handle doesn't stop the mark (below): the items carry it, and enter that index.
- **The mark's name:** **a read model whose outbox items are written where `__edd_rm__` is already a key attribute (the outbox table's key or index attributes, or any key attribute of that table: a member's primary or secondary index, an aggregate's, an event stream's index) runs without the mark, exactly as on 1.40.0, and doesn't get this protection: two items at one key replace each other. Rename that attribute to get it.** It's decided from the definitions, never from what a stored item holds.
- **Sweeping:** `drainPending(deliver)` finds rows with pending effects through `outbox.index`, a sparse index whose key attributes only outbox items carry. It covers rows that receive no further events. It drains its own read model's items only: read models of one entity type may share the index, and each one's drainer leaves the others' items, unclaimed, to them. An item is its own when the row it names has a key its read model writes, for values of its composites' types (a read model keyed by a date drains `at_2026-11-11t08:00:00.000z`, never the label `at_x_q`), and, from 1.41.0, when the item names its read model: an outbox item's mark (`__edd_rm__`) starts with a tag of its read model's key template, so two read models whose keys meet only through a string value holding `#` (one keyed by `shop`, one by `shop` then `branch`) each drain exactly their own. An item written before 1.41.0 carries no mark: one at a key both read models can write is drained by both drainers, as on 1.40.0. Outbox items are short-lived, so those drain away after an upgrade. A 1.40.0 drainer still running in a rolling deployment delivers and deletes the items 1.41.0 writes, the ones beside another included, in order, as it does any other. **Where two read models' row keys can be the same text, upgrade their drainers before their writers: a 1.40.0 drainer takes the other read model's items at its row for its own, as it always did, and those now include the items kept beside its own.** `drain` and `deliver` decide the same way, item by item: where two read models' row keys are the same text (`shop` = `north#branch_b1` beside `shop` = `north` and `branch` = `b1`), their items share a row key, and each drainer passes over the other's.
- **Limit:** a transaction holds 100 items, so one row write can commit at most 99 effects.

## Repair

`rebuild(rowKey, { instances })` re-derives a row from the named instances. A `sourcesOf(rowKey)` in the config can find them instead, for example over a stream index.
- It folds each instance's events keyed to the row from `initial`.
- It writes every checkpoint from scratch, with the next revision.
- A field-mapped scalar goes to the first instance in fold order, which repairs a row adopted by the wrong instance.

```typescript region="rebuild" example="guide-projections-advanced.ts"
const rebuilt = yield* ShipmentProjection.rebuild(
  { shipmentId: "sh-1" },
  {
    instances: {
      order: [{ orderId: "o-1" }],
      scan: [{ shipmentId: "sh-1" }],
      weigh: [{ sessionId: "w-1" }],
    },
  },
)
```

`catchUp(rowKey)` brings every instance the row's checkpoints know up to its head.
