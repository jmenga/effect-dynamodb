This guide covers how to define access patterns using indexes, how key generation works, and how to use collections for cross-entity queries.

## Entity Primary Key

Entities define their **primary key** and **GSI indexes** together. Collections are auto-discovered from entities sharing the same `collection` name on a GSI.

```typescript region="task-entity" example="guide-indexes.ts"
const Tasks = Entity.make({
  model: Task,
  entityType: "Task",
  primaryKey: {
    pk: { field: "pk", composite: ["taskId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    byProject: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["projectId"] },
      sk: { field: "gsi1sk", composite: ["priority"] },
    },
    byAssignee: {
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["employeeId"] },
      sk: { field: "gsi2sk", composite: ["priority"] },
    },
  },
  timestamps: true,
})
```

### Anatomy of a Primary Key

```typescript
primaryKey: {
  pk: {
    field: "pk",                         // Physical DynamoDB attribute
    composite: ["taskId"],               // Model attributes -> partition key
  },
  sk: {
    field: "sk",
    composite: [],                       // Empty = one item per partition key
  },
}
```

| Property | Type | Required | Description |
|----------|------|----------|-------------|
| `pk.field` | `string` | Yes | Physical DynamoDB attribute name |
| `pk.composite` | `string[]` | Yes | Model attributes composing the partition key |
| `sk.field` | `string` | Yes | Physical DynamoDB attribute name |
| `sk.composite` | `string[]` | Yes | Model attributes composing the sort key |

### Access Patterns via the Primary Index

Every entity exposes a `.primary(...)` query accessor on the bound client — the primary index is treated symmetrically with GSI indexes. Pass the required PK composites (and optionally one or more SK composites) to return a `BoundQuery`:

```typescript
// `Memberships` primary key: pk = orgId, sk = userId
//
// List all items under a shared primary partition key (PK only)
const allMembers = yield* db.entities.Memberships.primary({
  orgId: "org-acme",
}).collect()

// Narrow by partial SK composite (begins_with prefix match)
const acmeAdmins = yield* db.entities.Memberships.primary({
  orgId: "org-acme",
})
  .filter({ role: "admin" })
  .collect()
```

This is the natural access pattern for shared-PK single-table designs — for example a join table that holds many channel grants under one `accountId`. Use `.get(fullKey)` when you want a strongly-consistent single-item fetch by the full composite key; use `.primary(partialKey)` when you want a `Query` that returns every item in the partition (or a prefix-matched subset).

### GSI Access Patterns via Entity Indexes

GSI access patterns are defined directly on the entity via the `indexes` property. Each index specifies the physical GSI, PK composites, and SK composites — see the `task-entity` block above for the canonical shape.

Several entities can overload one physical GSI (`gsi1` serving `byProject` on one entity and `byTenant` on another), but one physical index has one key schema. Every member of a table that declares it, including the auto-generated `_cascade_<field>` indexes and an aggregate's collection and list indexes, must name the same `pk.field` / `sk.field` and agree on GSI versus LSI. Entities on one table must also declare the same primary-key fields. `Table.make` and `Table.definition` throw `[EDD-9069]`, naming both declarers, when they differ; earlier releases silently kept the first declaration, so the other member's items never reached the index.

### Z-order Sort Keys

A secondary index's sort key half can declare `zorder` instead of `composite`: a list of dimensions whose values are bit-interleaved into one binary (`B`) sort key, so a single query can bound several attributes at once with `.within()`. Optional `prefix` composites are exact-match and sit in front of the address:

```typescript region="zorder-entity" example="guide-zorder.ts"
const Listings = Entity.make({
  model: Listing,
  entityType: "Listing",
  primaryKey: {
    pk: { field: "pk", composite: ["listingId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    search: {
      name: "gsi1",
      // Exact-match facets, as for any index: one partition per region.
      pk: { field: "gsi1pk", composite: ["region"] },
      sk: {
        field: "gsi1sk", // a binary (B) attribute
        prefix: ["agencyId"], // exact-match, in front of the address
        zorder: [
          // Declaration order is interleave priority.
          { field: "price", min: 0, max: 5_000_000, step: 1_000 }, // 13 bits
          { field: "bedrooms", min: 0, max: 15 }, // 4 bits
          { field: "listedAt", from: "2024-01-01", unit: "hours", bits: 16 }, // 16 bits
        ],
      },
    },
  },
})
```

`zorder` belongs on a secondary index's sort key half: not on the primary key, not on a partition key half, and never together with `composite` (`[EDD-9086]`). The physical attribute is declared `B` in the table definition; the partition key half stays an ordinary string key. The [Z-order Indexes guide](/effect-dynamodb/guides/zorder/) covers the dimensions, the key layout, the read strategies, and when Z-order pays; [indexPolicy](/effect-dynamodb/guides/index-policy/#z-order-sort-keys) covers how writes keep the address current.

### Logical Names as API Surface

Collection names become query accessors on the typed client:

```typescript region="query-accessors" example="guide-indexes.ts"
// Logical names become query accessors — no physical index names in code
const alphaTasks = yield* basic.entities.Tasks.byProject({ projectId: "proj-alpha" }).collect()

const aliceTasks = yield* basic.entities.Tasks.byAssignee({ employeeId: "emp-alice" }).collect()
```

You never reference physical index names (`gsi1`, `gsi2`) in application code.

## Key Generation

effect-dynamodb generates DynamoDB key values automatically from your composite declarations. You declare *which* attributes compose each key — the system handles *how*.

### Format

```
$<schema>#v<version>#<prefix>#<attrName>_<value>#<attrName>_<value>
```

Each composite value is prefixed with its attribute name (separated by `_`) and segments are joined with `#`. Given `DynamoSchema({ name: "myapp", version: 1 })` and `entityType: "Task"`:

| Composite | Generated Key |
|-----------|---------------|
| `["taskId"]` with value `"t-001"` | `$myapp#v1#task#taskid_t-001` |
| `["projectId", "status"]` with values `"proj-alpha"`, `"active"` | `$myapp#v1#task#projectid_proj-alpha#status_active` |
| `[]` (empty) | `$myapp#v1#task` |

A [Z-order sort key](#z-order-sort-keys) is the exception: it is binary, holds the prefix segments and the interleaved address only, and carries no schema, version or entity type prefix.

### Empty Composites

Both `pk.composite` and `sk.composite` can be empty arrays. The entity type prefix guarantees no collisions between entity types.

| pk | sk | Use Case |
|----|----|----------|
| `[]` | `[]` | Singleton (config, counters) |
| `["userId"]` | `[]` | One item per user |
| `[]` | `["userId"]` | All users in one partition |
| `["tenantId"]` | `["userId"]` | Users partitioned by tenant |

### Attribute Serialization

| Type | Key Value |
|------|-----------|
| `string` | As-is; in a sort key, characters up to `%` escaped ([Sort key text](#sort-key-text)) |
| `number`, `bigint` | Numeric key text (below) |
| `DateTime.Utc` | ISO 8601 |
| `boolean` | `"true"` / `"false"` |
| Branded string | Underlying value |

### Numeric composites

DynamoDB orders sort keys as text, byte by byte, so numbers are written as text that sorts in numeric order. Ranges with `.where()` and `.within()` over a numeric composite return rows in numeric order, negatives and fractions included.

| Value | Key text |
|-------|----------|
| `42` | `0000000000000042` (16 digits; a `bigint` is padded to 38) |
| `3.14` | `0000000000000003.14` |
| `1e21` | `:0211` (exponent and digits, for 1e16 and up; 1e38 and up for a `bigint`) |
| `-3.14` | `-9999999999999996.85:` (each digit complemented, so larger magnitudes sort first) |
| `Infinity` / `-Infinity` | `;` / `-)` |

The text holds no letters and no `#`, so casing never changes it. A composite holding one numeric value matches only that value: a query accessor given every sort key composite sends `sk = …`, so `seq: 3` never returns `3.14` or `3.5` (see [Queries](/effect-dynamodb/guides/queries/#how-much-of-the-sort-key-an-accessor-pins)).

`NaN` has no order and can't be a key composite. An entity operation given one — `put`, `create`, `upsert`, `update`, `get`, `delete`, `restore`, `purge`, `append`, or a batch or transaction — fails with a `ValidationError` (`EDD-9096`) before anything is sent, and a query accessor, `.where()` or `.within()` given one throws it. Up to 1.36 a `get` by a `NaN` key failed with `ItemNotFound` and a `delete` did nothing. A bigint of more than 1,000 digits is refused the same way. Aggregates and event stores don't convert it: there it is a defect.

:::caution[Stored keys changed in 1.37.0]
Up to 1.36, a number was zero-padded as text (`String(n).padStart(16, "0")`), which sorted `-3` above `-5` and `10.5` below `3.14`. Non-negative integers below 1e16 (below 1e38 for a `bigint`) keep the same key text. Every other value composes different text: negatives, fractions, 1e16 and up, `Infinity`, and a `DateEpochMs` or `DateEpochSeconds` date before 1970. A row written by 1.36 with one in a key keeps its old key until it moves. Single-item operations still find it, and move it the first time they write it, and queries that pin its key read it (see [Migrating rows written by 1.36](#migrating-rows-written-by-136)); a range bound misses or misorders it until it moves.
:::

### Sort key text

In a sort key, a string's text escapes every character up to `%` — control characters, space, `!`, `"`, `#`, `$` and `%` — as `%` and two hex digits, after casing:

| Value | Sort key text (`"lowercase"` casing) |
|-------|--------------------------------------|
| `new york` | `new%20york` |
| `a#b` | `a%23b` |
| `50%` | `50%25` |
| `"Line\nTwo"` | `line%0atwo` |

Every remaining character sorts above the `#` that follows a composite, so keys sort as their values do and a value may hold `#`: a bound on any composite is one key condition that returns exactly the values it means, and `a` neither equals nor prefixes `a#b` (see [Queries](/effect-dynamodb/guides/queries/#sort-key-conditions)). Every sort key composed from composite values is escaped: table and index sort keys, time-series event keys, version snapshot and tombstone keys, aggregate sort keys and Z-order prefix segments. Partition keys and unique-constraint values aren't, and the stored attribute keeps its value.

:::caution[Stored keys changed in 1.37.0]
Up to 1.36 a sort key held a string's text as it was: a space, `!`, `"` or control character sorted below the `#` after a composite, so `new york` sorted before `new` and bounds returned the wrong rows, and `#` split a value in two. A string without a character up to `%` keeps the same key text. A row written by 1.36 with such a string in a sort key composite, or as a time-series `orderBy`, keeps its old sort key until it moves (below); partition keys are unaffected.
:::

### Migrating rows written by 1.36

Through 1.37.x, single-item operations keep working over rows 1.36 wrote under key text that has since changed. `get`, `getVersion`, `deleted.get`, `Batch.get` and `Transaction.transactGet` read the 1.36 key when the current key misses. `put`, `create`, `upsert`, `update`, `patch`, `append`, `delete`, `deleteIfExists`, soft delete, `restore`, `purge` and `Batch.write` act on the item wherever it is; the first write moves it to its current key, recomposing its index keys under their index policy and moving its unique-constraint sentinels and, on a `retain` entity, the snapshot of the version it is at (older snapshots and tombstones stay where they are and are read there), and a unique value held under its 1.36 sentinel stays taken. Concurrent first writes of an unmoved item all succeed. An operation whose keys did not change sends exactly the requests it always did.

Moving costs requests while the fallback is on. A conditioned `put`, `upsert`, `update`, `patch` and `append` are sent first, as if the item were at its current key; only when that finds no item do they move it (one read of the 1.36 key and one transaction) and send again, so creating a new item this way costs one failed conditional write more. An unconditioned `put` of an item whose key text changed is always one transaction of two items, a Put at the current key and a Delete at the 1.36 key: twice the write capacity of a plain put for each, and a concurrent transaction on either key can cancel it, which the put retries up to three times. A value holding `%` and no character below it, whose 1.36 key can be another value's current key (below), is put as a conditioned put is. `Batch.write` deletes a put's 1.36 key in a later request, once the put is written. On a `retain` entity a move also reads the snapshot of the item's version and moves it in the same transaction: one more strongly consistent read and two more transaction items.

1.36 didn't escape sort key text, so the 1.36 key of a string holding `%` and two hex digits can be another value's current key: `foo%20bar`'s 1.36 row sits where `foo bar` is stored now, and `x%23y`'s where `x#y` is. Operations tell the two apart by the row's values. A `get`, a batch or transaction read, or an accessor query of `foo bar` doesn't return `foo%20bar`'s row. `update`, `patch` and `delete` of `foo bar` treat it as no item, and `purge` deletes only the item's own rows. A write that needs the key — a `put`, `create` or `upsert` of `foo bar`, or the move of `foo bar`'s own 1.36 row — first moves `foo%20bar`'s row to its own current key. The other way round, a write of `foo%20bar` leaves `foo bar`'s row at its 1.36 key alone: a `put` of it is sent as a conditioned put is, and `create` and `restore` read that key first. A retained `foo%20bar` created afresh continues its own versions, not `foo bar`'s, and each lists only its own: 1.36 kept `foo%20bar`'s version history under the prefix `foo bar`'s history is under now, so a write of `foo bar` whose version snapshot lands on one of `foo%20bar`'s moves that snapshot to `foo%20bar`'s current key first. `Transaction.transactWrite` can't move the row, so it fails `ItemNotMoved` naming the item that holds the key; write that item once through the entity first.

A transaction can't move an item: an update, patch, conditioned put or delete, guarded put or condition check in `Transaction.transactWrite` of an item still under its 1.36 key fails with `ItemNotMoved` (`EDD-9097`) and writes nothing. Write the item once through the entity, then run the transaction again.

A query that pins a key prefix reads the 1.36 key for the same pins too: an index or primary accessor (its pins, and an `eq` or `beginsWith` in `.where()` that extends them), `Entity.query.*`, a collection, `.history()`, `versions()`, `deleted.list()` and `count()`. It reads the 1.36 key first and the current key second (the other way round under `.reverse()`), so `limit`, pages and `count()` span both and a cursor resumes in the right one. Rows still under their 1.36 key come first, in their 1.36 order: the two keys are read one after the other, not merged. `versions()` lists a version whose snapshot is under both keys once, from the current key; to know which, it first looks under the 1.36 key (one keys-only read of one row) and, when a snapshot is there, reads the current key's versions (keys only).

Aggregates are read under both keys, and `update` moves every row it finds under a 1.36 key in the same transaction as its write, and recomposes a root's list keys that hold 1.36 text, so an `update` that changes nothing moves the aggregate; `create` fails `ConditionalCheckFailed` when the aggregate exists under its 1.36 key, and `list` lists it. An event store stream whose stream id's key text changed (a number passed as a stream id) is read and appended under its 1.36 key until `rekey` moves it: it is never split across the two keys, and a new stream starts under its current key. An append to it carries one more check, that `rekey` hasn't moved it meanwhile; an append that loses that race fails with `VersionConflict`, and finds the stream at its current key when it is retried. A projection reads a read-model row, or its tombstone, under its 1.36 key and folds onto it, and its next write moves it; `drain(key)` and `drainPending` deliver a row's outbox effects under both keys in one order. An effect of `foo bar`'s row never replaces `foo%20bar`'s pending one at the same key: it moves that one to `foo%20bar`'s current key first, and each `drain(key)` delivers only its own row's effects.

Until a row moves, some reads are not transparent:

- A range bound in `.where()` (`gt`, `gte`, `lt`, `lte`, `between`) and `.within()` read the current key only, so they miss rows still under their 1.36 key.
- Rows under their 1.36 keys come before the others (after them under `.reverse()`), in 1.36's order: a negative number sorts above a smaller one.
- Time-series events of a `NumberFromString` or `BigIntFromString` `orderBy` that 1.36 wrote come before the current ones, in 1.36's order, and `.history().where()` bounds hold on their numbers; to do that, a bounded `.history()` reads all of the item's events. Events of a `Schema.Number` `orderBy` that is negative, fractional or 1e16 and up, or of a string `orderBy` holding a character up to `%`, are read in text order and bounds compare text.
- A collection query can return another value's 1.36 row stored at a key it pins (`foo%20bar`'s under pins on `foo bar`), and an `append` overwrites another value's 1.36 event stored under the same key text. (`deleted.list()` lists every tombstone in the partition, as it always has.)
- A `many` edge's elements over unmoved rows assemble in key text order.

To move every remaining row, run `db.tables.<Table>.rekey()` once the deploy has finished: it scans the table and moves each row the way its own operations would — items with their index keys and unique sentinels, version snapshots, tombstones, time-series events, aggregates, event streams, and projections' row tombstones and outbox items — reports conflicts instead of overwriting anything, and moves nothing on a rerun. Once a rerun moves nothing and reports no conflicts, turn the fallback off with `DynamoSchema.make({ name, version, legacyKeys: false })`; the fallback and the setting are removed in the next major release. [Upgrading from 1.36](/effect-dynamodb/guides/upgrading/) walks through it: the dry run, resuming a bounded run, what each kind of row costs, and resolving conflicts.

### Casing Resolution

Casing is applied across the generated key — schema name, entity type, collection name, composite attribute names, **and composite attribute values**. Resolution order:

1. Index-level `casing` (highest priority) — on `primaryKey` or on any entry in `indexes`
2. Schema-level `casing` (default: `"lowercase"`)

Under the default `"lowercase"`, `"Emp-Alice"` and `"emp-alice"` produce identical keys. The original attribute value is preserved on the stored attribute itself — only the composed key string is cased.

```
// With casing: "lowercase", entityType: "Employee", employeeId: "Emp-Alice"
// Composed PK:      $myapp#v1#employee#employeeid_emp-alice
// Stored attribute: employeeId = "Emp-Alice"  (original casing preserved)
```

An index's own `casing` overrides the schema's for that index's keys — entity type or collection name and composites, in both halves. The `$<schema>#v<n>` prefix keeps the schema's casing. Use it when one access pattern needs case-sensitive values on a schema that folds case:

```typescript region="index-casing" example="guide-indexes.ts"
// External references are case-sensitive: "AbC-1" and "abc-1" are different
// accounts. The schema folds case, so this index keeps it with its own `casing`.
class Integration extends Schema.Class<Integration>("Integration")({
  integrationId: Schema.String,
  externalRef: Schema.String,
}) {}

const Integrations = Entity.make({
  model: Integration,
  entityType: "Integration",
  primaryKey: {
    pk: { field: "pk", composite: ["integrationId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    byExternalRef: {
      name: "gsi1",
      casing: "preserve",
      pk: { field: "gsi1pk", composite: ["externalRef"] },
      sk: { field: "gsi1sk", composite: [] },
    },
  },
})

const CasingTable = Table.make({ schema: AppSchema, entities: { Integrations } })
```

```typescript region="index-casing-queries" example="guide-indexes.ts"
yield* casing.entities.Integrations.put({ integrationId: "int-1", externalRef: "AbC-1" })
yield* casing.entities.Integrations.put({ integrationId: "int-2", externalRef: "abc-1" })

// gsi1pk: $myapp#v1#Integration#externalRef_AbC-1 — the case survives
const exact = yield* casing.entities.Integrations.byExternalRef({ externalRef: "AbC-1" }).collect()
// → [int-1] only. With the schema's "lowercase", both items share one gsi1pk and both return.
```

Entities sharing a collection compose its keys together, so they must agree on the collection index's casing — a mismatch fails at `DynamoClient.make()` / `Collection.make()` with `EDD-9055`. An index `casing` equal to the schema's agrees with an index that sets none.

:::caution[Setting `casing` on an index that holds data]
Changing an index's casing changes the keys it composes. Items written before keep their old index keys until they are written again, so queries through that index won't find them in the meantime. Before 1.22, `casing` on an `indexes` entry was accepted but ignored — if you had set it, items written by earlier versions carry schema-cased keys for that index.
:::

## Collections

Collections group multiple entity types that share a partition key, enabling cross-entity queries. Two modes are supported: **isolated** (default) and **clustered**. Isolated keeps each entity's sort-key namespace separate so single-entity scans remain efficient; clustered places the collection name above each entity's sort key so all members are physically interleaved (required for sub-collections).

### Isolated Collections

Each entity owns its sort key prefix. Collection queries use only the partition key — no sort key condition.

```typescript region="isolated-entities" example="guide-indexes.ts"
const IsolatedEmployees = Entity.make({
  model: Employee,
  entityType: "Employee",
  primaryKey: {
    pk: { field: "pk", composite: ["employeeId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    departmentStaff: {
      collection: "departmentStaff",
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["department"] },
      sk: { field: "gsi1sk", composite: ["hireDate"] },
    },
  },
  timestamps: true,
})

class Equipment extends Schema.Class<Equipment>("Equipment")({
  equipmentId: Schema.String,
  department: Schema.String,
  name: Schema.String,
  purchaseDate: Schema.String,
}) {}

const Equipments = Entity.make({
  model: Equipment,
  entityType: "Equipment",
  primaryKey: {
    pk: { field: "pk", composite: ["equipmentId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    departmentStaff: {
      collection: "departmentStaff",
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["department"] },
      sk: { field: "gsi1sk", composite: ["purchaseDate"] },
    },
  },
  timestamps: true,
})
```

**Sort key format (isolated):**

```
$myapp#v1#employee_1#hiredate_2020-01-15        <- Employee entity owns its SK
$myapp#v1#equipment_1#purchasedate_2023-06-01   <- Equipment entity owns its SK
```

**Query behavior:**

| Query | Mechanism | Returns |
|-------|-----------|---------|
| Everything | PK only (no SK condition) | Employee + Equipment |
| Employees only | PK + `begins_with(SK, "$myapp#v1#employee_1")` | Employee |

**Best for:** High-volume single-entity queries where cross-entity queries are occasional.

### Clustered Collections

The collection name sits at the top of every entity's sort key. All entities share this prefix.

```typescript region="clustered-entities" example="guide-indexes.ts"
const ClusteredEmployees = Entity.make({
  model: Employee,
  entityType: "Employee",
  primaryKey: {
    pk: { field: "pk", composite: ["employeeId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    tenantMembers: {
      collection: "tenantMembers",
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["tenantId"] },
      sk: { field: "gsi1sk", composite: ["department", "hireDate"] },
      type: "clustered",
    },
  },
  timestamps: true,
})

const ClusteredTasks = Entity.make({
  model: Task,
  entityType: "Task",
  primaryKey: {
    pk: { field: "pk", composite: ["taskId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    tenantMembers: {
      collection: "tenantMembers",
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["tenantId"] },
      sk: { field: "gsi1sk", composite: ["projectId", "taskId"] },
      type: "clustered",
    },
  },
  timestamps: true,
})
```

**Sort key format (clustered):**

```
$myapp#v1#tenantmembers#employee_1#department_engineering#hiredate_2020-01-15
$myapp#v1#tenantmembers#task_1#projectid_proj-alpha#taskid_t-001
^^^^^^^^^^^^^^^^^^^^^^^^^^
collection prefix (shared)
```

**Query behavior:**

| Query | Mechanism | Returns |
|-------|-----------|---------|
| Everything | PK + `begins_with(SK, "$myapp#v1#tenantmembers")` | Employee + Task |
| Employees only | PK + `begins_with(SK, "$myapp#v1#tenantmembers#employee_1")` | Employee |
| Tasks only | PK + `begins_with(SK, "$myapp#v1#tenantmembers#task_1")` | Task |

**Best for:** Cross-entity queries, relationship-dense data.

### Hierarchical Sub-Collections

True parent/child sub-collections nest the collection hierarchy in the sort key so a `begins_with` query at the parent level returns the parent's items **and** every descendant. Two requirements:

1. Use the array form on the entity index: `collection: ["parent", "child"]` (deeper levels add more elements).
2. Use `type: "clustered"` so the SK puts the hierarchy above the entity-type prefix.

In the example below, `Employee` lives at the parent level (`["contributions"]`) while `Task` and `ProjectMember` live one level deeper (`["contributions", "assignments"]`). All three share `gsi2` keyed on `employeeId`:

```typescript region="subcollection-entities" example="guide-indexes.ts"
// True hierarchical sub-collections via the array form `collection: ["parent", "child"]`
// + `type: "clustered"`. The full hierarchy is written into the SK so a begins_with
// query at the parent level matches every descendant — querying "contributions"
// returns SubEmployee + SubTasks + SubProjectMembers, while "assignments" returns
// only SubTasks + SubProjectMembers.
const SubEmployee = Entity.make({
  model: Employee,
  entityType: "Employee",
  primaryKey: {
    pk: { field: "pk", composite: ["employeeId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    contributions: {
      collection: ["contributions"],
      type: "clustered",
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["employeeId"] },
      sk: { field: "gsi2sk", composite: ["department"] },
    },
  },
  timestamps: true,
})

const SubTasks = Entity.make({
  model: Task,
  entityType: "Task",
  primaryKey: {
    pk: { field: "pk", composite: ["taskId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    assignments: {
      collection: ["contributions", "assignments"],
      type: "clustered",
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["employeeId"] },
      sk: { field: "gsi2sk", composite: ["projectId", "taskId"] },
    },
  },
  timestamps: true,
})

const SubProjectMembers = Entity.make({
  model: ProjectMember,
  entityType: "ProjectMember",
  primaryKey: {
    pk: { field: "pk", composite: ["employeeId", "projectId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    assignments: {
      collection: ["contributions", "assignments"],
      type: "clustered",
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["employeeId"] },
      sk: { field: "gsi2sk", composite: ["projectId"] },
    },
  },
  timestamps: true,
})
```

**SK shape written by each entity:**

| Entity | SK |
|--------|----|
| `SubEmployee` | `$myapp#v1#contributions#employee_1#department_engineering` |
| `SubTasks` | `$myapp#v1#contributions#assignments#task_1#projectid_p-α#taskid_t-001` |
| `SubProjectMembers` | `$myapp#v1#contributions#assignments#projectmember_1#projectid_p-α` |

Both descendant SKs start with the parent prefix `$myapp#v1#contributions`, so a query at the parent level returns all three. The child query uses the longer prefix `$myapp#v1#contributions#assignments` and returns only the two descendant entities.

**Query at any depth:**

| Collection | begins_with prefix | Returns |
|------------|-------------------|---------|
| `contributions` | `$myapp#v1#contributions` | `Employee` + `Task` + `ProjectMember` |
| `assignments` | `$myapp#v1#contributions#assignments` | `Task` + `ProjectMember` |

```typescript
// Parent — includes everything
const contributions = yield* db.collections
  .contributions({ employeeId: "emp-alice" })
  .collect()
// { SubEmployee: Employee[], SubTasks: Task[], SubProjectMembers: ProjectMember[] }

// Child — only descendants
const assignments = yield* db.collections
  .assignments({ employeeId: "emp-alice" })
  .collect()
// { SubTasks: Task[], SubProjectMembers: ProjectMember[] }
```

:::note[When to use sub-collections]
Sub-collections are an advanced pattern — they cost a clustered SK layout and require every entity in the hierarchy to share the same physical GSI. Reach for them when you need a single query to return multiple entity types in a strict parent/child relationship without doing N queries. For independent collections that just happen to share an index, use a single-element string (`collection: "name"`) instead.
:::

### Defining Collections

Collections are defined by adding a `collection` property to entity indexes. Entities sharing the same `collection` name on the same physical GSI are automatically grouped into a collection by `DynamoClient.make()`:

```typescript
// On EmployeeEntity
indexes: {
  tenantMembers: {
    collection: "tenantMembers",
    name: "gsi1",
    pk: { field: "gsi1pk", composite: ["tenantId"] },
    sk: { field: "gsi1sk", composite: ["department", "hireDate"] },
    type: "clustered",
  },
}

// On TaskEntity — same collection name + same GSI
indexes: {
  tenantMembers: {
    collection: "tenantMembers",
    name: "gsi1",
    pk: { field: "gsi1pk", composite: ["tenantId"] },
    sk: { field: "gsi1sk", composite: ["projectId", "taskId"] },
    type: "clustered",
  },
}
```

When you call `DynamoClient.make({ entities, tables })`, the client auto-discovers that both entities share the `tenantMembers` collection and exposes `db.collections.tenantMembers(...)` as a cross-entity query accessor.

### Validation Rules

- All entities in a collection must share the same PK composite on that index
- All entities sharing an index must agree on the type (no mixing isolated/clustered)
- Sub-collections sharing an index must use the same PK and SK fields
- Every member declaring one physical index must use the same key attributes (`[EDD-9069]`, thrown by `Table.make` / `Table.definition`)
- A Z-order index can't declare `collection` or join one (`[EDD-9090]`): its binary sort key has no entity type prefix to tell members apart
- One physical attribute can't be a binary Z-order half on one member and a string key half on another (`[EDD-9091]`)
- No duplicate entity types within a single collection

## Worked Example: Multi-Tenant Project Management

### Access Patterns

| Pattern | Collection | PK | SK |
|---------|-----------|----|----|
| Get employee by ID | primary | `employeeId` | -- |
| Get task by ID | primary | `taskId` | -- |
| Employees in tenant | TenantMembers (gsi1) | `tenantId` | `department`, `hireDate` |
| Tasks in tenant | TenantMembers (gsi1) | `tenantId` | `projectId`, `taskId` |
| All tenant items | TenantMembers (gsi1) | `tenantId` | -- |
| Employee by email | ByEmail (gsi2) | `email` | -- |
| Tasks by assignee | ByAssignee (gsi2) | `employeeId` | `priority` |

### DynamoDB Items

Each composite value in a key is prefixed with its attribute name (e.g., `employeeid_emp-alice`). Structural parts (schema, entity type, collection) are cased according to the schema/index casing rules.

| pk | sk | gsi1pk | gsi1sk | __edd_e__ |
|----|----|--------|--------|------------|
| `$myapp#v1#employee#employeeid_emp-alice` | `$myapp#v1#employee` | `$myapp#v1#tenantmembers#tenantid_t-acme` | `$myapp#v1#tenantmembers#employee_1#department_engineering#hiredate_2024-01-15` | Employee |
| `$myapp#v1#task#taskid_t-001` | `$myapp#v1#task` | `$myapp#v1#tenantmembers#tenantid_t-acme` | `$myapp#v1#tenantmembers#task_1#projectid_proj-alpha#taskid_t-001` | Task |
