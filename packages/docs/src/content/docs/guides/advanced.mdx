This guide covers rich update operations, batch operations, multi-table design, the low-level expression builder API, and timeouts and cancelling requests.

## Updating Items

Beyond `.set()`, effect-dynamodb provides combinators for all DynamoDB update expression types. Chain them on the `BoundUpdate` builder from `db.entities.X.update(key)` — they compile to one `UpdateItem` call.

### Removing Attributes

Deletes attributes entirely from the item:

```typescript region="remove" example="guide-advanced.ts"
  // #region remove
  yield* db.entities.Products.update({ productId: "p-1" }).remove(["description"])
```

### Atomic Increment

Atomically increments numeric attributes. Thread-safe — no read-modify-write cycle:

```typescript region="add" example="guide-advanced.ts"
yield* db.entities.Products.update({ productId: "p-1" }).add({ viewCount: 1, stock: 50 })
```

### Atomic Decrement

Synthesizes `SET #field = #field - :val` (DynamoDB has no native subtract):

```typescript region="subtract" example="guide-advanced.ts"
yield* db.entities.Products.update({ productId: "p-1" }).subtract({ stock: 3 })
```

### Appending to Lists

Appends elements to the end of a list attribute using `list_append`. Each element is encoded through the list's element schema, so a list of dates stores its wire form:

```typescript region="append" example="guide-advanced.ts"
  // #region append
  yield* db.entities.Products.update({ productId: "p-1" }).append({
    tags: ["on-sale", "featured"],
  })
```

### Removing from Sets

Removes specific elements from a DynamoDB Set attribute (StringSet, NumberSet):

```typescript region="delete-from-set" example="guide-advanced.ts"
  // #region delete-from-set
  yield* db.entities.Products.update({ productId: "p-1" }).deleteFromSet({
    categories: new Set(["obsolete"]),
  })
```

Removing the last element is fine. DynamoDB can't store an empty set, so the attribute goes, and a required set reads back empty. See [Values DynamoDB Can't Store](/effect-dynamodb/guides/expressions/#values-dynamodb-cant-store).

### Composing Multiple Update Types

All update combinators compose as arguments — they are merged into one `UpdateItem` call:

```typescript region="composed-updates" example="guide-advanced.ts"
  // #region composed-updates
  yield* db.entities.Products.update({ productId: "p-1" })
    .set({ name: "Premium Mouse", price: 39.99 })
    .add({ viewCount: 10 })
    .subtract({ stock: 5 })
    .append({ tags: ["premium"] })
    .remove(["description"])
    .expectedVersion(6)
```

## Working in Bulk

The `Batch` module provides batch operations that automatically handle DynamoDB limits (chunking) and retry unprocessed items:

```typescript region="batch-ops" example="guide-advanced.ts"
// Batch write (auto-chunks at 25 items)
yield* Batch.write([
  Users.put({ userId: "u-1", email: "a@b.com", displayName: "A" }),
  Users.put({ userId: "u-2", email: "b@c.com", displayName: "B" }),
  Users.put({ userId: "u-3", email: "c@d.com", displayName: "C" }),
])

// Batch get (auto-chunks at 100 items)
const [u1, u2, u3] = yield* Batch.get([
  Users.get({ userId: "u-1" }),
  Users.get({ userId: "u-2" }),
  Users.get({ userId: "u-3" }),
])

// Batch delete
yield* Batch.write([Users.delete({ userId: "u-2" }), Users.delete({ userId: "u-3" })])
```

Note: Batch operations do **not** enforce unique constraints (no transactional guarantees). Use individual `put`/`delete` for entities with unique constraints.

## Conditional Writes

Entity-level `condition()` adds a `ConditionExpression` to any mutation (put, update, delete). The condition is evaluated server-side — if it fails, the operation is rejected with `ConditionalCheckFailed`.

Conditional put — only if item doesn't already exist:

```typescript region="conditional-put" example="guide-advanced.ts"
  // #region conditional-put
  // Conditional put — only if item doesn't already exist
  const condPutResult = yield* db.entities.Users.put({
    userId: "u-10",
    email: "new@example.com",
    displayName: "New User",
  })
    .condition((t, { notExists }) => notExists(t.email))
    .asEffect()
    .pipe(
      Effect.match({
        onFailure: (e) => `${e._tag} — already exists`,
        onSuccess: (u) => `created ${u.displayName}`,
      }),
    )
```

Conditional delete — only if a specific attribute value matches:

```typescript region="conditional-delete" example="guide-advanced.ts"
  // #region conditional-delete
  // Conditional delete — only if stock is zero
  const condDeleteResult = yield* db.entities.Products.delete({ productId: "p-1" })
    .condition((t, { eq }) => eq(t.stock, 0))
    .asEffect()
    .pipe(
      Effect.match({
        onFailure: (e) => `${e._tag} — stock not zero, delete prevented`,
        onSuccess: () => "deleted (stock was 0)",
      }),
    )
```

Conditional update — only if status matches:

```typescript region="conditional-update" example="guide-advanced.ts"
  // #region conditional-update
  // Conditional update — only if status is "active"
  yield* db.entities.Tasks.update({ taskId: "t-1" })
    .set({ status: "done" })
    .condition((t, { eq }) => eq(t.status, "active"))
```

### Composing with Optimistic Locking

When using `condition()` on an update that also has `Entity.expectedVersion()`, the user condition is ANDed with the version check:

```typescript region="optimistic-condition" example="guide-advanced.ts"
  // #region optimistic-condition
  yield* db.entities.Products.update({ productId: "p-1" })
    .set({ price: 24.99 })
    .expectedVersion(7)
    .condition((t, { gt }) => gt(t.stock, 0))
  // ConditionExpression: (#version = :v_lock) AND (#stock > :v0)
```

### Handling ConditionalCheckFailed

`ConditionalCheckFailed` is on the typed error channel wherever it is reachable: on `create()`, `patch()` and `deleteIfExists()` (which carry a built-in condition), on `upsert()`, and on any operation once `.condition(...)` is applied. Either way, `Effect.catchTag` handles it without widening by hand:

```typescript region="handle-conditional" example="guide-advanced.ts"
  // #region handle-conditional
  const result = yield* db.entities.Users.create({
    userId: "u-10",
    email: "new@example.com",
    displayName: "New User",
  })
    .asEffect()
    .pipe(Effect.catchTag("ConditionalCheckFailed", () => Effect.succeed("already exists")))
```

## Creating Items Safely

`Entity.create()` is a convenience for "put if not exists" — it's `Entity.put()` with an automatic `attribute_not_exists` condition on the primary key:

```typescript region="create-safely" example="guide-advanced.ts"
  // #region create-safely
  // Create — fails with ConditionalCheckFailed if item already exists
  const user = yield* db.entities.Users.create({
    userId: "u-20",
    email: "alice@example.com",
    displayName: "Alice",
  })

  // Duplicate — caught gracefully
  const dup = yield* db.entities.Users.create({
    userId: "u-20",
    email: "alice@example.com",
    displayName: "Alice",
  })
    .asEffect()
    .pipe(
      Effect.map(() => "created"),
      Effect.catchTag("ConditionalCheckFailed", () => Effect.succeed("already exists")),
    )
```

## Working with Multiple Tables

While single-table design is the default pattern, effect-dynamodb supports entities on different tables.

### Declaring Multiple Tables

```typescript
const UserTable = Table.make({ schema: AppSchema, entities: { Users } })
const AuditTable = Table.make({ schema: AppSchema, entities: { AuditEntries } })

// Provide physical table names at runtime
program.pipe(
  Effect.provide(
    Layer.mergeAll(
      DynamoClient.layer({ region: "us-east-1" }),
      UserTable.layer({ name: "Users" }),
      AuditTable.layer({ name: "AuditLog" }),
    )
  ),
)
```

### When to Use Multiple Tables

| Single Table | Multiple Tables |
|-------------|-----------------|
| Related entities queried together | Independent entity groups |
| Need cross-entity queries (collections) | No cross-entity query need |
| Fewer provisioned tables to manage | Different capacity settings per table |
| Index overloading (one GSI serves many patterns) | Simpler, entity-specific indexes |

### Considerations

- **Collections require the same table.** All entities in a collection must share a table.
- **Transactions can span tables.** DynamoDB transactions work across tables.
- **Each table is a separate DynamoDB resource.** Separate provisioning, backups, and billing.

## Building Expressions

### Entity-Level Expressions

Type-safe conditions, filters, and projections using `PathBuilder`:

```typescript region="entity-expressions" example="guide-advanced.ts"
// Condition — type-safe, nested paths, OR/NOT composition
Products.condition((t, { eq, gt, and }) => and(eq(t.category, "peripherals"), gt(t.stock, 0)))

// Filter — shorthand applied to collection queries
const filtered = yield* db.entities.Products.byCategory({ category: "peripherals" })
  .filter({ name: "Widget Pro" })
  .collect()

// Projection — select specific attributes
const projected = yield* db.entities.Products.scan()
  .select((t) => [t.name, t.price])
  .collect()
```

### Low-Level Builders

The `Expression` module provides raw builders for advanced use cases:

```typescript region="expression-builders" example="guide-advanced.ts"
// Condition expression (for conditional writes)
const cond = Expression.condition({
  eq: { status: "active" },
  gt: { stock: 0 },
})

// Filter expression (for query post-filtering)
const filter = Expression.filter({
  between: { price: [10, 50] },
  attributeExists: "category",
})

// Update expression
const upd = Expression.update({
  set: { displayName: "New Name", updatedAt: new Date().toISOString() },
  remove: ["temporaryFlag"],
  add: { loginCount: 1 },
})
```

See the [Expressions Guide](/effect-dynamodb/guides/expressions/) for the complete reference with DynamoDB mapping tables, all operators, and PathBuilder documentation.

## Timeouts and Cancelling Requests

The AWS SDK sets no request timeout by default, so a connection that stays open and never answers keeps the call waiting, for good. Two things end that wait: a timeout on the HTTP handler, and interrupting the fiber.

### Setting Timeouts

`DynamoClient.layer` and `DynamoStreamsClient.layer` pass `requestHandler` and `maxAttempts` to the SDK client. The library sets no default for either, so what you leave out stays the SDK's.

```typescript region="request-timeouts" example="guide-advanced.ts"
const WithTimeouts = DynamoClient.layer({
  region: "us-east-1",
  endpoint,
  credentials,
  requestHandler: {
    connectionTimeout: 1_000, // to open the connection
    socketTimeout: 5_000, // with no bytes moving on it
  },
  maxAttempts: 2, // the first included
})
```

A plain object is handed to the SDK, whose build for your runtime makes its own HTTP handler from it. The library imports no handler, so the options you can use depend on where you run:

| Option | Node and Bun (`NodeHttpHandler`) | Browsers and Workers (`FetchHttpHandler`) |
|---|---|---|
| `connectionTimeout` | Time to open the connection | Not available |
| `socketTimeout` | Time with no bytes moving on the socket | Not available |
| `requestTimeout` | **Only logs a warning**, unless `throwOnRequestTimeout` is set | Fails the attempt. The `fetch` itself runs on until the fiber is interrupted |
| `throwOnRequestTimeout` | Makes `requestTimeout` fail the attempt | Not available |

Or pass a handler you built, for agents or a logger. A handler you pass is destroyed with the layer.

A timeout is an attempt like any other, and the SDK retries it: with its default of 3 attempts, `socketTimeout: 100` fails after about 400 ms. The call then fails with a `DynamoError` whose `cause` is the SDK's error, named `TimeoutError`. On Node the SDK gives that name to a dropped connection too, so `cause.code` tells them apart: `ECONNRESET` or `EPIPE` for a connection that dropped, and for a timeout `ETIMEDOUT` or nothing at all.

`layerConfig` reads `maxAttempts` and the handler's timeouts through `Config`, because they are what an operator tunes per environment. One the provider doesn't hold stays unset, and one that doesn't parse fails the layer with its `ConfigError`. A handler instance holds code, so it is passed as itself.

```typescript region="request-timeouts-config" example="guide-advanced.ts"
const FromConfig = DynamoClient.layerConfig({
  region: Config.String("AWS_REGION").pipe(Config.withDefault("us-east-1")),
  endpoint: Config.succeed(endpoint),
  credentials: Config.succeed(credentials),
  requestHandler: {
    connectionTimeout: Config.Int("DYNAMODB_CONNECTION_TIMEOUT_MS"),
    socketTimeout: Config.Int("DYNAMODB_SOCKET_TIMEOUT_MS"),
  },
  maxAttempts: Config.Int("DYNAMODB_MAX_ATTEMPTS"),
})
```

### Cancelling a Request

Every operation passes Effect's abort signal to the SDK, so interrupting the fiber ends the request. That covers `Effect.timeout`, a sibling failing in `Effect.all`, and a `Stream` whose scope closes. The connection closes, the SDK makes no further attempt, and the fiber does not wait for an answer. The connection can't be reused afterwards, so the next request opens a new one.

```typescript region="cancel-request" example="guide-advanced.ts"
// Past 5 seconds this interrupts the call, which aborts its request.
const answered = yield* db.entities.Products.get({ productId: "p-1" }).pipe(
  Effect.timeoutOption("5 seconds"),
)
```

An interrupted request counts once in [consumed capacity](/effect-dynamodb/guides/consumed-capacity/), under `unreportedRequests`, since no capacity came back for it.

### Aborting Ends the Wait, Not the Request

A write already sent may still be applied. The caller sees the same interrupt or timeout either way, and the library can't tell which it was, so a caller who needs to know has to settle it. Write so that doing it twice is safe, and do it again:

```typescript region="settle-write" example="guide-advanced.ts"
const order = {
  productId: "p-order-1",
  name: "Ordered",
  price: 10,
  stock: 1,
  viewCount: 0,
  tags: [],
  category: "orders",
  categories: new Set(["orders"]),
}
const create = db.entities.Products.create(order).asEffect()

const first = yield* create.pipe(Effect.timeoutOption("5 seconds"))
if (Option.isNone(first)) {
  // The wait ended, not the request: the write may have been applied or may still be.
  // Writing again settles it, because only one create can succeed.
  yield* create.pipe(
    Effect.catchTag("ConditionalCheckFailed", () =>
      Effect.logInfo("The first attempt had been applied"),
    ),
  )
}
```

What settles it depends on the write:

- **`create`, or any `.condition()`:** the retry fails with `ConditionalCheckFailed` if the first was applied.
- **`.expectedVersion(n)`:** the retry fails with `OptimisticLockError` if the first moved the version on.
- **`Transaction.transactWrite`:** a conditioned item makes the retry fail with `TransactionCancelled`.
- **`EventStream.append`:** the retry at the same `expectedVersion` fails with `VersionConflict`.
- **`commandHandler` with `idempotency`:** the retry with the same `commandId` fails with `DuplicateCommand`.

A plain `put` or an unconditional `update` has nothing to settle it with. Applying it again is safe when it writes the same values, and an `.add()` is applied twice.

### When the Layer Closes

A request in flight when the layer's scope closes has its connection closed by the client's `destroy()`. The SDK would take that for a dropped connection and send the request again on a new one, so the layer stops it: the request fails with a `DynamoError` whose `cause` is named `ClientClosedError`, and a write it carried may still have been applied. A fiber interrupted before the scope closes has aborted its request already. A request sent after the scope closed still goes out, since the SDK client stays usable.
