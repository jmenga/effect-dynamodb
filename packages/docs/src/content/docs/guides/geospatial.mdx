The `@effect-dynamodb/geo` package enables proximity-based ("nearby") queries on DynamoDB using [H3 hexagonal grid cells](https://h3geo.org/). It transforms latitude/longitude coordinates into hierarchical H3 cells, stores them as GSI fields, and provides efficient radius-based search.

**Use cases:** real-time location tracking, venue/store discovery, fleet management, delivery radius checks.

## Installation

```bash
pnpm add @effect-dynamodb/geo
```

**Dependencies:** `effect-dynamodb`, `effect`, and `h3-js` (installed automatically).

## How It Works

1. **Write time** — Coordinates are converted to H3 cells at two resolutions: a fine cell (sort key) and a coarse parent cell (partition key). A time partition bucket is also computed for temporal scoping.
2. **Query time** — The search center and radius determine which H3 cells to query. Contiguous cells are grouped into `BETWEEN` range queries on the sort key. All queries execute in parallel.
3. **Post-filter** — Results are filtered by great-circle distance and sorted by proximity.

## Setup

### 1. Define a Model with Coordinate Fields

The model needs latitude, longitude, and fields for the computed geo values. The geo fields (`cell`, `parentCell`, `timePartition`) are optional because they're computed automatically on write.

```typescript title="models.ts" region="model" example="guide-geospatial.ts"
class Vehicle extends Schema.Class<Vehicle>("Vehicle")({
  vehicleId: Schema.String,
  latitude: Schema.optional(Schema.Number),
  longitude: Schema.optional(Schema.Number),
  timestamp: Schema.Number,
  cell: Schema.optional(Schema.String),
  parentCell: Schema.optional(Schema.String),
  timePartition: Schema.optional(Schema.String),
}) {}
```

### 2. Create Entity with Geo GSI

The geo index uses a GSI where the partition key is composed from `parentCell` + `timePartition` and the sort key from `cell`.

```typescript title="entities.ts" region="entity" example="guide-geospatial.ts"
const AppSchema = DynamoSchema.make({ name: "fleet", version: 1 })

const Vehicles = Entity.make({
  model: Vehicle,
  entityType: "Vehicle",
  primaryKey: {
    pk: { field: "pk", composite: ["vehicleId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    vehiclesByCell: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["parentCell", "timePartition"] },
      sk: { field: "gsi1sk", composite: ["cell"] },
    },
  },
  timestamps: true,
})

const MainTable = Table.make({ schema: AppSchema, entities: { Vehicles } })
```

### 3. Create GeoIndex

Bind geo configuration to the entity:

```typescript region="geo-index" example="guide-geospatial.ts"
const VehicleGeo = GeoIndex.make({
  entity: Vehicles,
  index: "vehiclesByCell",
  coordinates: (item) =>
    item.latitude !== undefined && item.longitude !== undefined
      ? { latitude: item.latitude, longitude: item.longitude }
      : undefined,
  fields: {
    cell: { field: "cell", resolution: 15 },
    parentCell: { field: "parentCell", resolution: 3 },
    timePartition: {
      field: "timePartition",
      source: "timestamp",
      bucket: "hourly",
    },
  },
})
```

**Configuration:**

| Field | Description |
|-------|-------------|
| `entity` | The effect-dynamodb Entity to bind to |
| `index` | Name of the entity GSI to use for geo queries |
| `coordinates` | Extractor function — returns `{ latitude, longitude }` or `undefined` for items without location |
| `fields.cell` | Fine-grained H3 cell (sort key). Resolution 15 is ~1m precision |
| `fields.parentCell` | Coarse H3 cell (partition key). Resolution 3 is ~12km hexagons |
| `fields.timePartition` | Time bucketing for temporal scoping. `source` names the timestamp field (epoch ms); `bucket` is the partition width, `"hourly"` or any `Duration` (see [Time buckets](#time-buckets)) |

## Usage

### Writing with Geo Enrichment

After binding with `GeoIndex.bind()`, use `vehicleGeo.put()` instead of the entity's `put()`. It computes and sets the geo fields, then writes through the entity's own `put`, so it fails with that put's errors and returns the written item:

```typescript region="put" example="guide-geospatial.ts"
const vehicleGeo = yield* GeoIndex.bind(VehicleGeo)

yield* vehicleGeo.put({
  vehicleId: "v-1",
  latitude: 37.7749,
  longitude: -122.4194,
  timestamp: now,
})
// cell, parentCell, and timePartition are computed automatically
```

Items without coordinates (where the `coordinates` extractor returns `undefined`) skip geo field enrichment and don't appear in the geo GSI (sparse index pattern).

### Nearby Search

Find items within a radius of a center point:

```typescript region="nearby" example="guide-geospatial.ts"
const results = yield* vehicleGeo.nearby({
  center: { latitude: 37.7749, longitude: -122.4194 },
  radius: 2000,
  unit: "m",
  timeWindow: {
    start: now - H3.HOURLY_BUCKET_MS,
    end: now + 1000,
  },
  sort: "ASC",
})

for (const { item, distance } of results) {
  console.log(`${item.vehicleId}: ${distance.toFixed(0)}m away`)
}
```

**Options:**

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `center` | `{ latitude, longitude }` | required | Search center |
| `radius` | `number` | required | Search radius |
| `unit` | `"m"` \| `"km"` | `"m"` | Radius unit |
| `timeWindow` | `{ start, end }` | past 15 minutes | Inclusive time range (epoch ms), compared against the `timePartition.source` field |
| `sort` | `"ASC"` \| `"DESC"` | `"ASC"` | Sort by distance |
| `pkFilter` | `Record<string, unknown>` | — | Values for any GSI partition-key composites besides `parentCell` and `timePartition` (a tenant, for example) |

**Returns:** `Array<{ item, distance: number }>`, sorted by distance and filtered to the exact radius using great-circle distance. Each `item` is decoded as the entity's own queries decode a row (a model class instance for a `Schema.Class` model), typed as the GeoIndex's item type: the entity's put input, with binary fields as bytes (see [Offloaded fields](#offloaded-fields)).

`timeWindow` filters items, not just partitions. The search queries every time partition the window touches, then keeps only the items whose `timePartition.source` timestamp lies within `[start, end]`, so a 30-second window on an hourly index returns only items from those 30 seconds, never the rest of the hour. The filtered-out items are still read from those partitions and consume read capacity, so cost scales with the number of partitions the window touches, not with how long the window is.

### Time buckets

`bucket` sets the width of a time partition: `"hourly"` or any `Duration` input, such as `"1 day"`, `"6 hours"`, `Duration.days(1)`, `{ hours: 6 }` or a number of milliseconds. It must be a positive whole number of milliseconds; anything else makes `GeoIndex.make` throw `[EDD-9185]`. A row's partition is `floor(timestamp / width)`, counted from the Unix epoch, so a daily bucket is a UTC day.

Match the width to the windows you search:

- **Too narrow.** A search runs one query per partition per contiguous cell range, all in parallel, with no cap. A 24-hour window on an hourly index is 24 or 25 partitions; on a daily index it is at most two, and on a one-minute index 1,440 or 1,441. To see what a search sends, turn on [consumed-capacity reporting](/effect-dynamodb/guides/consumed-capacity/): its `GeoIndex.nearby` report counts the queries in `requests`. Items written once and searched for hours afterwards suit a wide bucket. Whatever the width, a window finds only items whose timestamp it contains, so such searches need long windows; a wide bucket makes a long window cheap.
- **Too wide.** Each partition the window touches is read whole, and items outside the window are dropped after they are read, so they still consume read capacity. A 15-minute window (the default) on a daily index reads a whole day of items for each cell range, or two days when the window crosses midnight UTC. Items written often and searched over minutes suit a narrow bucket.

When you need both, give one entity two geo indexes, each writing its own partition attribute. Attributes they share (`cell`, `parentCell`, the timestamp `source`) must be computed the same way. `GeoIndex.make` throws `[EDD-9186]` if two geo indexes of one entity would write one attribute differently (a cell at another resolution, or a partition of another width or from another source), or if one writes the attribute another reads its timestamp from. A row holds one value per attribute, so one index would overwrite what the other needs:

```typescript region="time-buckets" example="guide-geospatial.ts"
class Sighting extends Schema.Class<Sighting>("Sighting")({
  sightingId: Schema.String,
  latitude: Schema.Number,
  longitude: Schema.Number,
  seenAt: Schema.Number,
  cell: Schema.optional(Schema.String),
  parentCell: Schema.optional(Schema.String),
  hourPartition: Schema.optional(Schema.String),
  dayPartition: Schema.optional(Schema.String),
}) {}

const Sightings = Entity.make({
  model: Sighting,
  entityType: "Sighting",
  primaryKey: {
    pk: { field: "pk", composite: ["sightingId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    sightingsByHour: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["parentCell", "hourPartition"] },
      sk: { field: "gsi1sk", composite: ["cell"] },
    },
    sightingsByDay: {
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["parentCell", "dayPartition"] },
      sk: { field: "gsi2sk", composite: ["cell"] },
    },
  },
})

// Each index writes its own partition attribute; both share the cell fields,
// at the same resolutions.
const SightingsByHour = GeoIndex.make({
  entity: Sightings,
  index: "sightingsByHour",
  coordinates: (item) => ({ latitude: item.latitude, longitude: item.longitude }),
  fields: {
    cell: { field: "cell", resolution: 15 },
    parentCell: { field: "parentCell", resolution: 3 },
    timePartition: { field: "hourPartition", source: "seenAt", bucket: "hourly" },
  },
})

const SightingsByDay = GeoIndex.make({
  entity: Sightings,
  index: "sightingsByDay",
  coordinates: (item) => ({ latitude: item.latitude, longitude: item.longitude }),
  fields: {
    cell: { field: "cell", resolution: 15 },
    parentCell: { field: "parentCell", resolution: 3 },
    timePartition: { field: "dayPartition", source: "seenAt", bucket: "1 day" },
  },
})

const SightingsTable = Table.make({ schema: AppSchema, entities: { Sightings } })
```

`put` enriches only its own index's fields, so a write through both enriches with the other first:

```typescript region="time-buckets-usage" example="guide-geospatial.ts"
const byHour = yield* GeoIndex.bind(SightingsByHour)
const byDay = yield* GeoIndex.bind(SightingsByDay)

// One write fills both indexes: each enrich adds its own partition
yield* byHour.put(
  byDay.enrich({
    sightingId: "s-1",
    latitude: 37.7749,
    longitude: -122.4194,
    seenAt: now - Duration.toMillis(Duration.hours(20)),
  }),
)

// A 24-hour window reads at most two daily partitions per cell range
const today = yield* byDay.nearby({
  center: { latitude: 37.7749, longitude: -122.4194 },
  radius: 1000,
  timeWindow: { start: now - Duration.toMillis(Duration.days(1)), end: now },
})
```

**Changing the width of an index that holds data.** The partition value doesn't record the width, so after a change, searches read partition values the existing rows don't have, and those rows can't be found until each item is written again. To change the width without a gap, add a second index with the new width on its own partition attribute, write through both until every item searched for has been written again, then search the new index and drop the old one.

### Enriching for Transactions

When using transactions or batch writes, use `enrich()` to compute geo fields without writing:

```typescript region="enrich" example="guide-geospatial.ts"
const enriched = VehicleGeo.enrich({
  vehicleId: "v-6",
  latitude: 37.78,
  longitude: -122.41,
  timestamp: now,
})
// enriched now has cell, parentCell, timePartition set
// Use in Transaction.write() or Batch.write()
```

### Offloaded fields

A geo entity can [offload fields to a blob store](/effect-dynamodb/guides/blob-offload/) (`DynamoModel.Packed({ ..., external })` or `DynamoModel.External()`). `GeoIndex` adds no option:

```typescript region="offloaded-geo" example="guide-geospatial.ts"
class Landmark extends Schema.Class<Landmark>("Landmark")({
  landmarkId: Schema.String,
  latitude: Schema.Number,
  longitude: Schema.Number,
  timestamp: Schema.Number,
  photo: Schema.Uint8Array,
  cell: Schema.optional(Schema.String),
  parentCell: Schema.optional(Schema.String),
  timePartition: Schema.optional(Schema.String),
}) {}

const Landmarks = Entity.make({
  model: DynamoModel.configure(Landmark, {
    photo: { storedAs: DynamoModel.External({ contentType: "image/jpeg" }) },
  }),
  entityType: "Landmark",
  primaryKey: {
    pk: { field: "pk", composite: ["landmarkId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    landmarksByCell: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["parentCell", "timePartition"] },
      sk: { field: "gsi1sk", composite: ["cell"] },
    },
  },
})

const LandmarkGeo = GeoIndex.make({
  entity: Landmarks,
  index: "landmarksByCell",
  coordinates: (item) => ({ latitude: item.latitude, longitude: item.longitude }),
  fields: {
    cell: { field: "cell", resolution: 15 },
    parentCell: { field: "parentCell", resolution: 3 },
    timePartition: { field: "timePartition", source: "timestamp", bucket: "hourly" },
  },
})
```

```typescript region="offloaded-geo-usage" example="guide-geospatial.ts"
// GeoIndex.bind needs a BlobStore in context for an entity that offloads
const landmarkGeo = yield* GeoIndex.bind(LandmarkGeo)

// A binary field takes a Uint8Array: one type is put's input and nearby's result
yield* landmarkGeo.put({
  landmarkId: "l-1",
  latitude: 37.8199,
  longitude: -122.4783,
  timestamp: now,
  photo: jpeg,
})

// nearby reads offloaded fields eagerly, for every row its cell queries return
const found = yield* landmarkGeo.nearby({
  center: { latitude: 37.82, longitude: -122.478 },
  radius: 500,
  unit: "m",
})
const photo: Uint8Array | undefined = found[0]?.item.photo // never a handle
```

- **`GeoIndex.bind`** checks the entity and its context as `Entity.bind` does: an entity that offloads a field needs a table schema that sets `escapeKeys: true` (`[EDD-9146]`, see [key text](/effect-dynamodb/guides/blob-offload/#key-text-escapekeys-true)), a `BlobStore` (`[EDD-9115]`), and every codec its `Packed` fields name registered (`[EDD-9078]`). All three are defects at bind.
- **One item type.** A GeoIndex types `put`'s input and `nearby`'s results with one type, so a binary field is a `Uint8Array` on both sides: `put` takes no `Stream`, handle or `Offload.source` for it, and results never hold a lazy handle.
- **`nearby` reads eagerly, both kinds.** Each cell query's page is resolved together, and the search's parallel queries share one pool of the store's `readConcurrency`. Offloaded values are fetched for **every row a cell query returns**, including rows the time window and the radius then drop: keep large values out of entities whose searches return many rows outside the window.
- **Errors.** `put` and `nearby` add `BlobStoreError` for an entity that offloads, and only for one.

## How the Query Works

Given a nearby search with `center` and `radius`:

1. **Optimal resolution** — H3 resolution is chosen to balance precision and query count
2. **Grid disk** — Concentric rings of H3 cells are generated around the center
3. **Edge pruning** — Cells whose nearest edge exceeds the radius are removed
4. **Contiguous chunking** — Adjacent H3 cells (numerically sequential) are grouped into `BETWEEN` range queries on the sort key, reducing the number of DynamoDB queries
5. **Time partitions** — The time window is divided into the index's time buckets (`bucket`)
6. **Parallel execution** — All (partition × chunk) query combinations execute in parallel
7. **Time-window filter** — Items whose source timestamp falls outside `[start, end]` are dropped, since the first and last partitions extend past the window
8. **Great-circle filter** — Results are post-filtered using haversine distance to the exact radius

## H3 Resolution Guide

| Resolution | Avg Edge Length | Use Case |
|------------|----------------|----------|
| 0 | ~1,107 km | Continent-scale |
| 3 | ~59 km | City/region grouping (recommended for `parentCell`) |
| 7 | ~1.2 km | Neighborhood |
| 10 | ~70 m | Block-level |
| 15 | ~0.5 m | Precise positioning (recommended for `cell`) |

Lower `parentCell` resolution = fewer partitions but larger GSI items per partition. Higher `cell` resolution = more precise sort key ranges.
