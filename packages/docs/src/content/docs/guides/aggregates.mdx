This guide covers three related features for modeling rich domain relationships in DynamoDB:

1. **Entity References** — Denormalized copies of related entities, with automatic ID-based inputs and hydration on write
2. **Aggregates** — Graph-based composite domain objects assembled from multiple entity types sharing a partition key
3. **Cascade Updates** — Propagating source entity changes to all items that embed it via refs

## Entity References

### The Problem

DynamoDB doesn't have JOINs. When your domain model needs data from a related entity, you denormalize — store a copy of the related data alongside the item that references it. This creates two problems:

- **Write complexity** — Instead of accepting an ID, you must fetch the full entity by ID and embed its data
- **Read/write type mismatch** — Create/update inputs should accept IDs; read outputs should return full entity data

### DynamoModel.identifier

Mark the primary business identifier field on any entity that can be referenced:

```typescript region="identifier-model" example="guide-aggregates.ts"
class Team extends Schema.Class<Team>("Team")({
  id: Schema.String.pipe(DynamoModel.identifier),
  name: Schema.String,
  country: Schema.String,
  ranking: Schema.Number,
}) {}
```

Rules:
- Exactly one field per model may be annotated with `identifier`
- The field should be a string or branded string type
- Only entities with an `identifier` field can be referenced via `DynamoModel.ref`

### DynamoModel.ref

Mark a field as a denormalized reference to another entity:

```typescript region="ref-model" example="guide-aggregates.ts"
class SquadSelection extends Schema.Class<SquadSelection>("SquadSelection")({
  squadId: Schema.String,
  selectionNumber: Schema.Number,
  team: Team.pipe(DynamoModel.ref),
  player: Player.pipe(DynamoModel.ref),
  squadRole: Schema.Literals(["batter", "bowler", "all-rounder"]),
  isCaptain: Schema.Boolean,
}) {}
```

`DynamoModel.ref` is a schema annotation. It tells Entity how to handle the field across different type contexts.

### Entity Ref Integration

When creating an entity with ref fields, provide a `refs` config mapping field names to the entities they reference:

```typescript region="entity-with-refs" example="guide-aggregates.ts"
const SquadSelections = Entity.make({
  model: SquadSelection,
  entityType: "SquadSelection",
  primaryKey: {
    pk: { field: "pk", composite: ["squadId"] },
    sk: { field: "sk", composite: ["selectionNumber"] },
  },
  indexes: {
    byPlayer: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["playerId"] },
      sk: { field: "gsi1sk", composite: ["squadId", "selectionNumber"] },
    },
  },
  refs: {
    team: { entity: Teams },
    player: { entity: Players },
  },
})
```

### Type Transformation

Ref fields transform across Entity's derived types:

| Type | Ref field shape | Example |
|------|-----------------|---------|
| `Entity.Input<E>` | ID field (derived from identifier name + "Id" suffix) | `teamId: string`, `playerId: string` |
| `Entity.Record<E>` | Full domain object | `team: Team`, `player: Player` |
| `Entity.Update<E>` | Optional ID field | `teamId?: string`, `playerId?: string` |

```typescript region="ref-put-get" example="guide-aggregates.ts"
// Input accepts IDs — not full objects
yield* db.entities.SquadSelections.put({
  squadId: "aus#2024-25#BGT",
  selectionNumber: 1,
  teamId: "aus",
  playerId: "cummins-01",
  squadRole: "bowler",
  isCaptain: true,
})

// Record returns full domain objects
const selection = yield* db.entities.SquadSelections.get({
  squadId: "aus#2024-25#BGT",
  selectionNumber: 1,
})
```

### Ref Hydration

On `put` and `update`, Entity automatically:
1. Extracts the ID from each ref field in the input
2. Fetches the referenced entity by ID (parallel fetches for multiple refs)
3. Embeds the entity's core domain data (Schema.Type — no system fields) in the DynamoDB item
4. Returns `RefNotFound` if any referenced entity doesn't exist

```typescript region="ref-not-found" example="guide-aggregates.ts"
  // #region ref-not-found
  // RefNotFound when a ref doesn't resolve
  const refError = yield* db.entities.SquadSelections.put({
    squadId: "aus#2024-25#BGT",
    selectionNumber: 99,
    teamId: "aus",
    playerId: "nonexistent",
    squadRole: "batter",
    isCaptain: false,
  })
    .asEffect()
    .pipe(Effect.flip)

  if (refError._tag === "RefNotFound") {
    // refError.field     → "player"
    // refError.refId     → "nonexistent"
    // refError.refEntity → "Player"
  }
```

### DynamoDB Storage

In DynamoDB, a ref field is stored as an embedded map containing the referenced entity's domain fields:

```json
{
  "pk": { "S": "$cricket#v1#squad_selection#aus#2024-25#BGT" },
  "sk": { "S": "$cricket#v1#squad_selection#1" },
  "team": { "M": { "id": { "S": "aus" }, "name": { "S": "Australia" }, "country": { "S": "Australia" }, "ranking": { "N": "1" } } },
  "player": { "M": { "id": { "S": "cummins-01" }, "firstName": { "S": "Pat" }, "lastName": { "S": "Cummins" }, "role": { "S": "bowler" } } },
  "squadRole": { "S": "bowler" },
  "isCaptain": { "BOOL": true }
}
```

## Aggregates

### The Problem

Real-world DynamoDB applications model rich domain objects as multiple denormalized items sharing a partition key. A cricket match, for example, might store the match root, venue, two team sheets, coaches, and player selections as separate items in the same partition. Building and maintaining these structures requires:

- Manual collection queries with discrimination by entity type
- Complex assembly logic (reduce + merge items into domain shape)
- Deep destructuring for mutations
- Transactional writes for consistency

The `Aggregate` module automates all of this.

### Core Concepts

An **Aggregate** is a domain object composed of multiple DynamoDB entity types sharing a partition key. The structure is a directed acyclic graph (DAG):

- **Root node** — The aggregate identity
- **Edges** — Relationships with cardinality (`one` or `many`)
- **Edge attributes** — Data owned by the relationship, not the referenced entity (e.g., `isCaptain`, `battingPosition`)
- **Sub-aggregates** — Reusable child aggregates that form transaction boundaries

### Defining an Aggregate

#### Step 1: Domain Schemas

Define the composed domain shape using Schema.Class. Ref fields reference other entities; edge fields reference aggregate members.

```typescript region="aggregate-schemas" example="guide-aggregates.ts"
class PlayerSheet extends Schema.Class<PlayerSheet>("PlayerSheet")({
  player: Player.pipe(DynamoModel.ref),
  battingPosition: Schema.Number,
  isCaptain: Schema.Boolean,
}) {}

class TeamSheet extends Schema.Class<TeamSheet>("TeamSheet")({
  team: Team.pipe(DynamoModel.ref),
  coach: Coach.pipe(DynamoModel.ref),
  homeTeam: Schema.Boolean,
  players: Schema.Array(PlayerSheet),
}) {}

class Match extends Schema.Class<Match>("Match")({
  id: Schema.String,
  name: Schema.String,
  venue: Venue.pipe(DynamoModel.ref),
  team1: TeamSheet,
  team2: TeamSheet,
}) {}
```

#### Step 2: Sub-Aggregates

Define reusable graph shapes for repeated structures. A sub-aggregate specifies a root entity type and edges to member entity types.

```typescript region="sub-aggregate" example="guide-aggregates.ts"
const TeamSheetAggregate = Aggregate.make(TeamSheet, {
  root: { entityType: "MatchTeam" },
  edges: {
    team: Aggregate.ref(Teams),
    coach: Aggregate.one({ entityType: "MatchCoach", entity: Coaches }),
    players: Aggregate.many({ entityType: "MatchPlayer", entity: Players }),
  },
})
```

- `Aggregate.one(config)` — One member item per aggregate instance (decomposes to separate DynamoDB item)
- `Aggregate.many(config)` — Multiple member items per aggregate instance (one DynamoDB item per element)
- `Aggregate.ref(entity)` — Inline ref edge (stays in the parent item, no separate DynamoDB item; hydrates on create)

Edge keys (`coach`, `players`) correspond to fields on the schema, and the editor completes them from it. The `(name, config)` forms of `one` and `many`, and `many`'s `edgeAttributes`, are deprecated: neither the name nor `edgeAttributes` is read, and both are removed in the next major release.

##### Sort keys for `many` edges

Each element of a `many` edge becomes its own DynamoDB item, and by default its sort key is composed from the **referenced entity's identifier**. That is enough while an entity appears at most once in an aggregate. When the same entity legitimately appears twice — distinguished by a field on the edge element rather than by the ref — both elements compose the same sort key, and DynamoDB rejects the whole write.

Declare `sk.composite` to say what separates them:

```typescript region="many-edge-sk-models" example="guide-aggregates.ts"
// A panel seats two on-field umpires, plus a third umpire and a referee — and
// the same person routinely holds more than one appointment.
class MatchOfficial extends Schema.Class<MatchOfficial>("MatchOfficial")({
  umpire: Umpire.pipe(DynamoModel.ref),
  role: Schema.Literals(["onfield", "third", "referee"]),
}) {}

class OfficiatedMatch extends Schema.Class<OfficiatedMatch>("OfficiatedMatch")({
  matchId: Schema.String,
  name: Schema.String,
  officials: Schema.Array(MatchOfficial),
}) {}
```

```typescript region="many-edge-sk" example="guide-aggregates.ts"
const OfficiatedMatchAggregate = Aggregate.make(OfficiatedMatch, {
  table: MainTable,
  schema: CricketSchema,
  pk: { field: "pk", composite: ["matchId"] },
  collection: { name: "officiated" },
  root: { entityType: "OfficiatedMatchItem" },
  edges: {
    officials: Aggregate.many({
      entityType: "MatchOfficial",
      entity: Umpires,
      sk: { composite: ["role", "umpire.id"] },
    }),
  },
})
```

```typescript region="many-edge-sk-create" example="guide-aggregates.ts"
const officiated = yield* OfficiatedMatchAggregate.create({
  matchId: "bgt-2025-test-1",
  name: "AUS vs IND",
  officials: [
    // A role seating two umpires.
    { umpireId: "bowen-01", role: "onfield" },
    { umpireId: "kumar-01", role: "onfield" },
    // ...and an umpire holding two appointments.
    { umpireId: "bowen-01", role: "third" },
    { umpireId: "erasmus-01", role: "referee" },
  ],
})
```

Pick the composite that is unique across the whole edge, not just the case in front of you. Here neither half would do alone — `["role"]` collides on the two on-field umpires, and the ref-identifier default collides on the umpire holding two appointments. `["role", "umpire.id"]` separates both. `["role"]` alone is right only when every role seats exactly one official.

Each entry must resolve to a **scalar** — string, number, bigint, boolean or date. Naming the hydrated ref itself (`"umpire"`) rather than a scalar path (`"umpire.id"`) fails with `AggregateDecompositionError` rather than serialising the object into the key.

A declared `sk.composite` is **authoritative**: it replaces the ref-identifier default rather than extending it, so it decides both uniqueness and the order elements sort in. Note `umpire.id` is a **dotted path** — hydration replaces the input's `umpireId` with the hydrated `umpire` object, so the bare name no longer exists at the top level.

An alternative modelling, when the roles are fixed and few, is an edge per role — `onfield: Aggregate.many(...)` over `Schema.Array(Umpire)` alongside `third: Aggregate.one(...)`. Elements there are the referenced entity itself, so each row is keyed by that entity's `DynamoModel.identifier` and no declaration is needed. It costs the ability to add a role without changing the schema.

Two shapes need a declaration, because nothing about the element identifies it on its own:

- an edge with no `entity`, whose elements are plain structs
- an edge whose elements share a referenced entity

Without one, decomposition fails with `AggregateDecompositionError` naming the edge and the colliding sort key — rather than the DynamoDB `ValidationException` ("Transaction request cannot include multiple operations on one item") that the collision would otherwise produce.

#### Step 3: Top-Level Aggregate

Bind the full domain schema to a table, schema namespace, and partition key:

```typescript region="top-level-aggregate" example="guide-aggregates.ts"
const MatchAggregate = Aggregate.make(Match, {
  table: MainTable,
  schema: CricketSchema,
  pk: { field: "pk", composite: ["id"] },
  collection: { name: "match" },
  consistentRead: true,
  root: { entityType: "MatchItem" },
  edges: {
    venue: Aggregate.one({ entityType: "MatchVenue", entity: Venues }),
    team1: TeamSheetAggregate.with({ discriminator: { teamNumber: 1 } }),
    team2: TeamSheetAggregate.with({ discriminator: { teamNumber: 2 } }),
  },
})
```

**Config properties:**

| Property | Description |
|----------|-------------|
| `table` | The DynamoDB table |
| `schema` | DynamoSchema namespace for key prefixing |
| `pk` | Partition key definition (field + composite attributes from the schema) |
| `collection` | Collection naming for the read path. `name` is required; `index` + `sk` only when assembling through a secondary index (see below) |
| `consistentRead` | Use strongly consistent reads when assembling. Defaults to `false` |
| `root` | Entity type for the root item |
| `context` | Optional array of schema field names to propagate to all member items |
| `timestamps` | Optional auto-managed `created` / `updated` attributes on every row the aggregate writes (see below) |
| `edges` | Map of schema fields to edge descriptors, ref edges, or bound sub-aggregates |

#### System Timestamps

An aggregate composes its DynamoDB rows directly rather than routing them through
`Entity` write ops, so entity-level `timestamps` never reach them. Configure them on the
aggregate instead — it takes the same config, so field names and `DynamoModel` storage
annotations behave exactly as they do on `Entity.make`:

```typescript region="aggregate-timestamps" example="guide-aggregates.ts"
const AuditedMatchAggregate = Aggregate.make(Match, {
  table: MainTable,
  schema: CricketSchema,
  pk: { field: "pk", composite: ["id"] },
  collection: { name: "audited-match" },
  root: { entityType: "AuditedMatchItem" },
  edges: {
    venue: Aggregate.one({ entityType: "AuditedMatchVenue", entity: Venues }),
  },
  timestamps: {
    created: { field: "created", schema: DynamoModel.DateEpochMs },
    updated: { field: "updated", schema: DynamoModel.DateEpochMs },
  },
})
```

Every row the aggregate writes is stamped — the root item, `one` and `many` edges, and
every row inside a sub-aggregate's transaction group.

**`updated` is per row.** It records when *that row* last changed. `update` diffs the
decomposition and rewrites only the sub-aggregate groups whose content actually changed,
so rows a mutation leaves alone keep their stored value. That is what a downstream sync
guarding its writes with `attribute_exists(updated) and updated < :updated` wants: rows
that did not change do not need a new stamp.

**`created` survives rewrites.** Aggregate writes are `Put`, not `UpdateItem`, so a
rewritten row would otherwise lose its original create instant. The stored value is read
back off the partition the update already fetched and re-emitted unchanged.

Timestamp attributes are stripped on the read path, so they never appear on the assembled
domain object. If you want them *in* the domain model, declare the field under the same name,
on the root or on any row below it: a sub-aggregate root, a `one` edge or a `many` element.
That row then works like an entity:

- The input doesn't need the date, required or optional. The library stamps it, using the
  model's own encoding, and a value you supply wins.
- `create` and `update` return what they stored, and the value is decoded normally on read.
- On `update`, `createdAt` stays what's stored whatever the mutation did. A mutation that
  changes `updatedAt` gives it; otherwise a rewritten row gets a new stamp.
- A field of that name that isn't a date is yours, on that row, and the library leaves it
  alone. On the root it turns that stamp off for every row.
- A partition key or a `many` edge's sort key over a stamped `updatedAt` is refused at
  `Aggregate.make` (`EDD-9121`), in `@effect-dynamodb/schema` too: those keys name rows, and it
  moves on every write.
- A `many` edge held as a `Schema.Record`, with a custom `decompose` and `assemble`, is filled the
  same way: its rows are taken apart, filled and put back, and the input type makes the date
  optional there too. Its `sk.composite` names are checked against the record's value. With a
  `decompose` and no `assemble`, an array still fills and anything else must supply its dates, since
  nothing says how to put its rows back. A `many` edge can be held as a `Schema.ReadonlyMap` the same
  way, since it's the rows that are stored and not the map.
- A `one` edge with no entity of its own takes its value in the input under its field name, with
  the date optional. Only an edge with an `entity` takes an id (`venueId`).

#### Do You Need a Secondary Index?

Usually not. Assembly queries the whole partition with a bare `pk = :pk` condition and
discriminates items by entity type in memory — it issues no sort-key condition and depends
on no ordering. When the aggregate is keyed on the table's primary partition key, that
query runs against the base table, so no index is provisioned and no mirror sort-key
attribute is written on every item.

Supply `collection.index` and `collection.sk` together only when the aggregate's `pk.field`
is **not** the table's primary partition key — then a GSI is genuinely load-bearing, because
you are querying a partition key the base table does not have.

Prefer the base table where you can. An LSI's only capability a GSI cannot match is strongly
consistent reads, and it costs a 10 GB cap on the item collection plus a permanent commitment
at `CreateTable` — LSIs cannot be added or removed later. An aggregate is exactly the shape
that grows (root + N edges), so that cap is a poor trade for an index the read path never uses.

#### Consistent Reads

Aggregate writes are transactional, so root and edges land atomically. Reads are eventually
consistent by default, which means a read taken shortly after a write can observe a torn
collection — the root may be missing (raising `AggregateAssemblyError`), or an edge may be
missing while the root is visible, which for optional or empty-able edges assembles into an
aggregate that is quietly incomplete.

Set `consistentRead: true` to close that window. It doubles the RCU cost of every assembly
read, so it is opt-in. It requires an aggregate collection that can be read strongly
consistently — on the base table, or on an LSI (an aggregate's collection index whose
partition key is the table's is created as one). DynamoDB reads a GSI only eventually
consistently: with a GSI-shaped collection index, `make()` accepts it, and every assembly
read is rejected by DynamoDB. `get`, `update` and `list` then fail with a `ValidationError`
(`operation: "get.consistentRead"` and so on) naming the aggregate and the index; `delete`,
which declares no `ValidationError`, fails with DynamoDB's own `DynamoValidationError`, its
message explained the same way.

#### Sub-Aggregate Binding with Discriminators

When the same sub-aggregate shape appears multiple times (e.g., `team1` and `team2`), use `.with()` to bind discriminator values:

```typescript
team1: TeamSheetAggregate.with({ discriminator: { teamNumber: 1 } }),
team2: TeamSheetAggregate.with({ discriminator: { teamNumber: 2 } }),
```

Discriminator values are stored on each member item in DynamoDB and used during assembly to route items to the correct sub-aggregate instance.

##### Nested sub-aggregates

A sub-aggregate can itself bind another sub-aggregate, for example a `Club` sub-aggregate whose `squad` field is a bound `Squad` sub-aggregate, used twice on a `League` as `club1` and `club2`. `create`, `get`, `list`, `update` and `delete` all work at every depth.

The nested level inherits its parent's discriminator. Its rows carry both attributes, and their sort keys are prefixed with the parent's discriminator values, so each binding of the parent keeps its own copy of the inner sub-aggregate:

```text
SK = $app#v1#leagueclub#clubno#1                         → LeagueClub (club1)
SK = $app#v1#leaguesquad#clubno#1#squadno#1              → LeagueSquad (club1.squad)
SK = $app#v1#leaguesquadplayer#clubno#1#squadno#1#p-1    → LeagueSquadPlayer (club1.squad.players)
SK = $app#v1#leaguesquad#clubno#2#squadno#1              → LeagueSquad (club2.squad)
```

(Numeric discriminator values are zero-padded in real keys; they are shortened here.) Each nested sub-aggregate is its own transaction group, so `update` rewrites only the inner group that changed.

Give a nested binding its own discriminator attribute. Reusing one it inherits (`{ clubNo: 9 }` inside a parent bound with `{ clubNo: 1 }`) would overwrite the parent's value on the inner rows, so `Aggregate.make` throws `EDD-9056`, naming the sub-aggregate's path.

Sub-aggregates bound directly on the root keep exactly the keys they had before. Nested sub-aggregates did not work in 1.22.0 and earlier: they were written, but reading them failed (`Missing key at ["club"]["squad"]`). Rows those versions wrote below the first level used different keys and are not read, so recreate those aggregates.

### How Values Are Stored

Aggregate items store their values in their schema's **wire form**, the same form `Entity.put` writes, however deeply they are nested. A `Schema.DateTimeUtcFromString` is an ISO string (`S`) in each of these places:

- a root field (`startDate`)
- an element of a root array (`matchDays: Schema.Array(Schema.DateTimeUtcFromString)`)
- a field of a class inside an array (`sessions[].startTime`)
- a member of a `Schema.NullOr` or other union, including inside an array (`Schema.Array(Schema.NullOr(...))`) and a union of a class and a scalar (`Schema.Union([Slot, Schema.String])`)
- a `Schema.Record` value or a `Schema.Tuple` element
- a field of a ref hydrated into a `one` or `many` item (`player.dateOfBirth` on a `MatchPlayer` item), at the root or inside a sub-aggregate
- a field of a `one` or `many` edge declared without an `entity`

Other transforms follow the same rule. A `Schema.BigIntFromString` or `Schema.NumberFromString` is stored as a string, and self date schemas such as `Schema.DateTimeUtc` and `Schema.Date` default to an ISO string. In a union that mixes a date with another type (`Schema.Union([Schema.DateTimeUtcFromString, Schema.Number])`), each value is stored by the member it belongs to, so a `5` stays a number. A plain `Schema.BigInt` is stored as a number and reads back as a `bigint`. On read, each value is decoded back to its domain type, so the assembled aggregate holds real `DateTime` instances, and a zoned date keeps its named or offset zone.

Self dates in unions follow the entity rules in [Dates in unions](/effect-dynamodb/guides/modeling/#dates-in-unions). A date next to a string member claims only its canonical ISO string, so a string member holding exactly such an instant reads back as a `DateTime`. An epoch-stored date next to a numeric member is rejected by `Aggregate.make` with `EDD-9058`. On an aggregate, that includes a `Schema.NumberFromString` or `Schema.BigIntFromString` member. These are stored as strings, but `update` re-decodes the aggregate's domain values, where they are numbers, and a number there could belong to either member. Entities accept those two.

A ref in a `many` edge can be declared in any of these ways, and all of them round-trip through `create`, `get` and `update`:

- inside an element class, annotated: `player: Player.pipe(DynamoModel.ref)`
- inside an element class, as the plain class `player: Player`, matched by name to the edge's `entity`
- as the element itself: `players: Schema.Array(Player.pipe(DynamoModel.ref))`

Refs are matched by the field's schema, not its name. A nested field that happens to share a ref edge's name (a `coach: Schema.String` inside an array, next to a root `coach` edge) is stored and read as its own schema.

Composed keys (`pk`, `sk`, collection and list-index keys) are not affected by this encoding. They are built exactly as before, so existing rows stay addressable.

Container `.check()` refinements are enforced on `create` and `update`, as they are on entities (see [Container checks](/effect-dynamodb/guides/modeling/#container-checks)). An array, struct or checked-struct class holding a date or another substituted value that breaks its check fails with a `ValidationError`. Earlier versions silently dropped those checks. Reads don't enforce them, so a stored row that breaks one still assembles. Every `update` of that aggregate then fails until the same update makes the value valid, which repairs the row. On an entity, a `.set()` of other fields still succeeds on such a row.

:::caution[Custom `decompose` that renames fields]
A `many` edge with a custom `decompose` that **renames** element fields (`{ noteId, at }` → `{ nid, when }`) is the one exception. Encoders are matched to the element's own field names, so a renamed field is stored as its domain value, and a `DateTime` there is still written as a map. It reads back as a real `DateTime`. To store it in wire form, keep the element's field names in `decompose`, or encode the value yourself before returning it.
:::

#### What a custom `decompose` is handed

A `many` edge's custom `decompose` is handed a write's value as 1.39.0 handed it, so its rows store, key and read exactly as they did on 1.39.0. The value you gave is read stored form first, once. Where a transformation has one type on both sides, that decodes a value once more: on a field that multiplies by 10 on decode, `create(50)` hands `decompose` 500. Anything else is handed as it is, such as a `Schema.NumberFromString` or a field with no transformation. `update` hands it the state it read as it was read, and the new state as a write's value.

What `decompose` returns is stored as on 1.39.0. Its fields are encoded as every other edge's are, and a sort key composite is read from what it returns. So a `decompose` that encodes such a field itself (`f / 10`) keeps working:

| `decompose` returns | Stored | Sort key text | `get` | After an `update` |
|---|---|---|---|---|
| `f / 10`, the field encoded | 5 | 50 | 50 | the same row, unchanged |
| `f`, the field unchanged | 50 | 500 | 500 | 500 stored under 5000, reads 5000 |

One that hands such a field back unchanged has it decoded once more on every write, as on 1.39.0. Encode the field in `decompose`, as `f / 10` does. Because `update` hands it the state it read as it was read, each `update` rewrites the edge's rows, even one that changes nothing, as on 1.39.0.

That's how 1.x hands `decompose` a value. The next major hands it the edge's decoded value, and a `decompose` that encodes a field itself drops that step then.

On an edge held as a `Schema.Record` without an `entity`, a date field that `decompose` returns in its stored form, such as the ISO text of a `Schema.DateTimeUtcFromString` or the epoch milliseconds of a number decoded to a `Date`, is stored as it is and keyed by it, as on 1.39.0. There a value in neither form is refused with a `ValidationError` (`EDD-9127`), and nothing is written. On an array edge, or one with an `entity`, `decompose` returns a date field's domain value: a value in another form fails the write with a defect, as on 1.39.0.

On 1.39.0 a `many` edge held as a `Schema.Record` stored what `decompose` returned without encoding it. Its fields are now encoded as an array edge's are. A `Schema.NumberFromString` there is stored as its text where 1.39.0 stored the number, under the same key, and reads the same value. A field that multiplies by 10 on decode, returned as `f / 10`, now reads back the value you gave instead of ten times it, and a row 1.39.0 wrote reads as it did.

#### What a custom `assemble` is handed

A `many` edge's `assemble` is handed the rows read, unmarshalled, with packed fields unpacked, under their stored attribute names. Removed from each row: `__edd_e__`, the attributes named `pk` and `sk`, every attribute whose name begins with `gsi` or `lsi`, and the timestamps the library stamps that the edge's model doesn't declare. Everything else stays, including a collection sort-key mirror under another name, and discriminator and context attributes. Nothing is decoded: on a field that multiplies by 10 on decode, it's handed 5 where `get` returns 50. What it returns is decoded with the rest of the aggregate.

#### Which rows are the aggregate's: `ownsRows`

An aggregate's rows are the ones its value keys. `update` deletes the keys the old value decomposes to and the new value doesn't, and `rekey` moves the rows the value decomposes to. A custom `decompose`'s row moves as stored, with only its keys replaced: decomposing the value read back needn't give what the row holds (one renaming a transformed field would store it decoded once more). Neither touches any other row in the partition, as on 1.39.0, because another aggregate or an entity can write rows of the same entity type there, and nothing in a row says which one wrote it. (`delete` has its own rule.)

Some rows the value doesn't key are the aggregate's own stale rows. A `decompose` that encodes its keyed field (`f / 10`) leaves them, because the value read back keys its rows elsewhere. Removing an element leaves its row, and `get` still returns it. Changing the keyed value leaves the old row beside the new one. `rekey` leaves the edge's rows in the old partition. A row your `assemble` drops is another such row.

When nothing else writes rows of the aggregate's entity types into its partition, declare it with `ownsRows: true` on `Aggregate.make`. The aggregate then takes every row of its entity types in its partition for its own.

**`update`** sends the same transactions it sends without the option. After the last one commits, it deletes the rows it read of each edge that changed, where the new value doesn't write their keys.
- An edge changed when the update writes its transaction and the edge's items differ, compared as the update always compares them: entity types and stored attributes in order, not keys. So an update is a no-op when the stored attributes don't change, even if a key would: a codec that stores every number as 0 makes 50 → 60 a no-op.
- After an update that changes an edge, that edge's rows are exactly what it decomposes to for the new value, except a row another edge of the same entity type could hold, which is left. So a custom `decompose` that leaves out an element you keep loses that element's row. An edge the update doesn't change keeps its rows.
- These `Delete`s go in requests of their own, up to 100 at a time. Each is sent on condition that the row is gone or still of the type read. A row another write removed in between is fine, and one replaced by a row of another type is left.
- If a request is cancelled, the `Delete`s whose condition failed are dropped and the rest are sent once more. Your mutation isn't run again, and nothing is read again.
- If that fails too, the update fails as it does when a later sub-aggregate's transaction fails. Its transactions have committed, and the rows it didn't delete stay until the next update that changes their edge.
- An update whose new value decomposes to what the old one did writes nothing.

**`rekey`** moves exactly what it moves without the option, and sends the same requests. Where any other row of its types would go can't be told from what's stored: a codec can store a value its key doesn't show, and a custom `assemble` or `decompose` can hand a row's values to another element. So no such row is moved.
- When such a row's own partition key changes, `rekey` reports the aggregate as a `failed` conflict naming the row, and moves none of it, since moving the rest would strand that row. Otherwise it leaves the row and counts it under `skipped.unrecognizedKey`.
- To repair a failed aggregate, run an update that changes the row's edge: it deletes the row. A row another edge of the same entity type could hold isn't deleted, so that update doesn't repair it.

`DynamoClient.make` checks the declaration against every entity and aggregate it can see: those your aggregate's table declares, those you bind, and those of the tables you bind. If one of them can write a row of the aggregate's entity types into its partition, it refuses with `EDD-9130`, naming the member, the entity type and how it writes the row. Which table a row is on is decided for each row the member writes: a read model's outbox items count on the outbox's table, for every projection defined on the read model.

The check counts every attribute a member stores, the library's own included, as the row holds it after the last write. So a unique sentinel's back-pointer, a projection outbox's event type or index key, or another aggregate's collection sort-key copy (on every one of its rows) under the partition key's attribute can put a row in the partition, and an aggregate's timestamp stored under `__edd_e__` can give its rows any type. It reads no schema: a model attribute, another aggregate's context and discriminator attributes, and whatever a custom `decompose` returns, are any name holding any text. So a member whose rows can carry one of your aggregate's entity types is refused unless the library writes the partition key's attribute on those rows after them, with text that can't be your aggregate's partition key: an entity's own table keys, or another aggregate's own partition key. For example, an aggregate with a `Line` edge that assembles off an index under `gpk` and `gsk` is refused beside a plain aggregate storing `Line` rows under `pk` and `sk`, even though that aggregate's model has no `gpk` and decoding drops one passed to it. The check errs toward refusing: with cased keys, `line` collides with `Line`, and `Line#Profile` collides with `Line` under any casing.

Every row an entity writes counts, even when it declares an edge's keys. An entity puts each key value after its field's name (`id_p`) and an aggregate doesn't, so none of an entity's rows is one of the aggregate's own. The check is a safety net, not a proof. A writer this client doesn't bind, in this process or another, isn't seen, and its rows are taken for the aggregate's. Every process that writes the table must bind every member that writes it. The check runs in `DynamoClient.make` only: an aggregate whose operations run without it, given a `DynamoClient` and its table's layer directly, is never checked.

Aggregate updates have no concurrency control. So a concurrent update's row at a key the cleanup deletes can be deleted, as a `Delete` of a key the value decomposes to can be on 1.39.0.

Leave `ownsRows` off when the partition is shared. Without it, stale rows stay, and two aggregates that share a partition and an entity type can still delete each other's rows where their keys collide, as on 1.39.0.

#### What `create` and `update` take

A value you hand to `create` or `update` is a domain value, as it is on an entity: in the input, in `state`, `cursor` and `current`, and in what a mutation returns. It's stored in its wire form and reads back as you gave it. An `update` leaves a field it doesn't change, and one that changes nothing writes nothing. A value that can't be a domain value but is the wire form, such as `"5"` for a `Schema.NumberFromString`, is still taken. Anything else is refused with a `ValidationError`.

A transformation that changes a value on decode, such as `SchemaTransformation.toLowerCase()`, reads the same on both. `create` returns what a read gives, as an entity's `put` does, and an aggregate stores that, where an entity stores what it was given.

A value its field's schema can't encode is stored as it was given, and only if the aggregate reads back that way. A one-way transformation, whose encode fails, does read back, so its value is stored. A transformation over itself, such as `s.pipe(Schema.decodeTo(s, SchemaTransformation.passthrough()))` where `s` holds a transformation, can't encode or decode any value, and stored as given its value reads back as something else: a bigint as a number, a class as a map. `create` and `update` refuse that value with a `ValidationError` naming the field (`EDD-9127`), and write nothing.

:::caution[Rows written by 1.39.0 or earlier]
Up to 1.39.0, where a transformation has one type on both sides, an aggregate took a value as its stored form if the stored side accepted it. On a field that multiplies by 10 on decode:

| | Returned | Stored | `get` |
|---|---|---|---|
| `create(50)` now, and on an entity | 50 | 5 | 50 |
| `create(50)` on 1.39.0 | 500 | 50 | 500 |
| Then an `update` of another field on 1.39.0 | | 500 | 5000 |
| Then another | | 5000 | 50000 |

Every `update` did this again to every such field in every row of the aggregate, whatever the mutation changed. That includes context fields and the fields of a hydrated ref.

**This affected** a custom transformation with one type on both sides, whatever the value, and `Schema.StringFromBase64`, `Schema.StringFromBase64Url`, `Schema.StringFromHex`, `Schema.StringFromUriComponent` and `Schema.fromJsonString`, for a value that was already valid in that form: `create("aGVsbG8=")` on `Schema.StringFromBase64` returned and read back `"hello"`. An `update` left those as they were, unless the decoded text was valid in that form too. A plain word that happens to be valid base64 went the same way, and what it was given is gone: `create("test")` on `Schema.StringFromBase64` returned `"��-"` and stored `77+977+9LQ==`, where an entity stores `dGVzdA==` and reads `"test"`. It didn't affect a transformation that gives the same result twice, such as `Schema.Trim`, or one with different types on its two sides, such as `Schema.NumberFromString`.

**If you pass the stored form to `create`, change it. Nothing will warn you.** On 1.39.0 the stored form was the only input on these fields that read back as you meant. It's a valid domain value too, and no check can tell the two apart, so it's now taken as one, with no error, and you read back what you passed:

| Field | Code | 1.39.0: stored, `get` | 1.39.0, after an `update` of another field | Now: stored, `get`, the same after an `update` |
|---|---|---|---|---|
| Multiplies by 10 | `create(5)` | 5, 50 | 50, 500 | 0.5, 5 |
| `Schema.StringFromBase64` | `create("aGVsbG8=")` | `aGVsbG8=`, `"hello"` | `aGVsbG8=`, `"hello"` | `YUdWc2JHOD0=`, `"aGVsbG8="` |

Pass the value you want to read instead: `create(50)` and `create("hello")` store `5` and `aGVsbG8=`, what those two calls stored before. If you encode a value before passing it to `create`, or set an encoded value in an `update`, stop encoding it.

**Rows already stored stay as they are.** The library can't tell what such a row should have held, so it can't recover it and doesn't try. Those rows keep what they store and read as they did on 1.39.0, and a row that went through `update` has compounded, once for each update. An `update` no longer makes it worse. To repair a row you need to know the right value yourself: set it in an `update`, which stores its encoded form.
:::

#### Upgrading from 1.22.0 or earlier

:::caution[Upgrade readers first]
1.22.0 can't read every row this version writes. A **self** date schema (`Schema.DateTimeUtc`, `Schema.Date`, or one with `storedAs`) inside a `NullOr` or other union, a `Record` or a `Tuple` is now stored as a string or number. A 1.22.0 reader fails on it with `Expected DateTime.Utc`, or, in a union with a string member, reads it back as a plain string. **Upgrade every reader before any writer, and don't roll back past this version** once new rows are written.

1.22.0 does read the other shapes this version writes differently. These include dates in root arrays and arrays of classes, transform dates such as `Schema.DateTimeUtcFromString` in any container, plain-class refs in `many` elements, and optional `NumberFromString` fields. Nested sub-aggregates and refs annotated with `DynamoModel.ref` in a `many` element never read back on 1.22.0 anyway.
:::

Versions up to and including 1.22.0 encoded only top-level fields, and only when the field's own schema was a transform. A transformed value nested inside an array, a union, a class or a hydrated ref was marshalled as the domain object itself, so a `DateTime` was stored as a map such as `{ epochMilliseconds, "~effect/DateTime", _tag: "Utc" }`. On Effect 4.0.0, rows written under an Effect release candidate (whose maps carry `~effect/time/DateTime`) failed assembly with `Expected DateTime.Utc`. Rows written under 4.0.0 decoded as plain objects that only looked like `DateTime`s.

Existing rows need no migration step:

- **Reads** rebuild a stored `DateTime` map into a real `DateTime`, whichever type-id key it carries. `Zoned` values keep their named or offset zone. A plain `Schema.BigInt`, stored as a number, now reads back; earlier versions could not read it.
- **Writes** rewrite a row in wire form the next time an `update` changes its group (the root item, or the sub-aggregate it belongs to). An update that changes nothing writes nothing, and there is no automatic backfill, so rows that are never updated keep the map form and keep reading correctly.
- **Lost values.** Some domain objects have no enumerable state, so the map they were stored as holds no value: a `Schema.Date` was stored as an empty map, and a `URL`, `Duration` or `BigDecimal` lost its value the same way. These cannot be recovered, and reading them fails with a `ValidationError`.

**Some attributes change stored type.** A few values that 1.22.0 stored in their domain form are now encoded, which changes their DynamoDB type. Keys are not affected. The affected attributes are:

- a top-level field wrapped in `Schema.optional(...)` or `Schema.NullOr(...)` around a non-date transform such as `Schema.NumberFromString`, on the root item, an edge item or a `many` element's own fields
- a `Schema.NumberFromString` nested inside a hydrated ref

For example, an optional `NumberFromString` holding `5` was stored as `{ "N": "5" }` and is now `{ "S": "5" }`. Rows of both kinds read back correctly. However, a `list` filter on such an attribute can match old and new rows differently until the old rows are rewritten: a `filter` expression compares against one DynamoDB type, and a `filterBy` predicate receives the stored value, a number on old rows and a string on new ones. DynamoDB Streams consumers also see the attribute change type. The same applies to an optional `Schema.BigIntFromString`. Rows 1.22.0 stored as `{ "N": "5" }` could not be read back at all; they now read back as `5n`.

### Aggregate Operations

#### get — Read and Assemble

Fetch all items in the partition, then assemble them into the domain object:

```typescript region="aggregate-get" example="guide-aggregates.ts"
const fetched = yield* MatchAggregate.get({ id: "bgt-2025-test-1" })
```

Assembly works by:
1. Querying all items in the partition
2. Discriminating items by `__edd_e__` entity type + discriminator values
3. Traversing the graph leaves-to-root (topological sort)
4. Building the Schema.Class instance at each node

Returns `AggregateAssemblyError` if the collection query returns incomplete or unexpected items.

#### create — Decompose and Write

Create a new aggregate from input data. Ref fields accept IDs (not full objects):

```typescript region="aggregate-create" example="guide-aggregates.ts"
const match = yield* MatchAggregate.create({
  id: "bgt-2025-test-1",
  name: "AUS vs IND, 1st Test",
  venueId: "mcg",
  team1: {
    teamId: "aus",
    coachId: "mcdonald",
    homeTeam: true,
    players: [
      { playerId: "cummins-01", battingPosition: 8, isCaptain: true },
      { playerId: "smith-01", battingPosition: 4, isCaptain: false },
    ],
  },
  team2: {
    teamId: "ind",
    coachId: "gambhir",
    homeTeam: false,
    players: [{ playerId: "kohli-01", battingPosition: 4, isCaptain: true }],
  },
})
```

The create operation:
1. Validates the input against the schema
2. Hydrates all ref fields (fetches entities by ID, embeds domain data)
3. Decomposes the domain object into individual DynamoDB items following the graph structure, with every value in its wire form (see [How Values Are Stored](#how-values-are-stored))
4. Adds partition keys, sort keys, entity type discriminators, and context fields
5. Writes items in sub-aggregate transaction groups (each sub-aggregate = one `transactWriteItems`). The root item goes first, in the first transaction, conditioned on `attribute_not_exists`

Fields other than refs can be given in their domain form as well as their wire form, so the input may carry a `DateTime`, an `Option` or a `Redacted`, including the `Option` a `Schema.OptionFromOptional` makes. These are kept intact while ref IDs are replaced with hydrated data.

A ref ID is a value of the attribute the referenced entity is keyed by, of that attribute's type: a number for a number key, a `bigint` for a bigint key, a `Date` (or its ISO string) for a date key. Each is fetched by the key the entity's own `put` wrote. An ID of another type (`"5"` for a number key) or one no item can be keyed by (`Infinity`) fails with a `ValidationError` (`EDD-9131`), and so does an edge whose entity is keyed by more than one attribute (`EDD-9129`): no one ID names one of its items, so give that edge's value whole. Both are checked for every edge before anything is fetched or written.

In a `many` edge whose element is a union, each element is read as the first member that takes it, as the aggregate's input schema decodes it. Only a member whose field of the entity's name holds the entity takes an ID there. A member that declares that field a scalar keeps the value it's given, and so does any ID field it declares itself.

Returns `RefNotFound` if a ref ID doesn't resolve. Each sub-aggregate group is its own transaction, written in turn, so a multi-group write is not atomic. DynamoDB's limits are not checked before sending: a group over 100 items (DynamoDB's transaction limit) is rejected by DynamoDB and fails with `AggregateTransactionOverflow`; an item over 400 KB, a group over 4 MB, or a key over its size limit (2048 bytes for a partition key, 1024 for a sort key) fails with a `ValidationError` naming the item and its key. Nothing from the rejected group is written, DynamoDB's error is the `cause`, and the error says which groups were already committed (`AggregateTransactionOverflow.committed` and its `message`, or the `ValidationError`'s message). A `create` whose root group committed fails on the existing root if retried: `update` or `delete` the partial aggregate instead.

Returns `ConditionalCheckFailed` if the aggregate already exists. Its root item's guard cancels the first transaction, so nothing is written: not the root, not an edge, not a sub-aggregate row. Earlier versions overwrote the root and left behind any old rows the new aggregate didn't rewrite. To replace an aggregate, `update` it, or `delete` it first. Each sub-aggregate is still its own transaction, so if a later one fails, the ones before it stay written.

The guard is on the root item only. Edge and sub-aggregate rows left without a root, for example by an earlier write that failed partway, don't stop `create`. `get` then reads them back together with the new aggregate's rows, merging stale edges into it. Before creating an aggregate where an earlier write may have failed partway, `delete` its key: `delete` removes every row in the partition, orphans included. The library doesn't check for orphan rows on `create`, because that would add a partition read to every create.

#### update — Diff and Write

Fetch the current state, apply a mutation function, diff, and write only changed sub-aggregate groups:

```typescript region="aggregate-update-spread" example="guide-aggregates.ts"
const updated = yield* MatchAggregate.update({ id: "bgt-2025-test-1" }, (current) => ({
  ...current.state,
  team1: {
    ...current.state.team1,
    players: current.state.team1.players.map((ps) => ({
      ...ps,
      isCaptain: ps.player.lastName === "Smith",
    })),
  },
}))
```

The update operation:
1. Fetches the current aggregate via `get`
2. Applies the mutation function to produce the updated domain object
3. Decomposes both old and new into DynamoDB items
4. Diffs at sub-aggregate group boundaries
5. Writes only the groups that changed

**Context field propagation:** If the mutation changes a context field (a root-level field propagated to all members), all sub-aggregate groups are rewritten with the new context values.

#### UpdateContext

The mutation function receives a single `UpdateContext` object with tools for composable, type-safe immutable updates:

```typescript region="aggregate-update-cursor" example="guide-aggregates.ts"
const cursorUpdated = yield* MatchAggregate.update({ id: "bgt-2025-test-1" }, ({ cursor }) =>
  cursor
    .key("team1")
    .key("players")
    .modify((players) =>
      players.map((ps) => ({ ...ps, isCaptain: ps.player.lastName === "Smith" })),
    ),
)
```

The `UpdateContext` provides:

| Property | Type | Description |
|----------|------|-------------|
| `state` | `TIso` | The current aggregate as a plain object (for spreads) |
| `cursor` | `Cursor<TIso>` | Pre-bound optic for navigating and transforming — no need to pass `state` explicitly |
| `optic` | `Optic.Iso<TIso, TIso>` | Composable optic for external lenses — pass `state` explicitly |
| `current` | `TClass` | Schema.Class instance (rarely needed) |

**Cursor operations** (pre-bound to current state):

| Operation | Description |
|-----------|-------------|
| `cursor.key("field")` | Focus on a required field |
| `cursor.optionalKey("field")` | Focus on an optional field |
| `cursor.at(index)` | Focus on an array element |
| `cursor.get()` | Get the focused value |
| `cursor.replace(value)` | Replace the focused value, return updated root |
| `cursor.modify(fn)` | Apply a function to the focused value, return updated root |

Simple field update:
```typescript region="aggregate-update-simple" example="guide-aggregates.ts"
yield* MatchAggregate.update({ id: "bgt-2025-test-1" }, ({ cursor }) =>
  cursor.key("name").replace("AUS vs IND, Boxing Day Test"),
)
```

Using `optic` + `state` (for external lenses):
```typescript region="aggregate-update-optic" example="guide-aggregates.ts"
yield* MatchAggregate.update({ id: "bgt-2025-test-1" }, ({ state, optic }) =>
  optic.key("name").replace("AUS vs IND, 1st Test", state),
)
```

The mutation function can return either a class instance (from spreading `current`) or a plain object (from cursor/optic operations) — the schema decode handles both.

#### delete — Remove All Items

Remove all items in the aggregate's partition:

```typescript region="aggregate-delete" example="guide-aggregates.ts"
yield* MatchAggregate.delete({ id: "bgt-2025-test-1" })
```

Queries all items in the partition and batch-deletes them.

#### list — Page Through Aggregates

`list` needs a **list index**: a GSI the root item of every aggregate is written to. `list` reads root items from one partition of it, then assembles each one.

```typescript region="list-model" example="guide-aggregates.ts"
class TournamentMatch extends Schema.Class<TournamentMatch>("TournamentMatch")({
  matchId: Schema.String,
  tournament: Schema.String,
  name: Schema.String,
  status: Schema.Literals(["scheduled", "completed"]),
}) {}
```

```typescript region="list-aggregate" example="guide-aggregates.ts"
const TournamentMatchAggregate = Aggregate.make(TournamentMatch, {
  table: MainTable,
  schema: CricketSchema,
  pk: { field: "pk", composite: ["matchId"] },
  collection: { name: "tmatch" },
  list: {
    index: "gsi1",
    name: "tmatchlist",
    pk: { field: "gsi1pk", composite: ["tournament"] },
    sk: { field: "gsi1sk", composite: ["matchId"] },
  },
  root: { entityType: "TournamentMatchItem" },
  edges: {},
})
```

The first argument selects the partition (and, with contiguous SK composites, a prefix within it). The second carries the paging options:

| Option | Meaning |
|--------|---------|
| `limit` | At most _n_ **aggregates**. Accumulates across as many requests as it takes — not DynamoDB's `Limit`, which bounds rows examined |
| `pageSize` | DynamoDB's `Limit` — rows examined per request. A contract on round trips, not on what comes back |
| `filter` | `FilterExpression` on the root-item query. Same callback and shorthand forms as `BoundQuery.filter()`, and the same empty-part rules: an empty filter is none, and an empty part under `or()` / `not()` or an `or()` with no parts fails with a `ValidationError` before sending. An `isIn` with no values is sent; DynamoDB rejects its `IN ()`, and `list` fails with a `ValidationError` (`operation: "list.filter"`) naming it |
| `reverse` | Walk the list index descending |
| `cursor` | Resume after the last aggregate the previous call returned |

```typescript region="list-filtered" example="guide-aggregates.ts"
const completed = yield* TournamentMatchAggregate.list(
  { tournament: "bgt-2025" },
  { filter: { status: "completed" }, limit: 2 },
)
```

`filter` is worth reaching for beyond ergonomics. `list` assembles each surviving root item with **its own partition read**, so filtering the result afterwards pays a full assembly for every aggregate it then discards. Pushing the predicate into the query means those rows are never assembled.

Because a `FilterExpression` runs _after_ DynamoDB's `Limit`, a request can come back empty. `limit` still means "this many matching aggregates": the query keeps asking until the page fills or the key range ends. `cursor` is an `Option<string>`: `Some` while there is more, `None` only when genuinely exhausted. `list({ cursor })` takes the string inside.

```typescript region="list-cursor" example="guide-aggregates.ts"
const nextPage = yield* Option.match(completed.cursor, {
  onNone: () => Effect.succeed([]),
  onSome: (cursor) =>
    TournamentMatchAggregate.list(
      { tournament: "bgt-2025" },
      { cursor, filter: { status: "completed" }, limit: 2 },
    ).pipe(Effect.map((next) => next.data)),
})
```

A cursor is opaque and belongs to the list that returned it. A cursor `list` can't decode fails with a `ValidationError` (`EDD-9094`, `operation: "list"`) before anything is sent, and so does an empty string. `list` can't tell another list's well-formed cursor from its own: DynamoDB may reject it, failing with a `DynamoValidationError`, or the list resumes from wherever the cursor points.

```typescript region="list-reverse" example="guide-aggregates.ts"
const latest = yield* TournamentMatchAggregate.list(
  { tournament: "bgt-2025" },
  { filter: (t, { eq }) => eq(t.status, "completed"), limit: 1, reverse: true },
)
```

:::caution[Sharded lists cannot be resumed]
With `list.cardinality`, the list index is spread across _n_ partitions and `list` fans out across all of them. `limit` bounds the merged result, but there is no resumable position across shards — `cursor` is always `None`, and passing one fails with a `ValidationError` (`EDD-9051`) rather than being silently ignored.
:::

#### An optional composite with no value

A composite of an aggregate's keys can be optional. What happens without a value depends on the key:

| Key | No value |
|---|---|
| `list` partition or sort key, sharded or not | The row is stored without either list attribute, so it isn't in that list. `get` still finds the aggregate, a later write with the value adds it, and one without takes it out |
| `collection` sort key | `ValidationError` (`EDD-9123`), nothing written. A root outside the collection index couldn't be read back |
| `pk` | `ValidationError` (`EDD-9123`) on `create`, `get` and `update`; `AggregateAssemblyError` on `delete`. Nothing can find an aggregate without its partition key |

A `list` filter that leaves out a composite of the list's partition key is the same `ValidationError`.

### Error Handling

| Error | When | Properties |
|-------|------|------------|
| `AggregateAssemblyError` | Read path: no items for the key, a missing root item, or duplicate root / sub-aggregate items | `aggregate`, `reason`, `key` |
| `ValidationError` | Read path: the assembled items fail schema decode (`operation: "aggregate.assemble"`) | `entityType`, `operation`, `cause` |
| `AggregateDecompositionError` | Write path: schema validation or structural error during decomposition | `aggregate`, `member`, `reason` |
| `AggregateTransactionOverflow` | Write path: DynamoDB rejected a sub-aggregate group over its 100-item transaction limit | `aggregate`, `subgraph`, `itemCount`, `limit`, `committed` (sub-aggregates already written), `operation` (`"create"` / `"update"`), `cause`; `message` states all of it |
| `RefNotFound` | Ref hydration: referenced entity not found | `entity`, `field`, `refEntity`, `refId` |

```typescript region="aggregate-error-handling" example="guide-aggregates.ts"
const result = yield* MatchAggregate.get({ id: "nonexistent" }).pipe(
  Effect.catchTag("AggregateAssemblyError", (e) =>
    Effect.succeed(`Assembly failed for ${e.aggregate}: ${e.reason}`),
  ),
)
```

## Cascade Updates

### The Problem

When denormalized data changes at the source (e.g., a player's name is corrected), every item that embeds that entity via `DynamoModel.ref` must be found and updated. Without automation, this requires per-entity-type GSIs and manual batch update logic.

### Entity.cascade

Attach a cascade to an `EntityUpdate` operation. After the source entity update completes, the cascade finds and updates all target items:

```typescript region="cascade-basic" example="guide-aggregates.ts"
  // #region cascade-basic
  const updatedPlayer = yield* db.entities.Players.update({ id: "smith-01" })
    .set({ firstName: "Steven" })
    .cascade({ targets: [SquadSelections] })
```

After updating the player, the cascade:
1. Identifies all ref fields on `SquadSelections` that reference `Players`
2. Queries the target entity's GSI (whose PK composite includes the player's ID field) to find all items embedding this player
3. Updates each matching item with the new denormalized player data

### Configuration

```typescript
Entity.cascade({
  targets: ReadonlyArray<Entity>,  // Required: entities that embed this source via ref
  filter?: Record<string, unknown>, // Optional: additional filter on target items
  mode?: "eventual" | "transactional", // Optional: default "eventual"
})
```

### Cascade Modes

**Eventual (default):** Batch-updates target items. No item limit. Partial failures are possible.

```typescript region="cascade-eventual" example="guide-aggregates.ts"
  // #region cascade-eventual
  yield* db.entities.Players.update({ id: "smith-01" })
    .set({ firstName: "Steven" })
    .cascade({ targets: [SquadSelections], mode: "eventual" })
```

**Transactional:** Atomic update via `transactWriteItems`. All target items updated in a single transaction. Maximum 100 items: over that (or over another DynamoDB write limit) DynamoDB rejects the transaction, nothing is written, and the update fails with `CascadePartialFailure` (`succeeded: 0`), whose `errors` hold a `ValidationError` explaining the limit, with DynamoDB's error as its `cause`.

```typescript region="cascade-transactional" example="guide-aggregates.ts"
  // #region cascade-transactional
  yield* db.entities.Players.update({ id: "smith-01" })
    .set({ firstName: "Steven" })
    .cascade({ targets: [SquadSelections], mode: "transactional" })
```

### Cascade Prerequisites

For cascade to work, the target entity must:
1. Have at least one `DynamoModel.ref` field pointing to the source entity type
2. Have a GSI whose PK composite includes the ref's ID field (e.g., `byPlayer` with `composite: ["playerId"]`)
3. Be configured with `refs` mapping the ref field to the source entity

### Error Handling

In eventual mode, partial failures return `CascadePartialFailure`:

```typescript
yield* db.entities.Players.update(
  { id: "smith-01" },
  Entity.set({ firstName: "Steven" }),
  Entity.cascade({ targets: [SquadSelections] }),
).pipe(
  Effect.catchTag("CascadePartialFailure", (e) => {
    console.log(`${e.succeeded} updated, ${e.failed} failed`)
    // Retry or handle partial failure
  }),
)
```

| Property | Description |
|----------|-------------|
| `sourceEntity` | Entity type of the source (e.g., `"Player"`) |
| `sourceId` | ID of the source entity |
| `succeeded` | Number of successfully updated target items |
| `failed` | Number of failed updates |
| `errors` | Array of individual error details |

In transactional mode, a failure rolls back the entire cascade (but not the source update — the source entity is already updated). You get `TransactionCancelled` instead of `CascadePartialFailure`.

### Multiple Targets

Cascade to multiple entity types in a single operation:

```typescript
yield* db.entities.Players.update(
  { id: "smith-01" },
  Entity.set({ firstName: "Steven" }),
  Entity.cascade({ targets: [SquadSelections, MatchPlayers, ContractRecords] }),
)
```

Each target is queried independently. In eventual mode, each target's updates are batched separately.
