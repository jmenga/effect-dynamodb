This guide covers the Query API: how to construct queries, apply sort key conditions, filter results, paginate, and collect.

## BoundQuery — A Fluent Chain

Queries in effect-dynamodb are **fluent chains** with pre-resolved services. A collection query or entity scan returns a `BoundQuery` that you chain combinators onto, then terminate with `.collect()`, `.fetch()`, or `.paginate()`.

```typescript
import { DynamoClient } from "effect-dynamodb"

const db = yield* DynamoClient.make({
  entities: { TaskEntity },
  tables: { MainTable },
})

// Construct and execute a query in one chain
const results = yield* db.entities.TaskEntity
  .byProject({ projectId: "proj-alpha" })
  .filter({ status: "active" })
  .limit(25)
  .reverse()
  .collect()
```

## Entity Queries

Query accessors live on `db.entities` (for entity index queries, primary key lookups, and scans) and `db.collections` (for auto-discovered cross-entity queries). Entity index queries return typed arrays; collection queries return grouped results.

```typescript region="entity-queries" example="guide-queries.ts"
// Primary key lookup (not a query — returns single item)
const task = yield* tasks.get({ taskId: "t-001" })

// Named index queries — via entity index accessors
const projectTasks = yield* db.entities.TaskEntity.byProject({
  projectId: "proj-alpha",
}).collect()
const assigneeTasks = yield* db.entities.TaskEntity.byAssignee({
  assigneeId: "emp-alice",
}).collect()
```

Every entity also exposes a `.primary(...)` accessor for the primary index — same contract as GSI accessors (required PK composites, optional SK composites: a partial sort key is a `begins_with` prefix match, a complete one an exact match):

```typescript
// Primary-index query — list every item under a shared primary partition.
// Used when multiple items share the primary PK and are distinguished by SK
// (the join-table single-table pattern).
const allMembers = yield* db.entities.Memberships.primary({
  orgId: "org-acme",
}).collect()
```

### Generated Accessor Mapping

Every index — **including `primary`** — gets a query accessor. Accessors accept required PK composites and optional SK composites (partial SK composites narrow to that level, stopping on a segment boundary; supplying every SK composite matches that key exactly). `.get(fullKey)` remains the dedicated `GetItem` path for single-item fetches by full primary key.

| Definition | Accessor | Argument Type |
|-----------|----------|---------------|
| `primaryKey: { pk: { composite: ["taskId"] }, ... }` | `db.entities.TaskEntity.get(...)` | `{ taskId: string }` |
| `primaryKey: { pk: { composite: ["orgId"] }, sk: { composite: ["userId"] } }` | `db.entities.Memberships.primary(...)` | `{ orgId: string; userId?: string }` |
| `indexes: { byProject: { name: "gsi1", pk: { composite: ["projectId"] }, ... } }` | `db.entities.TaskEntity.byProject(...)` | `{ projectId: string }` |
| `indexes: { byAssignee: { name: "gsi2", pk: { composite: ["assigneeId"] }, ... } }` | `db.entities.TaskEntity.byAssignee(...)` | `{ assigneeId: string }` |

### `.primary()` vs `.get()`

Use `.get(fullKey)` when you know the full primary composite key and want a single item — it's a strongly-consistent `GetItem`, cheaper than a `Query`. Use `.primary(partialKey)` when you want to list items that share a primary partition key, for example a join-table where one partition holds many items distinguished by the sort key:

```typescript
// `Memberships` primary key: pk = orgId, sk = userId
//
// List every membership in an organization — PK only, SK composites omitted
const allMembers = yield* db.entities.Memberships.primary({
  orgId: "org-acme",
}).collect()

// Pin the whole sort key — this matches `u-bob` exactly and returns an
// array (empty or one item) rather than failing with `ItemNotFound`.
const bobs = yield* db.entities.Memberships.primary({
  orgId: "org-acme",
  userId: "u-bob",
}).collect()
```

Behavior is symmetric with GSI accessors: `.where()`, `.within()`, `.filter()`, `.select()`, `.limit()`, `.pageSize()`, `.maxPages()`, `.reverse()`, `.startFrom()`, `.consistentRead()`, `.onRequest()`, `.collect()`, `.fetch()`, `.paginate()`, `.count()` and `.explain()` all chain off the returned `BoundQuery`.

### How much of the sort key an accessor pins

Supplying **some** of the sort key composites narrows to exactly those composite values. The condition stops on a segment boundary, so a value is never confused with a longer sibling — `byTenant({ tenantId, status: "done" })` on `sk: ["status", "taskId"]` matches `done` only, not `done_archived` or `doneish`.

On a secondary index that includes the row that stops at that level, which an update can leave by [truncating its key](/effect-dynamodb/guides/index-policy/): `byPlace({ region, country, city: "sf" })` on `sk: ["country", "city", "block"]` returns the row keyed `…#city_sf` and everything under `…#city_sf#`, so the condition is `sk BETWEEN …#city_sf AND …#city_sf#U+FFFF`. `.where(eq)` on a composite that isn't the last, and an `eq` in `.within()`, mean the same. The primary key's rows are never truncated, so there the condition is `begins_with(sk, …#city_sf#)`.

Supplying **all** of them is an exact match. The stored key ends there, so there is no boundary to stop on, and the accessor sends `sk = …#label_ship` instead of a range. On `sk: ["label"]`, `byBoard({ boardId, label: "ship" })` returns `ship` only, not `shipped` or `ship_it`, and on a numeric composite `seq: 3` returns `3` only, not `3.14` or `3.5`. Up to 1.36 a full pin was still a `begins_with` and did return those longer siblings.

The same rule applies to the primary accessor, every GSI accessor (an index that holds an isolated or a clustered collection included) and `Entity.query.<index>`. `Aggregate.list` follows it too. A collection query takes partition key composites only, so it is unaffected. A full pin on the primary accessor of a [time-series](/effect-dynamodb/guides/timeseries/) entity returns the current item only, never its `#e#` event rows. An index whose sort key has no composites has nothing to pin: its accessor sends the partition key alone, as before.

## Sort Key Conditions

`.where()` adds a `KeyConditionExpression` against a remaining sort key composite — DynamoDB evaluates it on the index server-side, so it **does** reduce read capacity. Use it whenever the condition is on a sort-key composite the accessor hasn't already pinned. Operators: `eq`, `lt`, `lte`, `gt`, `gte`, `between`, `beginsWith`.

`beginsWith` is a text-prefix test, and a number has no text prefix: `3` is not a prefix of `35` by value. On a `number` or `bigint` composite `beginsWith(t.seq, 3)` therefore compiles to `eq` and matches `3` only. Use `between` for a numeric range.

"Hasn't already pinned" is enforced, not advice. DynamoDB allows exactly one sort key condition, and `.where()` **replaces** the condition the accessor installed for its pinned prefix — so a condition on a composite the accessor already fixed would discard that prefix and return rows outside it, not narrow within it. `byBoard({ boardId, label: "ship" }).where((t, { eq }) => eq(t.label, "shine"))` would have matched `shine` rows. It is now refused with `EDD-9053`, and on an accessor that pins every composite `.where()` is not offered at all.

The operand you pass is a **composite attribute value**, not a raw sort key. The library runs it through the same pipeline the write path used — the composite's own codec, then serialization, then casing — and drops the result into the same `$schema#v1#entity#<name>_<value>` shape, so `gte(t.createdAt, "2025-02-10")` compares like-for-like against the stored key.

That includes the composite's **type**. A composite typed `number`, `bigint`, `boolean`, `Date` or `DateTime` takes a value of that type, not a string, because the write path writes numbers and bigints as key text that sorts in numeric order (`42` as `0000000000000042`, negatives and fractions included; see [Indexes](/effect-dynamodb/guides/indexes/#numeric-composites)) and formats dates as ISO strings. Passing `"42"` for a numeric composite is a compile error rather than a query that silently matches nothing.

It also covers composites whose schema **transforms** between its domain type and what DynamoDB stores. `Schema.BigIntFromString` has a `bigint` domain type and a string wire form, so a `420n` composite is stored as `txn_420`; `.where((t, { eq }) => eq(t.txn, 420n))` encodes the operand the same way and finds it. A value that cannot be encoded at all — a prefix string against a `bigint` composite, say — is refused with `EDD-9050` rather than silently compared against nothing.

:::note[Keys and composites always take the domain type]
`.get()`, `.update()`, `.delete()` and every query accessor take the composite's **domain** value — the same one the model holds and `.where()` accepts — never its stored wire form. On the `Ledger` above that is `get({ bookId, txn: 420n })`, not `get({ bookId, txn: "420" })`; the wire form is rejected with a `ValidationError` naming the attribute. One convention across the whole API.
:::

```typescript region="sk-conditions" example="guide-queries.ts"
// byProject SK composites: ["status", "createdAt"].
// `.where()` constrains the first composite the accessor did not pin.
const activeTasks = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .where((t, { eq }) => eq(t.status, "active"))
  .collect()

// Pin `status` on the accessor, then range over `createdAt`.
const activeSinceFeb = yield* db.entities.TaskEntity.byProject({
  projectId: "proj-alpha",
  status: "active",
})
  .where((t, { gte }) => gte(t.createdAt, "2025-02-10"))
  .collect()

// `between` is inclusive at both ends.
const activeInFeb = yield* db.entities.TaskEntity.byProject({
  projectId: "proj-alpha",
  status: "active",
})
  .where((t, { between }) => between(t.createdAt, "2025-02-01", "2025-02-28"))
  .collect()
```

```typescript region="sk-typed-operands" example="guide-queries.ts"
// `estimateHours` is a number, so `.where()` takes a number — not a string.
// The library encodes it exactly as the stored key was encoded.
const bigTasks = yield* db.entities.TaskEntity.byEstimate({ projectId: "proj-alpha" })
  .where((t, { gte }) => gte(t.estimateHours, 8))
  .collect()
```

`.where()` consumes the remaining SK composites — it can be called **once** per query. Constrain a later composite by pinning the earlier ones on the accessor itself, as `activeSinceFeb` does above. Targeting a composite while an earlier one is still unpinned is rejected with `EDD-9004`, and calling `.where()` on an index whose sort key has no composites is rejected with `EDD-9045`.

A condition on a **non-terminal** composite (`status`, with `createdAt` still to follow) covers that value's whole subtree: `eq(t.status, "active")` matches every `active` task regardless of `createdAt`, and `lte`/`between` include the far edge of the subtree.

Bounds compare values, whatever characters they hold. A string's key text escapes every character up to `%` (control characters, space, `!`, `"`, `#`, `$`, `%`) as `%` and two hex digits, so `new york` is stored as `new%20york` and keys sort the way their values do: on `sk: ["city", "siteId"]`, `lte(t.city, "new york")` returns `new` and `gt(t.city, "new")` returns `new york`, each in one request. A value may hold `#` — `a#b` is one value, and `eq(t.city, "a")` doesn't return it. Up to 1.36 keys weren't escaped: a space, `!`, `"` or a control character sorted below the `#` that follows a non-terminal composite, so the first bound left `new` out and the second left `new york` out. Values without such characters keep their 1.36 keys and requests; the [Key text](/effect-dynamodb/guides/indexes/#key-text) lists which stored keys changed in 1.37. A row 1.36 wrote under a key whose text changed is read by your pins and an `eq` or `beginsWith` bound, but not by a range bound until it moves ([Migrating rows written by 1.36](/effect-dynamodb/guides/indexes/#migrating-rows-written-by-136)).

A strict `lt` on the **last** SK composite when the accessor has pinned an earlier one — `byProject({ projectId, status: "active" }).where((t, { lt }) => lt(t.createdAt, "2025-03-01"))` — is sent as a `BETWEEN` from the pinned prefix to the greatest key text below the value's, so it is exact on the key. Up to 1.36 it threw `EDD-9046`, now retired.

## Bounding any sort key composite: `.within()`

`.where()` constrains the **first** composite the accessor left open. `.within()` bounds **any** of them, in their own types, and the library picks the plan:

```typescript region="within-skip-scan" example="guide-queries.ts"
// `.where()` can't bound createdAt without pinning status first. `.within()`
// can: it finds each status with a one-row probe, then reads only that
// status's createdAt range.
const febTasks = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .within({ createdAt: { between: ["2025-02-01", "2025-02-28"] } })
  .collect()
```

Each bound is `{ eq }`, `{ between: [low, high] }`, or a lower end (`gt` / `gte`) and / or an upper end (`lt` / `lte`). A composite left out is unbounded.

| Bounds | Plan | Reads |
|---|---|---|
| On the next open composite (and `eq` on any that follow it, then at most one range) | `key` | The one key condition `.where()` would send |
| Bounds no value satisfies (`{ gt: 3, lte: 3 }`, `{ gte: 4, lte: 3 }`) | `empty` | Nothing: no request is sent |
| On a later composite, with open composites before it | `skip-scan` | One `Limit: 1` probe per distinct value of the open composites (a *tuple*), then that tuple's range. Results come back in sort key order |
| The same, when skip-scan isn't sound | `filter` | The pinned range once, every bound checked per row |

Skip-scan pays when the skipped composites have few distinct values relative to the rows (statuses, categories, regions). Any composite can be in the tuple: key text escapes the `#` delimiter, so a probe always parses the tuple it lands on. It isn't sound, and the query takes the `filter` plan, in one case:

- **History rows.** The primary-key accessor of an entity with `versioned: { retain: true }`, `softDelete` or `timeSeries` shares its partition with snapshot, tombstone and event rows whose keys don't parse as tuples.

Each probe is a request, counted by `.maxPages()`, and costs the size of the row it reads (rounded up to 4 KB), not a fixed small amount. `maxSkips` (default 32) caps the probes per terminal call: past it, the rest of the range is read once with every bound checked per row. `{ maxSkips: 0 }` takes the filter plan from the start:

```typescript
db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .within({ createdAt: { gte: "2025-02-01" } }, { maxSkips: 0 })
```

A bound the key condition can't express is checked on each row, with the same casing and number padding the keys use. `.within()` excludes `.where()` (and a second `.within()`); it isn't offered on an accessor whose composites are all pinned, on collections or on `scan()`. A value that can't be encoded throws `EDD-9050`, and a misuse reachable from untyped code (an unknown or pinned field, an operator outside the list above) throws `EDD-9093`, both at `.within()`.

On a [Z-order index](/effect-dynamodb/guides/zorder/), `.within()` bounds a box over the interleaved dimensions instead.

On a [sharded index](/effect-dynamodb/guides/sharding/), `.within()` fails with `EDD-9104`.

## Post-Query Filtering

`.filter()` applies a `FilterExpression` after items are read from the index -- it does **not** reduce read capacity, only network transfer. Use it for conditions on non-key attributes.

```typescript region="filter-callback" example="guide-queries.ts"
// Shorthand — AND-equality on multiple fields
const highPriActive = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .filter({ status: "active", priority: "high" })
  .collect()
```

```typescript region="filter-shorthand" example="guide-queries.ts"
// Shorthand — simple AND-equality
const activeShorthand = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .filter({ status: "active" })
  .collect()
```

### Predicates DynamoDB cannot express

`.filterBy()` takes an ordinary TypeScript predicate, evaluated on the **decoded item** — for conditions a `FilterExpression` has no operator for. Case-insensitive matching is the standard case: DynamoDB has no `lower()`, so a `FilterExpression` compares the stored attribute byte-for-byte.

```typescript
// Stored: name = "Melbourne Cricket Ground"
.filter((t, { beginsWith }) => beginsWith(t.name, "melbourne"))   // no match
.filterBy((v) => v.name.toLowerCase().startsWith("melbourne"))    // matches
```

Composite **keys** do not have this problem — casing is folded on both the stored key and the operand — so take as much as the key prefix can carry and match the rest with `.filterBy()`.

The predicate runs **inside the same accumulate loop** `.limit()` uses, which is the whole point of it being a combinator rather than something you do to the result. Filtering `page.items` yourself breaks pagination twice over: the page comes back short, and its cursor resumes after the last item *returned* rather than the last one *kept*, so the next page skips rows.

Two consequences worth knowing:

- **It runs after the read.** Every examined row still crosses the wire and is still paid for. Prefer `.filter()` whenever DynamoDB can express the condition.
- **`.count()` reads rows.** `Select: "COUNT"` returns no items to test, so under `.filterBy()` the rows are read and the accepted ones counted. Correct, but it costs what a `.collect()` costs.

`.filterBy()` cannot be combined with `.select()` — a projection returns only the attributes it names, and a predicate is a closure whose reads the library cannot see, so it would be handed items missing the fields it tests. That combination raises `EDD-9054`.

`Aggregate.list` takes the same thing as `filterBy` in its options, applied to the root item **before assembly** — so a rejected aggregate never pays for its partition read.

**When to use SK composites vs `filter` vs `filterBy`:**

| Approach | DynamoDB Mapping | Reduces Read Capacity? | Use For |
|----------|------------------|----------------------|---------|
| SK composites in accessor | `KeyConditionExpression` | Yes | Narrowing by sort key prefix |
| `.within()` | `KeyConditionExpression` per tuple (skip-scan) | Yes, when the skipped composites have few values | Ranges on any sort key composite |
| `.filter()` | `FilterExpression` | No | Any attribute (post-read) |
| `.filterBy()` | none — runs in the client | No | Conditions DynamoDB has no operator for |

See the [Expressions Guide](/effect-dynamodb/guides/expressions/) for the complete operator reference and DynamoDB mapping tables.

## Collection Queries

Collection queries return all member entity types, grouped by member name.

```typescript
const db = yield* DynamoClient.make({
  entities: { ClusteredEmployees, ClusteredTasks },
  tables: { MainTable },
})

// All entities in the collection (auto-discovered from entity indexes with collection: "tenantMembers")
const { ClusteredEmployees, ClusteredTasks } = yield* db.collections
  .tenantMembers({ tenantId: "t-acme" })
  .collect()
// ClusteredEmployees: Employee[], ClusteredTasks: Task[]
```

### Hierarchical Sub-Collections

Use the array form `collection: ["parent", "child"]` together with `type: "clustered"` to nest entities in a hierarchy. A query at the parent level returns the parent's items **and** every descendant; a query at a child level returns only items at that level or deeper.

```typescript
// Parent — returns Employee + Task + ProjectMember (everything in the partition)
const contributions = yield* db.collections
  .contributions({ employeeId: "emp-alice" })
  .collect()
// { SubEmployee: Employee[], SubTasks: Task[], SubProjectMembers: ProjectMember[] }

// Child — returns only the deeper-level entities
const assignments = yield* db.collections
  .assignments({ employeeId: "emp-alice" })
  .collect()
// { SubTasks: Task[], SubProjectMembers: ProjectMember[] }
```

For independent collections that just happen to share an index (no parent/child relationship), use a single string instead of an array (`collection: "name"`). See the [Indexes & Collections guide](/effect-dynamodb/guides/indexes/#hierarchical-sub-collections) for the full pattern, SK shape, and trade-offs.

## Pagination

### Collect All Items

`.collect()` fetches all pages and flattens into a single array (or grouped result for collections):

```typescript region="collect-all" example="guide-queries.ts"
// Collect all items across all pages
const allProjectTasks = yield* db.entities.TaskEntity.byProject({
  projectId: "proj-alpha",
}).collect()
```

### `limit` vs `pageSize`

These are two different ideas, and they do not share a word:

| Combinator | Contract | Sets DynamoDB `Limit`? |
|---|---|---|
| `.limit(n)` | Return **at most `n` items** — a contract on results | Not as given — each request is [sized](#request-sizing) toward it |
| `.pageSize(n)` | Fetch in **batches of `n` rows** — a contract on round trips | Yes |
| `.maxPages(n)` | Stop after **`n` requests**, however many items that yielded | No |

```typescript region="limit-vs-pagesize" example="guide-queries.ts"
// `limit` bounds the RESULT — at most 3 tasks come back
const firstThree = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .limit(3)
  .collect()

// `pageSize` bounds each ROUND TRIP — every match comes back, fetched in
// requests of 2
const inBatches = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .pageSize(2)
  .collect()

// Both compose — requests of 2, accumulating until 5 items
const batchedAndCapped = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .pageSize(2)
  .limit(5)
  .collect()
```

`.limit(n)` works under a `.filter()` (and under a `.filterBy()`), and this is the reason the two are separate. DynamoDB's `Limit` bounds the rows **examined**, and a `FilterExpression` is applied *after* that — so `Limit` can never express "give me 3 matching items". `.limit()` is satisfied by accumulating across requests until `n` items are accepted or the key range is exhausted; each of those requests is sized as described below, or by `.pageSize()` when you set it. To bound the work outright, add `.maxPages()`.

:::caution[Changed in 1.16]
`.limit(n)` used to set DynamoDB's per-request `Limit`, which meant `.limit(3).collect()` returned **every** matching item, fetched in pages of 3. It now returns 3. If you were using `.limit()` as a page-size hint, move to `.pageSize()` — `.limit(2).paginate()` streaming everything in pages of 2 becomes `.pageSize(2).paginate()`.
:::

### Request sizing

With a `.limit()` and something that drops rows — a `.filter()`, a `.filterBy()` predicate, history rows, or a bound `.within()` checks per row — each request's `Limit` is **sized from the pass rate the earlier requests observed** (rows accepted ÷ rows examined, from DynamoDB's `ScannedCount`). The first request asks for twice the limit, and at least 16 rows (just the limit when only history rows are dropped); each later one for what the observed rate says the remaining items need, with a 25% margin. A request that accepts nothing doubles the next. Requests never ask for more than 100,000 rows, and DynamoDB still stops each at 1 MB.

```typescript region="adaptive-sizing" example="guide-queries.ts"
// Under a filter, each request's Limit is sized from the pass rate so far:
// the first asks for max(16, 2 × limit) rows, later ones for what the
// observed rate says the remaining items need.
const lowPriority = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .filter({ priority: "low" })
  .limit(2)
  .onRequest((event) =>
    Console.log(
      `  request ${event.request}: Limit ${event.limit}, examined ${event.scannedCount}, accepted ${event.accepted}`,
    ),
  )
  .collect()
```

```text
  request 1: Limit 16, examined 6, accepted 2
```

| Query | Each request's `Limit` |
|---|---|
| `.limit(n)` with a filter, predicate, history rows or a per-row check | Sized from the pass rate (above) |
| `.limit(n)` with nothing that drops rows | The items still owed |
| `.pageSize(n)` | `n`, never adapted (with a `limit` and nothing that drops rows, at most the items still owed) |
| `.pageSize("natural")` | 1.36's sizing (below) |
| `.limit(n)` with `.maxPages()` | 1.36's sizing: a capped number of smaller requests would return fewer items per call. A `.within()` query, new in 1.37, adapts under `.maxPages()` too |
| No `.limit()` | None: natural 1 MB pages, as before |

`.pageSize("natural")` opts out, and sizes every request exactly as 1.36 did: a natural 1 MB page under a filter or predicate, doubling per request over history rows, and the items still owed otherwise.

```typescript region="page-size-natural" example="guide-queries.ts"
// Opt out: size requests exactly as 1.36 did — a natural 1 MB page under a filter.
const lowPriorityNatural = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .filter({ priority: "low" })
  .limit(2)
  .pageSize("natural")
  .collect()
```

Any other string throws `EDD-9095`.

:::caution[Changed in 1.37]
Sizing is now adaptive by default for a `.limit()` under a filter. The items `collect()` and `count()` return, and the items a `fetch()` chain returns end to end, are unchanged; request counts and read units change. A selective filter with `limit(5)` no longer reads a 1 MB page to return 5 items, but a low or uneven pass rate can take more round trips than one natural page (a logarithmic number more in the worst case). Three things you can observe change with it:

- **A `fetch()` cursor's value** can differ. It resumes at the same place.
- **A `fetch()` cursor can be `Some` where it was `None`**: when the limit fills on the last row a sized request returned, DynamoDB reports more to read. The chain then ends with one empty page.
- **`Query.paginate`'s page boundaries** follow the sized requests, since it emits one array per request; the items it streams are unchanged. A bound query's `.paginate()` streams items and is unaffected.

`.pageSize("natural")` restores the 1.36 behaviour for one query.
:::

### Single Page

`.fetch()` returns one page of items plus an optional cursor. Without a `.limit()`, a page is one DynamoDB request; with `.limit(n)`, a page is `n` items and the request loop fills it:

```typescript region="single-page" example="guide-queries.ts"
// Single page with limit — returns page with items and cursor
const page = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" }).limit(3).fetch()
// page.items: Task[] (up to 3 items)
// page.cursor: Option<string> — Some resumes after the 3rd item, None when done
```

The cursor always resumes **after the last item you were handed**, even when the underlying request read past it and the surplus was discarded. A `None` cursor means the key range is genuinely exhausted.

:::caution[Changed in 1.37]
`cursor` is an `Option<string>`; it was `string | null`. Where something needs a nullable, such as a JSON response, use `Option.getOrNull(page.cursor)` (or a `Schema.OptionFromNullOr` field). `.startFrom()` still takes a string.
:::

### Cursor-Based Pagination

Use `.startFrom()` to resume from a previous page's cursor:

```typescript region="cursor-pagination" example="guide-queries.ts"
// Cursor-based pagination: the next page, if there is one
const alpha = db.entities.TaskEntity.byProject({ projectId: "proj-alpha" }).limit(3)
const page1 = yield* alpha.fetch()
const page2 = yield* Option.match(page1.cursor, {
  onNone: () => Effect.succeed([]),
  onSome: (cursor) =>
    alpha
      .startFrom(cursor)
      .fetch()
      .pipe(Effect.map((next) => next.items)),
})
```

To read every page by cursor, `Stream.paginate` takes the cursor as its stop signal: see [Z-order cursors](/effect-dynamodb/guides/zorder/#cursors). To stream every item in one process, use `.paginate()`.

A query on a [sharded index](/effect-dynamodb/guides/sharding/#cursors) has a cursor with one position per shard, under the same contract.

A cursor is opaque and belongs to the query that produced it: resume with the same accessor, bounds, `.within()` and direction. It is read when the terminal runs, not by `.startFrom()`, so the order of `.startFrom()` and `.within()` in the chain doesn't matter.

A malformed cursor fails the terminal with a `ValidationError` (`EDD-9094`, `operation: "query.startFrom"`). So does a cursor that only a `.within()` query could have written, given to a query without `.within()`. A `.within()` query also checks the cursor against its plan, and fails the same way for a cursor from a `.within()` query with other bounds, another partition, the other direction or another index declaration, or one whose position lies outside the plan. A query without `.within()` can't tell another query's well-formed cursor from its own: its cursors are the same as in earlier releases, with nothing to check. DynamoDB may reject that cursor, failing the query with a `DynamoValidationError`, or the query resumes from wherever the cursor points.

A `.within()` query's cursor records how far through its plan the query has got, so it stays valid if you change `maxSkips` or the [Z-order](/effect-dynamodb/guides/zorder/#cursors) strategy options between pages.

:::caution[Changed in 1.37]
A malformed cursor used to throw from `.startFrom()` itself. It now fails the query, with a `ValidationError` on the terminal's error channel. Cursors from earlier releases still work.
:::

### Streaming

`.paginate()` returns a `Stream<A>`, automatically handling DynamoDB pagination:

```typescript region="streaming" example="guide-queries.ts"
// Streaming — automatic pagination via Stream
const stream = tasks.scan().paginate()
const allFromStream = yield* Stream.runCollect(stream)
```

## Scan

Entity scans read the entire table and return items matching the entity type. `db.entities.Entity.scan()` returns a `BoundQuery`, so all combinators and terminals work with scans.

```typescript region="scan-basic" example="guide-queries.ts"
// Basic scan — all items of this entity type
const allTasks = yield* tasks.scan().collect()
```

```typescript region="scan-filter" example="guide-queries.ts"
// Scan with filter
const activeScan = yield* tasks.scan().filter({ status: "active" }).collect()
```

```typescript region="scan-limit" example="guide-queries.ts"
// Scan with limit — at most 3 items come back
const firstPage = yield* tasks.scan().limit(3).collect()
```

```typescript region="scan-page-size" example="guide-queries.ts"
// Scan in batches — every item comes back, read 3 rows per request
const batchedScan = yield* tasks.scan().pageSize(3).collect()
```

```typescript region="scan-consistent" example="guide-queries.ts"
// Scan with consistent read
const consistent = yield* tasks.scan().consistentRead().collect()
```

```typescript region="scan-stream" example="guide-queries.ts"
// Stream-based scan
const scanStream = tasks.scan().paginate()
yield* Stream.runForEach(scanStream, (t) => Console.log(`  Scanned: ${t.taskId} — "${t.title}"`))
```

**When to use Scan vs Query:**

| | Query | Scan |
|---|-------|------|
| Targets | Specific partition | Entire table |
| Efficiency | Reads only matching partition | Reads every item |
| Cost | Low (proportional to results) | High (proportional to table size) |
| Use cases | Normal application queries | Admin tools, migrations, data exports, analytics |

Scan automatically filters by `__edd_e__` -- even in a single-table design, `db.entities.Tasks.scan()` only returns Task items.

## Consistent Reads

By default, DynamoDB reads are eventually consistent. For strong consistency, use `consistentRead`:

```typescript region="consistent-get" example="guide-queries.ts"
// Consistent read on get — use entity definition's get + pipe
const consistentTask = yield* TaskEntity.get({ taskId: "t-001" }).pipe(Entity.consistentRead())
```

```typescript region="consistent-scan" example="guide-queries.ts"
// Consistent read on scan (applies to any BoundQuery against the base table).
// Note: DynamoDB reads a GSI only eventually consistently.
const consistentScan = yield* tasks.scan().consistentRead().collect()
```

Consistent reads cost 2x the read capacity of eventually-consistent reads. Use them when you need read-after-write consistency (e.g., immediately after a put or update). **An entity's consistent reads come from the base table** — `get`, a primary-key query or a scan. DynamoDB reads a GSI only eventually consistently, and an entity's indexes are always GSIs (`db.tables.*.create()` creates them as GSIs), so `.consistentRead()` on an entity index accessor, or on a collection over one, is sent as asked and DynamoDB rejects it: the query fails with a `ValidationError` (`operation: "query.consistentRead"`) naming the index, with DynamoDB's error as its `cause`. An index you pointed at an LSI of a table you created yourself reads consistently, as DynamoDB allows.

## Ordering

By default, results are in ascending sort key order. Use `.reverse()` for descending:

```typescript region="reverse" example="guide-queries.ts"
// The 3 most recent tasks (descending sort key order)
const recent = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .reverse()
  .limit(3)
  .collect()
```

## Inspecting a query: `explain()` and `onRequest()`

Every bound query, collection queries included, has two inspection hooks.

`.explain()` describes what the terminals would send, without sending anything: the plan, why it was chosen, the key ranges known up front, the bounds checked per row, and how requests are sized. It reads no cursor, so it describes the plan from its start, and it can't fail.

```typescript region="explain" example="guide-queries.ts"
const plan = yield* db.entities.TaskEntity.byProject({ projectId: "proj-alpha" })
  .within({ createdAt: { between: ["2025-02-01", "2025-02-28"] } })
  .explain()
// plan.plan   → "skip-scan"
// plan.reason → "skip tuple: status"
```

| Field | Meaning |
|---|---|
| `index` | The physical index, or `"primary"` |
| `plan` | `"key"` (one key condition alone), `"skip-scan"`, `"filter"`, `"empty"` (nothing to read), or a Z-order plan: `"naive"`, `"jump"`, `"precise"` |
| `reason` | Why: `"one key condition"`, `"skip tuple: status"`, `"history rows on the primary index"`, `"maxSkips: 0"`, `"the bounds admit no value"`, `"exact plan over maxRanges"`, … |
| `keyConditions` | The ranges known before anything is read, as `{ lower, upper, exact }`; `exact: false` means rows in it are also checked |
| `filter` | The `FilterExpression` the plan adds, if any |
| `rowChecks` | The fields checked on each row in the client |
| `sizing` | `"adaptive"`, `"budget"` (the items still owed), `"fixed"` (`pageSize(n)`) or `"natural"` |
| `zorder`, `maxSkips` | The Z-order box and address width; the skip-scan probe budget |
| `fanOut` | A [sharded index's](/effect-dynamodb/guides/sharding/#concurrency-and-inspection) partitions, whether a pin reduced them to one shard, and the requests in flight at once |

`.onRequest(observer)` runs `observer` after every request a terminal sends, probes included, in the terminal's fiber and in the order the observers were added. Each event carries:

| Field | Meaning |
|---|---|
| `kind` | `"read"`, `"probe"` (skip-scan) or `"count"` (`count()`'s `Select: "COUNT"` requests) |
| `request` | 1-based, within the terminal call |
| `lower`, `upper` | The sort key condition sent, for display |
| `limit` | The `Limit` sent |
| `scannedCount` | Rows DynamoDB examined (`ScannedCount`) |
| `count` | Rows after the `FilterExpression` (`Count`) |
| `accepted` | Rows that became items |
| `discarded` | A read sent alongside others, then not used (its rows are counted, none became items) |

Σ `scannedCount` against Σ `accepted` is what a query read against what it returned. A failure in the observer is a defect. DynamoDB calls the observer itself makes are not charged to the query's [consumed capacity](/effect-dynamodb/guides/consumed-capacity/) report.

`Query.explain` and `Query.onRequest` are the same hooks for a pipeable `Query`.

## Complete Example

```typescript
import { Effect, Layer, Stream } from "effect"
import { DynamoClient } from "effect-dynamodb"

const program = Effect.gen(function* () {
  const db = yield* DynamoClient.make({
    entities: { TaskEntity, ClusteredEmployees, ClusteredTasks },
    tables: { MainTable },
  })

  // --- Single entity scan with filter ---
  const activeTasks = yield* db.entities.TaskEntity.scan()
    .filter({ status: "active" })
    .limit(50)
    .collect()

  // --- Entity index query, reversed, with filter ---
  const recentHighPriority = yield* db.entities.TaskEntity
    .byAssignee({ assigneeId: "emp-alice" })
    .filter({ priority: "high" })
    .reverse()
    .limit(10)
    .collect()

  // --- Auto-discovered collection query: all tenant members ---
  const { ClusteredEmployees, ClusteredTasks } = yield* db.collections
    .tenantMembers({ tenantId: "t-acme" })
    .collect()
  // ClusteredEmployees: Employee[], ClusteredTasks: Task[]

  // --- Scan with streaming ---
  const scanStream = db.entities.TaskEntity.scan()
    .filter({ status: "active" })
    .paginate()
  yield* Stream.runForEach(scanStream, (t) =>
    Effect.log(`Task: ${t.title}`)
  )
})

const main = program.pipe(
  Effect.provide(
    Layer.mergeAll(
      DynamoClient.layer({ region: "us-east-1" }),
      MainTable.layer({ name: "Main" }),
    )
  )
)
```
