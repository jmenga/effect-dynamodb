This guide covers how to define domain models, application schemas, tables, and entities in effect-dynamodb. These four constructs form the foundation of every application.

## Defining Your Domain Model

Models use standard Effect Schema definitions — `Schema.Class` for class instances or `Schema.Struct` for plain objects. They contain only domain fields — no DynamoDB concepts, no key composition, no timestamps.

```typescript region="model" example="guide-modeling.ts"
class Employee extends Schema.Class<Employee>("Employee")({
  employeeId: Schema.String.pipe(Schema.brand("EmployeeId")),
  tenantId: Schema.String.pipe(Schema.brand("TenantId")),
  email: Schema.String,
  displayName: Schema.NonEmptyString,
  department: Schema.String,
  // Self schema — wire format chosen by the storage override below
  // (transforms paired with `storedAs` are rejected at Entity.make time).
  hireDate: Schema.DateTimeUtc,
  createdBy: Schema.String,
}) {}
```

Models are portable. The same `Employee` schema can be used with DynamoDB, SQL, API responses, or any other storage backend. Branded types like `Schema.brand("EmployeeId")` prevent accidentally mixing up identifiers at compile time.

## Adding DynamoDB Concerns

`DynamoModel.configure` layers DynamoDB-specific overrides onto a pure domain model. The model stays clean — infrastructure details like field renaming, storage encoding, and immutability are declared separately.

```typescript region="configure" example="guide-modeling.ts"
const EmployeeModel = DynamoModel.configure(Employee, {
  createdBy: { immutable: true },
  hireDate: { field: "hd", storedAs: DynamoModel.DateEpochSeconds },
  displayName: { field: "dn" },
  employeeId: { identifier: true },
})
```

Pass the configured model to `Entity.make({ model: EmployeeModel, ... })`. The Entity reads these overrides when building derived schemas and DynamoDB operations.

### Available Options

Each field accepts an `AttributeConfig` object with these options:

| Option | Type | Description |
|--------|------|-------------|
| `field` | `string` | Rename the domain field to a different DynamoDB attribute name |
| `storedAs` | `DynamoModel.*` date schema, `DynamoModel.SparseMap()` or `DynamoModel.Packed(...)` | Override how the field is stored: a date encoding (must match the domain type), or a storage layout (see [Storage Layouts](#storage-layouts)) |
| `immutable` | `boolean` | Exclude from `Entity.Update` — read-only after creation |
| `identifier` | `boolean` | Mark as the identity field for ref/aggregate resolution |
| `ref` | `boolean` | Mark as a denormalized reference to another entity |

### Field Renaming

Map domain field names to shorter or different DynamoDB attribute names. Useful for reducing storage costs or matching an existing table schema:

```typescript
const EmployeeModel = DynamoModel.configure(Employee, {
  displayName: { field: "dn" },
  department:  { field: "dept" },
})
// Domain: employee.displayName → DynamoDB attribute: "dn"
```

### Storage Encoding

Override how a field is stored in DynamoDB. The domain type must match (enforced at compile time):

```typescript
const EmployeeModel = DynamoModel.configure(Employee, {
  // Domain: DateTime.Utc → stored as epoch seconds (for DynamoDB TTL)
  hireDate: { storedAs: DynamoModel.DateEpochSeconds },
})
```

Available date schemas: `DynamoModel.DateString` (ISO), `DynamoModel.DateEpochMs`, `DynamoModel.DateEpochSeconds`, `DynamoModel.DateTimeZoned`. See [Advanced](/effect-dynamodb/guides/advanced/) for the full date schema reference.

#### Self schemas vs. transforms

**Storage overrides only apply to self date schemas.** If you declared a transform schema (e.g. `Schema.DateTimeUtcFromString`), that transform IS the wire format — `storedAs` and other `DynamoEncoding` annotations are rejected at `Entity.make()` time. The two configuration paths are mutually exclusive: either declare a self schema (`Schema.DateTimeUtc`) and let the annotation drive storage, OR declare a transform and own the wire format yourself.

| Pattern | Domain type | Wire format source |
|---|---|---|
| Self + annotation | `Schema.DateTimeUtc` | `storedAs` (configure) or `pipe(DynamoModel.storedAs(...))` annotation — `string` (default), `epochMs`, or `epochSeconds` |
| Transform | `Schema.DateTimeUtcFromString`, `DynamoModel.DateString`, `DynamoModel.DateEpochSeconds`, … | The transform itself — `storedAs` is rejected |

Applying `storedAs(DynamoModel.DateEpochSeconds)` on top of `Schema.DateTimeUtcFromString` (which already encodes to a string) used to silently override the transform's wire format. After the codec direction fix in v1.4, this combination raises a clear error at `Entity.make()` time. Migrate to a self schema (`Schema.DateTimeUtc.pipe(DynamoModel.storedAs(...))`) or drop the override.

#### Dates nested in containers

A self date schema is stored in its wire form wherever it sits in the model: at the top level, in a `Schema.Struct` or `Schema.Class`, in an array, and also in a container such as these:

- a `Schema.NullOr` or other union, such as `Schema.NullOr(Schema.DateTimeUtc)`
- a nullable class, such as `Schema.NullOr(Stamp)`, where `Stamp` has a date field
- an array of a union, such as `Schema.Array(Schema.NullOr(Schema.DateTimeUtc))`
- a `Schema.Record` value, such as `Schema.Record(Schema.String, Schema.DateTimeUtc)`
- a `Schema.Tuple`, `Schema.TupleWithRest` or `Schema.StructWithRest`

A `storedAs` annotation applies there too, so `Schema.NullOr(Schema.DateTimeUtc.pipe(DynamoModel.storedAs(DynamoModel.DateEpochMs)))` stores a number. A `DynamoModel.configure` `storedAs` override on a union field applies to the union's date member. If the union has more than one date member, the override can't say which one it means, and `Entity.make()` rejects it with `EDD-9057`; annotate the intended member with `.pipe(DynamoModel.storedAs(...))` instead. Transform schemas such as `Schema.DateTimeUtcFromString` already owned their wire form in every container and are unchanged.

#### Dates in unions

A union is read back by trying its members, so a stored value must not be claimable by two of them.

- **A date stored as a string next to a string member.** In `Schema.Union([Schema.DateTimeUtc, Schema.String])`, the date member claims only the exact ISO string the library writes for a date, and it is tried first. A string such as `"2020"`, `"5"` or `"hello"` reads back as a string. A string that happens to be a canonical ISO instant, such as `"2000-01-01T00:00:00.000Z"`, reads back as a `DateTime`. If a string field may legitimately hold ISO instants, use a tagged or discriminated shape instead of a bare union. The same rule applies through nested unions, such as `Schema.Union([Schema.NullOr(Schema.DateTimeUtc), Schema.String])`.
- **A date stored as a number next to a numeric member.** A date stored as epoch milliseconds or seconds next to `Schema.Number`, a number literal, `Schema.BigInt` or another epoch date can't be told apart from that member at all, so `Entity.make()` rejects it with `EDD-9058`. Store the date as a string (the default for a self date), or remove the numeric member. On an entity, `Schema.NumberFromString` and `Schema.BigIntFromString` are stored as strings, so they don't collide. An aggregate also rejects those two, because it re-decodes domain values on `update`, where their domain value is a number (see [Aggregates](/effect-dynamodb/guides/aggregates/#how-values-are-stored)).

#### Zoned dates

A zoned field, either `DynamoModel.DateTimeZoned` or a self `Schema.DateTimeZoned`, is stored as an ISO string with its zone, and read back with the same zone: a named zone as `2025-01-01T19:00:00.000+09:00[Asia/Tokyo]`, an offset zone as `2025-01-01T15:00:00.000+05:00`. That holds wherever the field sits, on entities and aggregates. Versions up to 1.22.0 read an offset zone back as UTC. The stored form is unchanged.

Offsets that aren't whole minutes, such as historical local-mean-time offsets or a sub-minute `DateTime.zoneMakeOffset`, are rounded to the minute by Effect's ISO format, and the instant read back moves by the same amount. Earlier versions behaved the same way.

#### Maps

Use `Schema.Record` for a keyed collection of values. A `Schema.ReadonlyMap` is refused when the model loads (`EDD-9125`), at any depth: it would be stored as a DynamoDB map, which reads back as a plain object, so the row wouldn't decode. `Schema.Record` is stored the same way, so rows a map field wrote read back with no rewrite.

A `Map` in your domain model is fine as long as its encoded side isn't one: decode it from a `Schema.Record` with `Schema.decodeTo`, or wrap it in `Schema.toCodecJson`. The field of a `many` edge can also be one, since its collection is taken apart into rows and never stored itself, so it's created, read and updated like any other `many` edge.

#### Types that can't be read back

`Entity.make`, `Aggregate.make`, `EventStore.makeStream` (each event, `metadata` and the snapshot state) and `outbox.schema` on `EventStore.projection` and `EventStore.multiProjection` refuse these when the definition loads (`EDD-9125`), at any depth, naming the path:

| Refused | What happens without the refusal | Use |
|---------|----------------------------------|-----|
| `Schema.URL` | Stored as a map of its parts, and the row doesn't decode | `Schema.URLFromString` |
| `Schema.ByteSize` | Stored as a number, and the row doesn't decode | `Schema.ByteSizeFromString` or `Schema.ByteSizeFromNumber` |
| `Schema.URLSearchParams` | Stored as a map of its size alone | `Schema.String`, holding the parameters as text |
| `Schema.RegExp` | Stored as an empty map | `Schema.String`, holding the pattern as text |
| `Schema.FormData` | Stored as an empty map | `Schema.Record` |
| `Schema.Headers` | Stored as a map, and the row doesn't decode | `Schema.Record` |
| `Schema.File` | Stored as bytes, without its name or type | `Schema.Uint8Array` |
| `Schema.ErrorInstance` | Stored as an empty map | `Schema.Defect()` |
| `Schema.Chunk` | The write overflows the stack, and nothing is stored | `Schema.Array` |
| `Schema.HashMap` | A non-empty one can't be written, and an empty one doesn't decode | `Schema.Record` |
| `Schema.ReadonlyMap` | See [Maps](#maps) | `Schema.Record` |
| A bigint `Schema.Literal` | Stored as a number, and the row doesn't decode | A string or number literal |
| `Schema.DurationFromNanos`, `Schema.ByteSizeFromBigInt`, or any transformation over `Schema.BigInt` | Stored as a number, and the row doesn't decode | `Schema.DurationFromMillis`, `Schema.ByteSizeFromString` |

A few more depend on what stores them. An entity's and an aggregate's fields are substituted before they're marshalled, so these read back there, in a struct, an array, a record, a tuple or a union. A stream, a snapshot and an outbox encode through the schema alone, and nothing reaches inside another declaration such as `Schema.Option` or `Schema.ReadonlySet`, a `Schema.suspend`, or a transformation over a container. In those places they're refused too. So are a `Schema.Date` and a `Schema.Redacted` in a struct, a record, a tuple or a union with a decoding default, where a read reaches them and a write doesn't:

| Refused | What happens without the refusal | Use |
|---------|----------------------------------|-----|
| `Schema.Date` | Stored as an empty map, so the instant is lost | `Schema.DateFromString` or `Schema.DateFromMillis` |
| `Schema.Redacted` | The value isn't stored, and the read dies | `Schema.RedactedFromValue` |
| `Schema.BigInt`, on an entity or an aggregate only | Stored as a number, and the row doesn't decode | `Schema.BigIntFromString` |

On a stream, a snapshot and an outbox, `Schema.BigInt` isn't refused. It's stored as a number, and every read gives back a `bigint`, at any depth and under `Schema.Option`, `Schema.ReadonlySet` or a `Schema.suspend`, on rows already stored too. A number past 2^53 and a smaller one read back alike. What's refused there is a union that stores something else as a number, such as `Schema.Union([Schema.Number, Schema.BigInt])`, `Schema.Literal(5)` beside it, or a struct or an event with a number in the same field: `5n` and `5` are stored the same, so a read can't tell which one was written. That's judged on what the members could store, so a struct holding a `bigint` beside any of Effect's other declarations is refused too. Use `Schema.BigIntFromString`, which is stored as a string. Under `DynamoModel.Packed`, a `bigint` fails its write with a `ValidationError` naming the path, as JSON has no form for it, and nothing is written.

`Schema.DateTimeUtcFromDate` and any other transformation over `Schema.Date` are refused on an entity, a stream, a snapshot and an outbox, and on an aggregate under a union or `Schema.NullOr`, or when it decodes to something other than a date. Use `Schema.DateTimeUtcFromString` or `Schema.DateTimeUtcFromMillis`.

`Schema.Date` and `Schema.Redacted` after another member of a `Schema.optionalKey` union are refused on an entity and an aggregate, in a struct or a list there too, because only the first member is written in its stored form: `Schema.optionalKey(Schema.Union([Schema.String, Schema.Date]))` would store a date as an empty map. Declare the member first, use `Schema.optional`, or use `Schema.DateFromString` or `Schema.RedactedFromValue`. On an aggregate, an attribute that's only a date or null isn't refused, because its date encoder stores it as a string.

What's read is the stored side, so any of these under `Schema.toCodecJson`, or decoded from a type that reads back, isn't refused.

#### Types that read back changed

These aren't refused, because rows exist and read, but what comes back isn't quite what was written. Prefer the form on the right for a new field.

- **`Schema.Duration`.** Stored as Effect's internal form, and reads back as a plain object with no prototype. `Duration.toMillis`, `Duration.sum` and `Duration.format` work on it. `Equal.equals` with the same duration is `false`, and `.pipe` is `undefined`. Use `Schema.DurationFromMillis`, which is stored as a number and comes back as a `Duration`.
- **`Schema.Option`.** Comes back as a real `Option`, equal to the one written, but it's stored as Effect's internal form: a map with `_op`, `_tag`, `value` and a `~effect/Option` marker. `Schema.OptionFromNullOr` stores the value or `null`, and comes back as an `Option` too. On an aggregate, `Schema.OptionFromOptional` and `Schema.OptionFromOptionalKey` read back, but `create` takes the value as it's stored, not an `Option`, and `update` refuses them, so use `Schema.OptionFromNullOr` there.
- **`Schema.BigInt` next to a member that takes a number, on an entity or an aggregate.** A stream, a snapshot and an outbox refuse this. A stored number reads back as a number below 2^53 and as a `bigint` past it, and each member gets its try before a number is lifted to a `bigint`. So `Schema.Union([Schema.Number, Schema.BigInt])`, in either order, reads `5n` back as the number `5`, and a value past 2^53 as a `bigint`. With `Schema.Literal(5)` or a checked number in place of `Schema.Number`, only what that member takes changes: `6n` stays `6n`. `Schema.Union([Schema.Struct({ v: Schema.BigInt }), Schema.Struct({ v: Schema.Number })])` reads `{ v: 5n }` as `{ v: 5 }`, and a `Schema.DateFromMillis` member reads `5n` as a date. To keep them apart, use `Schema.BigIntFromString`, which is stored as a string. A member that can't hold a number doesn't compete: `Schema.NullOr(Schema.BigInt)`, `Schema.Union([Schema.String, Schema.BigInt])` and `Schema.Union([Schema.Number, Schema.Struct({ b: Schema.BigInt })])` come back as written. Under `Schema.optionalKey`, a first `Schema.BigInt` takes the number, so `Schema.optionalKey(Schema.Union([Schema.BigInt, Schema.Number]))` reads `5` back as `5n`.
- **`Schema.DateTimeUtc` after another member of a `Schema.optionalKey` union.** Only the first member is written in its stored form, so `Schema.optionalKey(Schema.Union([Schema.String, Schema.DateTimeUtc]))` stores a date as Effect's internal form, a map, and a string that looks like a date reads back as that string. It comes back as a real `DateTime`, equal to the one written. Declared first, or under `Schema.optional`, it's stored as a string, and the text of a date reads back as a date. To tell them apart, use `Schema.DateTimeUtcFromString` with a string that can't look like a date.
- **`Schema.DateTimeUtc` beneath a decoding default.** In a struct or a record under `Schema.withDecodingDefault` or `Schema.withDecodingDefaultKey`, and on an entity in a `Schema.NullOr` too, it's stored as Effect's internal form, a map, as what's stored there can't be changed without moving rows. It comes back as a real `DateTime`, equal to the one written. Use `Schema.DateTimeUtcFromString`, which is stored as a string.
- **`Schema.DateTimeUtc` and `Schema.DateTimeZoned` on a stream, a snapshot and an outbox.** Stored as Effect's internal form, a map, or its JSON under `DynamoModel.Packed`. Every read gives back a real `DateTime` with a real zone, equal to the one written, at any depth and under `Schema.Option`. A union is read by trying its members, so a struct listed first that takes the same fields keeps them, and a `Schema.Unknown` field reads back the map, since nothing there declares a date. Use `Schema.DateTimeUtcFromString`, which is stored as a string.
- **`Schema.BigDecimal`.** Below 2^53 it reads back with a `number` where a `bigint` belongs, so `BigDecimal.format` works and `BigDecimal.sum` throws. Above that it works. A value that's been normalised, which `BigDecimal.equals` does to it, holds a reference to itself, so `put` dies with a stack overflow and writes nothing. Use `Schema.BigDecimalFromString`, which has neither problem.
- **`Schema.HashSet`.** A non-empty one is refused at write (`EDD-9124`), naming the field, with nothing written, and only an empty one reads back. Use `Schema.ReadonlySet`.
- **`Schema.SemVer`, `Schema.TimeZone`, `Schema.Cookie`, the IP, MAC, socket and DNS record types, and the crypto keys.** Read back as plain objects with no prototype. `Schema.DateTimeUtc` and `Schema.DateTimeZoned` do too under a transformation over a container on an entity or an aggregate, as they don't elsewhere there. Prefer a form stored as a string, such as `Schema.SemVerFromString` or `Schema.DateTimeUtcFromString`.

Under `DynamoModel.Packed`, nothing here can leave a row you can't read. A value JSON can't represent fails the write with a `ValidationError` naming the path, and nothing is written.

#### Declarations of your own

A `Schema.instanceOf` over a class of your own can't be judged when the model loads: it has the same AST as a duck-typed `Schema.declare`, and only the second reads back. So the value is judged when it's written. It goes through the real marshaller and back, which is what a read would hand the schema, and if that doesn't decode, the write fails with a `ValidationError` (`EDD-9126`) and nothing is written. Use a `Schema.Class`, or decode the class from something that's stored, with `Schema.decodeTo`.

That covers every write that stores the value: `put`, `create`, `upsert`, `update` and `patch` with their path operations, a time-series `.append()`, `Batch.write`, `Transaction.transactWrite`, an aggregate's `create` and `update`, and on a stream `append`, `commandHandler`, `additionalItems`, `writeSnapshot`, inline snapshots, metadata and outbox effects. What's judged is whether it reads back, not whether it's an instance, so a duck-typed `Schema.declare` that takes what's stored keeps writing, and so does a union with another member that takes the map. A model without a declaration of your own pays only for a scan when it loads, and its requests don't change.

Rows an earlier release stored aren't touched. They stay as they are and still fail on read.

#### Container checks

A `.check()` refinement on an array, a struct or a class built over a checked struct is enforced on every write when the container holds a date or another value the library substitutes, for example `Schema.Array(Schema.DateTimeUtc).check(Schema.isMaxLength(1))`. That covers `put`, `create`, `update` and `.set()`, path operations, `.append()`, Batch and Transaction. A violating value fails with a `ValidationError`. Earlier versions silently dropped these checks, so rows that break them may already exist. Reads don't enforce them, so those rows still read, and the next write that sets the field to a valid value repairs them.

:::caution[Upgrading from 1.22.0 or earlier]
Earlier versions stopped at unions, records and tuples, so a self date inside one was stored as a marshalled `DateTime` map (`{ epochMilliseconds, "~effect/DateTime", _tag: "Utc" }`). Those rows still read back, as real `DateTime` values, and are rewritten in wire form when the attribute is next written. Keys are not affected.

The new stored form can't be read by 1.22.0. A 1.22.0 reader fails with `Expected DateTime.Utc` on a self date written as a string inside a `NullOr`, `Record` or `Tuple`. Inside a union with a string member, it reads the date back as a plain string. **Upgrade every reader before any writer, and don't roll back past this version** once new rows are written.

Until old rows are rewritten, the attribute is a map (`M`) on old rows and a string or number on new ones. A filter on it can therefore match the two differently, and DynamoDB Streams consumers see the type change.
:::

### Storage Layouts

Two `storedAs` values change how a structured field is laid out on the item, rather than how one value is encoded:

| `storedAs` | Valid on | Stored as | Use when |
|---|---|---|---|
| *(omitted)* | any field | a native map (`M`) or list (`L`) | the default; DynamoDB can address paths inside it |
| `DynamoModel.SparseMap()` | a `Schema.Record` | one top-level attribute per entry (`metrics#2026-04`) | each key is updated, counted or checked on its own. See [Sparse Maps](/effect-dynamodb/guides/sparse-maps/). |
| `DynamoModel.Packed({ format: "json", compression? })` | a struct, class, array, record or union of them | one JSON string (`S`), or compressed binary (`B`) at or above a threshold | the value is read and written whole, and you want faster bulk reads or fewer write units. See [Packed Storage](/effect-dynamodb/guides/packed-storage/). |

```typescript
const OrderModel = DynamoModel.configure(Order, {
  lines: { storedAs: DynamoModel.Packed({ format: "json" }) },
  details: {
    field: "d",
    storedAs: DynamoModel.Packed({ format: "json", compression: { codec: "zstd" } }),
  },
})
```

A packed field can't be a key or index composite, a unique-constraint field or a ref, and DynamoDB can't see inside it. Conditions and filters only test whether it exists, and updates replace it whole. Readers go by each item's stored form, so turning packing on or off needs no data rewrite.

### Immutable Fields

Mark fields as read-only after creation. Immutable fields are present in `Entity.Input` (you provide them on creation) and `Entity.Record` (you can read them), but excluded from `Entity.Update`:

```typescript
const EmployeeModel = DynamoModel.configure(Employee, {
  createdBy: { immutable: true },
})
// Entity.Update<E> will not include createdBy
```

Primary key composite attributes are inherently immutable — you don't need to mark them.

An update may restate an immutable field with its current value, so spreading a whole record into `.set()` works. A `.set()` with a different value fails with a `ValidationError`, as does a `.set()` that changes a primary-key composite. Earlier versions silently ignored the latter. Clearing either kind of field fails the same way, as does any other update operation naming it.

### Identifier and Ref

`identifier` and `ref` support aggregate and reference resolution. See [Aggregates](/effect-dynamodb/guides/aggregates/) for details.

```typescript
const EmployeeModel = DynamoModel.configure(Employee, {
  employeeId: { identifier: true },  // identity field for ref resolution
})
```

### Combining Options

Options compose freely on a single field:

```typescript
const EmployeeModel = DynamoModel.configure(Employee, {
  createdBy:   { immutable: true },
  hireDate:    { field: "hd", storedAs: DynamoModel.DateEpochSeconds },
  displayName: { field: "dn" },
  employeeId:  { identifier: true },
})
```

## Namespacing Your Application

`DynamoSchema` defines the application-level namespace that prefixes every generated key.

```typescript region="schema" example="guide-modeling.ts"
const AppSchema = DynamoSchema.make({
  name: "projmgmt",
  version: 1,
  casing: "lowercase",
})
```

### Properties

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | *required* | Application name, used as key prefix |
| `version` | `number` | *required* | Schema version for migration support |
| `casing` | `"lowercase" \| "uppercase" \| "preserve"` | `"lowercase"` | Casing for the whole composed key — labels **and composite values** (see [Casing](#casing)) |

### Why Schema Versioning?

Schema versioning enables safe migrations. Items with `$projmgmt#v1#...` keys are completely isolated from `$projmgmt#v2#...` keys:

```
$projmgmt#v1#employee#employeeid_emp-alice    ← current production
$projmgmt#v2#employee#employeeid_emp-alice    ← new schema version (migration in progress)
```

This supports blue/green deployments and gradual rollback.

### Why Application Namespace?

Multiple applications can share the same DynamoDB table with complete key isolation:

```
$projmgmt#v1#employee#employeeid_emp-alice    ← Project Management app
$billing#v1#customer#customerid_cust-alice    ← Billing app
```

### Casing

Casing applies uniformly across the **entire generated key**: schema name, version prefix, entity type, collection name, composite attribute names, **and composite attribute values**. `"Male"` and `"male"` produce identical keys — this is important for case-insensitive lookups. The original attribute casing is preserved on the stored attribute value itself; only the composed key string is cased.

```typescript
// With casing: "lowercase", entityType: "Employee", composite value "Emp-Alice"
// Key:             $projmgmt#v1#employee#employeeid_emp-alice
// Stored attribute: employeeId = "Emp-Alice"  (original casing preserved)
```

:::caution[Ids that differ only by case share a key]
Under the default `"lowercase"`, `"Dev-A"` and `"dev-a"` compose the **same key**: a put for one overwrites the other and a get for one returns the other, with no error. If a composite holds an id that must stay distinct by case — device ids, tenant ids, external references — use `casing: "preserve"`.
:::

:::danger[Casing is part of the storage format]
Choose `casing` before a table holds data. Changing it later moves every composed key, so existing items are no longer found. Switching on a populated table needs a table rewrite.
:::

An index can override the schema's casing with its own `casing`, and an event stream with `makeStream({ casing })` — see [Casing Resolution](/effect-dynamodb/guides/indexes/#casing-resolution).

A few fixed markers inside keys are **not** cased, under any setting: the `v` in the version prefix (`$APP#v1`), the version-snapshot `#v#` and soft-delete `#deleted#` infixes, and the `_1` in event and isolated sort keys. Under `"uppercase"` a version snapshot key is `$APP#v1#EMPLOYEE#v#0000003`. The time-series `#e#` infix is the exception — it follows the casing (`#E#` under `"uppercase"`). These are fixed because they are already stored; they will not change.

## Declaring the Physical Table

`Table` declares the physical DynamoDB table and registers the entities that share it.

```typescript region="table" example="guide-modeling.ts"
const MainTable = Table.make({ schema: AppSchema, entities: { Employees } })
```

The Table owns "what exists physically." The Entity owns "how I use it." Multiple entities can share the same table (single-table design).

### Properties

| Property | Type | Description |
|----------|------|-------------|
| `schema` | `DynamoSchema` | Application schema for key prefixing |
| `entities` | `Record<string, Entity>` | Named entities registered on this table |
| `aggregates` | `Record<string, Aggregate>` | Named aggregates registered on this table (optional) |

The physical table name is provided at runtime via `MainTable.layer({ name: "ProjectManagement" })`. See [Advanced](/effect-dynamodb/guides/advanced/) for configuration details.

## Binding Models to Storage

The Entity binds a model to a table. It defines:
- **Indexes** — How model attributes compose into DynamoDB keys
- **System fields** — Timestamps, versioning, soft delete
- **Unique constraints** — Field-level uniqueness enforcement
- **Collections** — Cross-entity query groups

```typescript region="entity" example="guide-modeling.ts"
const Employees = Entity.make({
  model: EmployeeModel,
  entityType: "Employee",
  primaryKey: {
    pk: { field: "pk", composite: ["employeeId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    byTenant: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["tenantId"] },
      sk: { field: "gsi1sk", composite: ["department", "hireDate"] },
      type: "clustered",
    },
    byEmail: {
      name: "gsi2",
      pk: { field: "gsi2pk", composite: ["email"] },
      sk: { field: "gsi2sk", composite: [] },
    },
  },
  unique: { email: ["email"] },
  timestamps: true,
  versioned: { retain: true, ttl: Duration.days(90) },
  softDelete: { ttl: Duration.days(30) },
})
```

### Primary Key Definition

The `primaryKey` defines how the entity's partition key and sort key are composed from model attributes:

```typescript
primaryKey: {
  pk: {
    field: "pk",               // Physical DynamoDB attribute name
    composite: ["employeeId"], // Model attributes that compose the partition key
  },
  sk: {
    field: "sk",
    composite: [],             // Empty = one item per partition key value
  },
}
```

The `composite` array is an ordered list of model attribute names. The system generates the key value automatically: `$projmgmt#v1#employee#employeeid_emp-alice`.

GSI access patterns are defined on the entity via the `indexes` property. Collections are auto-discovered from entities sharing the same `collection` name on a GSI. See [Indexes & Collections](/effect-dynamodb/guides/indexes/) for full details.

### System Fields

Configure automatic metadata at the Entity level:

```typescript
// Timestamps
timestamps: true
timestamps: { created: "registeredAt", updated: "modifiedAt" }

// Versioning
versioned: true
versioned: { retain: true }
versioned: { field: "revision", retain: true, ttl: Duration.days(90) }

// Soft delete
softDelete: true
softDelete: { ttl: Duration.days(30) }
softDelete: { ttl: Duration.days(30), preserveUnique: true }
```

See [Lifecycle](/effect-dynamodb/guides/lifecycle/) for details on versioning and soft delete.

An index or a primary key can be composed from `createdAt`, and an index from `updatedAt`: see [Keys over values the library stamps](/effect-dynamodb/guides/index-policy/#keys-over-values-the-library-stamps). A model field named like a timestamp is stamped if it's a date, optional or not, and otherwise stays yours. To store the version under another name use `versioned: { field }`: a `configure` `field:` rename of it is refused (`EDD-9122`), while `createdAt` and `updatedAt` may be renamed either way.

### Generated IDs

Opt into auto-generated UUID primary keys with `generatedId`. The named field is filled with a cryptographically-secure UUID at write time **when the caller omits it** — a caller-supplied value is always respected. The field MUST exist in the model AND participate in the primary key (pk or sk composite); violating either throws `EDD-9008` at `make()` time.

```typescript region="entity" example="generated-id.ts"
const Widgets = Entity.make({
  model: Widget,
  entityType: "Widget",
  primaryKey: {
    pk: { field: "pk", composite: ["widgetId"] },
    sk: { field: "sk", composite: [] },
  },
  indexes: {
    byOwner: {
      name: "gsi1",
      pk: { field: "gsi1pk", composite: ["owner"] },
      sk: { field: "gsi1sk", composite: ["widgetId"] },
    },
  },
  // Auto-generate `widgetId` with a UUIDv4 when the caller omits it.
  generatedId: { field: "widgetId" },
})
```

`version` defaults to `"v4"` (random); pass `version: "v7"` for time-ordered ids, which sort in the order one client generated them. On `put`/`create`/`upsert` the field is optional in the input — omit it to auto-generate, or supply your own to override:

```typescript region="put" example="generated-id.ts"
// No `widgetId` supplied — the library fills it from the SecureRandom service.
const created = yield* db.entities.Widgets.put({
  owner: "alice",
  label: "Sprocket",
})
// created.widgetId is a freshly-generated UUID
```

The id is sourced from the bundled [`SecureRandom`](https://github.com/Effect-TS/effect) service from `effect/crypto`. `DynamoClient.make` provides a default `globalThis.crypto`-backed implementation (no extra dependency), so bound `put` stays `R = never` — your program needs no `SecureRandom` layer. Pass `DynamoClient.make({ crypto })` to override it with a `SecureRandom` service of your own, built with `SecureRandom.make` or read from a platform layer.

### Decoding Defaults

A field declared with `Schema.withDecodingDefault` can be left out of a `put`. The returned record and every later read carry the default. Whether the default is stored depends on the field:

- **A primary-key or index composite** is stored with its default, and its keys are composed from it, so the item is indexed under the value it reads back with. A `.remove()` of such a field stores the default again and keeps the item indexed under it.
- **Any other field** is not stored. The default is applied on read.

An `upsert` that omits a defaulted index composite reads the item first: it stores the default only when it creates the item, and otherwise keeps the stored value.

A default never creates a unique-constraint sentinel. A defaulted unique field that is also an index composite is listed in a hidden string-set attribute, `__edd_d__`, until a write supplies its value. See [Defaults and Unique Constraints](/effect-dynamodb/guides/data-integrity/#defaults-and-unique-constraints).

## Derived Types

Seven types are automatically derived from your Model + Table + Entity declarations. No manual type maintenance required.

```typescript
// Given Employees with timestamps: true, versioned: true

Entity.Model<typeof Employees>
// { employeeId, tenantId, email, displayName, department, hireDate, createdBy }

Entity.Record<typeof Employees>
// Model + { version, createdAt, updatedAt }

Entity.Input<typeof Employees>
// { employeeId, tenantId, email, displayName, department, hireDate, createdBy }

Entity.Update<typeof Employees>
// { email?, displayName?, department?, hireDate? }
// (employeeId, tenantId excluded — primary key composites)
// (createdBy excluded — immutable: true in DynamoModel.configure)

Entity.Key<typeof Employees>
// { employeeId }

Entity.Item<typeof Employees>
// All physical DynamoDB attributes (pk, sk, gsi1pk, gsi1sk, __edd_e__, ...)

Entity.Marshalled<typeof Employees>
// DynamoDB AttributeValue format ({ pk: { S: "..." }, ... })
```

### Type Hierarchy

```
Entity.Model      ← Pure domain object
    ↓ + system fields (version, timestamps)
Entity.Record     ← What the entity returns
    ↓ + key attributes (pk, sk, gsi1pk, ...)
Entity.Item       ← Full DynamoDB item (unmarshalled)
    ↓ + DynamoDB encoding
Entity.Marshalled ← DynamoDB AttributeValue format
```

`Entity.Record` extends `Entity.Model` — anywhere that accepts `Employee` also accepts a Record.

### Schema Accessors

For consuming raw DynamoDB data (e.g., DynamoDB Streams):

```typescript
// Decode an unmarshalled DynamoDB item to a Record
Entity.itemSchema(Employees)

// Decode a marshalled (AttributeValue) DynamoDB item to a Record
Entity.decodeMarshalledItem(Employees, marshalledItem)
```

See [DynamoDB Streams](/effect-dynamodb/guides/streams/) for usage.
