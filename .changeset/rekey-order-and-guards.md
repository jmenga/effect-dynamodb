`rekey`'s report, and the rows one run leaves, no longer depend on the order its visits meet the rows in. Each row, aggregate partition, event stream and unique reservation is judged once a run, by whichever visit reaches it first (the scan, or the move of a row it's in the way of), and counted once whoever judged it. An item's live row and its tombstones, which all name the item's key, are told apart through delete and re-create cycles whose keys chain across the settings: up to 1.40.0 a tombstone without `preserveUnique` could take the sentinel the live row held, so the live value could be taken again, and with `preserveUnique` a chain could end in `bothKeys` or need several runs, depending on the order. A run no longer meets its own writes: the scan passes a row the run put, and `scanned` counts each row stored when the run met it once, so a row moved before its segment was scanned is still counted and a row written ahead of the scan isn't counted again, or as `unchanged`. Aggregates sharing a partition are placed by which row is stored at a key, not by which keys are held, so three whose escaped sort keys chain all move in one run, whatever the order. A dry run sees what its earlier decisions would have written, so it reports what the run does, from a table a run cut short too: for an event stream already part-moved it plans only the copies the run sends, and judges the rows left under the old key as the run does, where 1.40.0 reported moved a stream whose left rows the run refuses as `bothKeys`. Up to 1.40.0 a chain could report `moved: 1` plus `unchanged: 1` where the dry run said `moved: 2`, a sentinel cycle across constraints `sentinelsMoved: 0` after moving all four, and three segments `scanned: 3` against a dry run's 4. Dense chains now finish in one run: a sentinel in a moving row's way moves out by itself, naming its row where it is, instead of with its row, so a row and another item whose key and sentinel chain the other way no longer wait on each other. Up to 1.40.0 about one dense random table in ten ended with conflicts no rerun cleared. A tombstone without `preserveUnique` no longer points a live item's sentinel at itself where its item's key under the other text is that live item's, and under `preserveUnique` a sentinel naming an item is attributed to the row of it whose value it holds. Over a table with nothing to move, a run without `reservations` sends exactly the requests 1.40.0 sent.

What a run remembers to do this is bounded, and costs nothing for a row it doesn't move, write or report: a table of rows already under their current keys, or of another application's rows, is scanned in flat memory. Each entry is a 128-bit digest with a few flags, never key text or a row (a real run keeps no image of a row it moved, but the last 64 it put; a dry run keeps the rows it plans to put, which its reads see). The new `journalCapacity` option bounds the entries (default 1,000,000, about 115 MiB when full; moving a row costs about five, an aggregate's row one, as does a unique sentinel under `preserveUnique` whose value's key text differs between the settings), and the new `report.journal` says how many the run kept and whether it ran out. Past the capacity the run carries on, every write as guarded as ever, and `report.journal.inexact` names the counts that may be off. 1.40.0 kept the text of two claims for every live entity item and of every aggregate partition, unbounded, which a `Set`'s limit of 2^24 entries stops near 8.4 million entity items.

A dry run with `repairIndexKeys` counts no key `repaired`: it writes none. 1.40.0 counted the keys it would have written.

With the new `reservations: true` option, `rekey` judges unique-constraint sentinels no row holds and counts them in the new `report.reservations` (`orphaned`, `undecided`, an entry for each), writing nothing; under `preserveUnique` that costs a query for an item's tombstones where its sentinel names an item that is gone or holds another value. Without the option a run judges none and sends exactly the requests 1.40.0 sent: such a sentinel is counted in `skipped.unrecognizedKey`, or, one naming a tombstone, not at all, as in 1.40.0. `rekey({ releaseOrphanedReservations: true, writesStopped: true })` also deletes the orphaned ones, so their values can be taken again: the reservations a delete, update or soft delete on 1.39 or earlier left for a unique value that read back otherwise than `put` keyed it, such as a `Schema.BigInt`. Releasing is a maintenance step, run with every writer to the table stopped, a second run releasing reservations included: without `writesStopped: true` the run fails with a `ValidationError` before anything is read. Each release is one transaction, conditioned on the sentinel and on the row it names as read, so a write that claims the value first wins even if the promise is broken: read again held or deleted, the sentinel is left and counted `raced`, apart from `orphaned`; changed under it twice, `skipped`. A move whose unique value's current key holds such a reservation is `taken`, as in 1.40.0, unless the option releases it first.

Two writes a move used to lose now cancel it, so the row moves with them: a `reembed` landing on a versioned item with a vector index (the move also holds its vector attributes as read), and a write adding a field of an aggregate node declared as an annotated class or a union (the move holds each property the node's schema can store still absent). What no condition on the move can see is counted in the new `report.guardGaps`, with writes going on: `stamp` (a wide row guarded on its `updatedAt`), `sparse` (an item with a sparse map, guarded whole) and `strongest` (a row of a part-moved aggregate or stream). With `writesStopped: true` nothing is counted. Counting reads and writes nothing.

`reembed` no longer overwrites a write that lands between its read of an item and its rewrite. Each rewrite is conditioned on the item's source fields and partition composites as `reembed` read them, so an update that changed the text (and embedded it) or moved the item's partition in between cancels it, and `reembed` skips the item: neither retried nor counted in the number it returns. Up to 1.40.0 the condition was `attribute_exists` alone, and such an update was left with the old text's vector or partition.
