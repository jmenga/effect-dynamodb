Effect's own value types: packed storage, key composites, and two fixes found on the way.

**If you ran 1.38.0, 1.39.0 or 1.40.0 with `effect` 4.1.3, and a key or a unique constraint holds a zoned date or a named zone whose id the runtime resolves to a different id (an alias such as `Etc/UTC`, `GMT` or `US/Pacific`, or a renamed zone such as `Asia/Kolkata`), those rows are keyed by the name the zone was given, and 1.41.0 keys it by the name the runtime resolves it to, the key 1.40.0 composed on `effect` 4.1.2. Until `rekey` moves them, such a row is not found: `get` and the index accessors miss it, a `delete` by key reports success and leaves it (one that reads the item first, on an entity with a unique constraint or soft delete, reports `ItemNotFound`), and the unique value it holds isn't enforced. Run `db.tables.<Table>.rekey({ repairIndexKeys: true })` before the table serves traffic on 1.41.0: it moves those rows, their snapshots, tombstones, time-series events, unique sentinels and aggregate rows, and rewrites their index keys. The resolved name is what the runtime's `Intl` makes of a zone's name, as it has been since 1.38.0, so it depends on the runtime's time zone data: a runtime that resolves a zone to another name keys it under another text.**

- **Packed storage takes Effect's instances.** A packed write refused a real `Duration`, `BigDecimal`, time zone, cookie or cookie jar, `UrlParams`, `SemVer` / `SemVerRange`, address, network, interface or host, DNS record, `Option` or `Result` ("an instance of Object"), in an entity's packed field, an aggregate edge's, event data and an inline snapshot alike, though a native attribute stores each as a map and reads it back. Each is now packed as that map, keys in the order DynamoDB Local hands it back, as a real `DateTime` already was: exactly the bytes 1.40.0 packed for the map a native read hands back for it. Where the schema declares one it reads back as the instance, which writes back as the same bytes; in a `Schema.Unknown` it reads back as the map, as it does natively. What JSON can't hold is still refused at its path: a `MacAddress`'s or a TLSA record's bytes, a `BigDecimal` or a `Duration` past 2^53, and a bigint, a `Date` or bytes inside an `Option` or a `Result`. Nothing 1.40.0 packed changes by a byte.
- **Effect's look-alikes as key composites.** A `Duration`, `BigDecimal`, time zone, `UrlParams`, `SemVer` / `SemVerRange`, address or DNS record composite, or an `Option` or `Result` holding one, was refused with `EDD-9128` (a row read back composed `[object Object]`). A key read back from a row now composes from the instance it stands for, so it's the key `put` wrote, and rows 1.39.0 wrote under such a key are found, restored, updated and released as before. `restore` of a 1.39.0 tombstone lands under the key `put` wrote, an aggregate `update` of such a root works, and `rekey` moves none of these rows. An item 1.39.0's or 1.40.0's `restore` put back under `[object object]`, where `get` didn't find it, is moved by `rekey` to the key `put` wrote, with its index keys; the unique sentinel that `restore` wrote there is left and counted `unrecognizedKey`, and the value stays reserved by the one `put` wrote, which moves with the item when `escapeKeys` is turned on. A `Cookie` or `Cookies` composite stays refused.
- **A named time zone is stored the same on Effect 4.1.2 and 4.1.3.** Effect 4.1.3 gave a named zone a `resolvedId` and kept the name it was made from (`Etc/UTC`, where 4.1.2 resolved it to `UTC`), so on 4.1.3 every stored named zone, native or packed, gained an entry, and a zone made from an alias was stored, keyed and written as ISO text under another name. A named zone is now stored, keyed and compared as 1.40.0 stored it on 4.1.2, whichever Effect is installed, however it's reached (in a date, an `Option`, a list, an untyped field, behind a getter) and whether it was made or read: two zones Effect holds equal have one key text, unique sentinel and ISO text. A zone already stored with a `resolvedId` reads back as the same zone on either Effect (where no schema types it, as the map it is, as 4.1.2's map always has), and is written in 4.1.2's form the next time the item is written; an `update` that doesn't touch the field leaves it as it is. Effect's own string codecs (`Schema.TimeZoneNamedFromString`, `Schema.TimeZoneFromString`, `Schema.DateTimeZonedFromString`) are Effect's, and still write the name the zone was made from on 4.1.3: the stored string for an alias zone differs after an upgrade from Effect 4.1.2 to 4.1.3 (`Etc/UTC` where 4.1.2 wrote `UTC`). Reads take both, and every key composed from such a field (a sort key, an index key, a unique sentinel, a time-series event's key, a `history().where()` bound) names the zone as 4.1.2 did, on either Effect. An equality condition or filter on that attribute compares the stored string, so it matches only the form the row holds.
- **A value DynamoDB doesn't store, in an untyped field, is refused at write.** In a `Schema.Unknown` or `Schema.Any` position, at any depth, 1.40.0 wrote a `Date` as an empty map and read it back as `{}`, with no error; a `RegExp`, a `WeakMap`, `WeakSet`, `WeakRef`, `FinalizationRegistry` or `Promise` the same; an `Error`'s message and cause were dropped, a `Redacted` was stored as its marker alone, a `Map`'s non-string keys came back as text, and an `ArrayBuffer` or `DataView` as empty bytes. Each is now a `ValidationError` naming the path (`EDD-9161`), with nothing written, on every write path: `put`, `create`, `upsert`, an update's `.set` and path operations, `transactWrite`, `Batch.write`, a time-series `append`, an aggregate's `create` and `update`, an event stream's events, metadata and snapshot, and a projection's outbox. A packed field already refused each, and now says so in the same words, through the same function. Rows already holding `{}` read as `{}`, a list holding `undefined` still closes up as it always has, and a model without an untyped position pays nothing.
- **An Effect `Chunk` in an untyped field** died with a stack overflow on every write path, as its empty end holds itself. It's now the `ValidationError` a `HashSet` there gets (`EDD-9124`), naming where it holds itself, with nothing written. Every other Effect collection and data type in an untyped field (`HashMap`, the mutable ones, `Trie`, `Graph`, `Option`, `Result`, `Exit`, `Cause`, `Duration`, `BigDecimal`, `DateTime`, `Redacted`, a `Data` class or tagged class, a `Schema.Class` instance) is either refused with a `ValidationError` or stored as the map of its properties and read back as that map, natively and packed.
- **An object as a key composite is refused at write.** A struct, a `Data` class or an instance of a class of your own without a `toString` composed the key text `[object Object]`, the same for every value, so items written with different values shared one key and overwrote each other. A write composing a key from one (`put`, `create`, `upsert`, an update recomposing an index key, `append`, a transaction's or a batch's put) is now a `ValidationError` naming the field (`EDD-9162`), with nothing written. An aggregate's write is refused the same way: `create` composing its partition key, `collection` sort key, `list` keys or a row's discriminator from such an object, and `update` composing any of them but the partition key, which it composes from the key it's given (up to 1.40.0 a second aggregate with another such partition value failed `create` as already there and `get` given it returned the first, aggregates with different list values shared one list key, and a sub-aggregate bound to such a discriminator was never read back). An `update` leaving the value as it read it writes the row where it is. A `get`, a `delete`, a `list` or a query given such a value still composes that text, so rows already written under it stay reachable. A value with a key form (a `Duration`, a list, a class with a `toString`) is untouched.
- **A history row whose sort key text holds a line break** (a sort key composite holding one, with `escapeKeys` off) was taken for an item: a scan or a primary-key query returned the snapshot or tombstone as an item, and `rekey` reported it as an unrecognised key. It's recognised as history now.
- **An aggregate `update` holding a `BigDecimal` that was compared or hashed** died with a defect and wrote nothing: comparing the rows to write with the rows read followed the decimal's cached normalized form, which holds itself, until the stack ran out. It now compares the decimal as it's stored, so an equal decimal writes nothing and another one is written as a fresh decimal of its value.
