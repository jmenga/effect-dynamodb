Projections sharing an outbox (#237).

**Outbox items gain an attribute, `__edd_rm__`, naming the read model they were written for** (a tag of its key template; part of no key, and a 1.40.0 drainer delivers and deletes a tagged item as any other).

**Every outbox item's `Put` gains a condition: `ConditionExpression: "attribute_not_exists(#pk) OR #rm = :rm"`, with `ExpressionAttributeNames: { "#pk": <the outbox table's partition key attribute>, "#rm": "__edd_rm__" }` and `ExpressionAttributeValues: { ":rm": { S: <the read model's tag> } }`. Nothing else in the request changes, and nothing is read first.** Two read models whose row keys are the same text (one keyed by `shop` = `north#branch_b1`, the other by `shop` = `north` then `branch` = `b1`, `escapeKeys` off) writing at one revision put their outbox items at one key, and on 1.39.0 and 1.40.0 the second replaced the first, whose effect was never delivered. The condition turns that into a cancelled transaction, read by position: the row's own condition failing is a lost race, as before; an item's alone is a key another read model's item holds, and that item is written beside it, at its key followed by `#` and the writer's tag, in a second transaction (one more request, only there). Both effects are delivered, each by its own drainer, in order. An item written before 1.41.0 carries no tag and may be either read model's, so it is never replaced: the new one goes beside it. A read model's own tagged item at the key (its revision starting again after its row was deleted outside the projection) is replaced, as on 1.40.0. Should the key beside be held too, by anything but the writer's own item, the write fails with a `ValidationError` (`EDD-9145`) naming both read models, the row and the key, with DynamoDB's error as its cause, and nothing is written. `escapeKeys: true` keeps such read models' keys apart.

`drainPending` on an outbox index shared by read models of one entity type drains only its own read model's items, and leaves the others' unclaimed for their drainers (1.39.0 and 1.40.0 claimed them and failed, leaving them claimed). So do `drain` and `deliver` where two read models' row keys are the same text (one keyed by `shop` = `north#branch_b1`, the other by `shop` = `north` then `branch` = `b1`): each item is judged as it comes to the head of the row. The exception is an item written before 1.41.0, which carries no tag, at a key both read models can write (one keyed by `shop`, the other by `shop` then `branch`, a shop holding `#`): both drainers drain it, as on 1.40.0. Those drain away after an upgrade. `EventStore.processBatch` runs a projection object built by hand, carrying the routes but not the read model, as 1.39.0 did, instead of dying with a `TypeError`. A projection whose row key holds a bigint (a `Schema.BigInt` composite) no longer dies with a `TypeError` in `applyBatch`, `rebuild` or a multi-source projection's `applyBatch` (as on 1.40.0): grouping events by row now tells a bigint apart from a number or a string of its digits, and leaves every other key as before. The shared outbox key space check (`EDD-9134`) no longer refuses two layouts 1.39.0 handled: at bind, a date composite the library encodes (a `DynamoModel` date schema, or `Schema.DateTimeUtc`, `Schema.Date` or `Schema.DateTimeZoned`) is taken as the text its encoding writes (an ISO date or instant, or a number); a date with a codec of its own is any text, as before, so a read model keyed by a date beside one keyed by a label the date's text can't spell binds; and the outbox table's `rekey` compares a member keyed as a read model by the kind of each composite, so a literal union where the read model has a string moves its items where the read model reads them.

The outbox table's `rekey` decides whose an outbox item is item by item, by the same function as `drainPending`, instead of refusing read models whose items it could read as each other's (`EDD-9134`, which 1.40.0 added to `rekey`). An item naming its read model, or one only one read model can have written, or one every possible owner would move to the same key, moves with no extra request. An item written before 1.41.0 that two read models would move to different keys (one keyed by `shop`, the other by `shop` then `branch`, a shop holding `#`) moves by the read model whose own row is at the row it names, read from each read model's table. When no read model has that row, or a row tombstone or more than one row is there, or a read model's table isn't provided, the item is left where it is, counted in `skipped.ambiguousOwner` and listed in the report's new `ambiguous` field with the reason; a rerun leaves it again. `rekey` still refuses, as on 1.40.0, read models whose items overwrite each other with ordinary values (no tag or row can tell those apart), and a member of the outbox table whose items would overwrite a read model's and whose primary key isn't the read model's.
