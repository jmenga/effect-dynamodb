A `.select()` naming a sparse map field returns the map. A `ProjectionExpression` can't name a map's entries (`<prefix>#<key>`), so the select projected the field's own name, which no row holds, and the map came back absent, on an entity's queries and scans and on a collection, as on 1.39.0. A select of the whole map now sends its request without a projection, rebuilds the map from each row's entries as a read does, and hands back every other path selected as its projection did, however it was spelled (a stored name, an entry's attribute, a key attribute), without unpacking, decompressing or checking anything the select doesn't name. It consumes the capacity a projected read consumes (DynamoDB charges by the items read, not what it returns) and returns every attribute of each row. A select of one entry (`t.f.entry("k")`, or `t.f.k`) projects the attribute the entry is stored under and returns the map trimmed to that entry, `{ f: { k } }`, with a list below it as DynamoDB projects it (`t.f.k.at(2)` of `[10, 20, 30]` gives `[30]`). For a map a `field:` rename stores whole it also projects that attribute whole, and returns what a read returns: through 1.40.0 such a select projected `sr.k`, which returned nothing from a row an update wrote. Two selected paths that overlap, a projection DynamoDB refuses, come back once beside the map. A select naming no sparse map sends the projection it always sent, and `.filterBy()` after any select is still refused (`EDD-9054`).

A model field whose own name holds `#` and is stored under another name (`field:`) is named by that name in path writes and conditions, as filters and projections already named it. A path write and a condition took such a first segment as a literal attribute name, so `pathSet(["a#b"])` on a field `a#b` stored as `stored` set a top-level `a#b` that no read looks at, and a condition on `t["a#b"]` tested an attribute `put` never stores, failing whatever the row held, as on 1.39.0. The refusal of a `pathRemove` of a sparse map's entry asks about the attribute the path names after that rename, as `.remove()`'s does, so a field named like an entry (`data#x#y`, stored as `counter`) is removed where it's stored. 1.39.0 removed the entry `x#y` instead, and 1.40.0 refused the removal. An entry named through its map (`.entry("b")`, `.set({ g: { b } })`, `removeEntries`, `clearMap`) is still the entry's attribute when a field carries the same name: only a bare segment the caller spells like an entry names the field. A path write on segments `.entry()` built, on an entity whose unique constraint names such a field, wrote the field on 1.40.0; it writes the entry.

A `pathRemove` that leaves a row no read can decode is refused in more places, with a `ValidationError` and nothing sent, and each was sent on 1.39.0 and 1.40.0:

- Below a sparse map's entry (`pathRemove(["data#2026-01", "views"])`): judged against the map's own schema, as a read rebuilds the map. A map a `field:` rename stores whole isn't judged.
- A list position whose removal moves a value where its position can't hold it: `f[0]` of a `[string, number?]` leaves the number where the string was.
- A list position whose shortened list only a member its tag rules out reads: `p[0]` of `{ kind: "a", p: [string, string] }` beside `{ kind: "b", p: [string] }`.
- Below a record with several index signatures, judged by the signatures its key matches: on `{ [open-*]: [string, string?], [fixed-*]: [string, string] }`, `["fixed-k", 0]` is refused and `["open-k", 0]` is sent. A record keyed by a template literal of strings is judged too.

Anything the guard can't model exactly is still sent, as before. A removal is judged against the update as a whole: where another clause of the same update writes or removes what a list position's judgement reads (another position of the list, a tag beside it), the position is judged as 1.40.0 judged it, so `f.kind = "b"` beside the removal of `f.p[0]` above is sent and reads back as `{ kind: "b", p: ["second"] }`, as on 1.40.0.

A condition or filter comparing the path builder itself (`eq(t, 1)`, `t.size()`) is refused with a `ValidationError` before anything is sent (`EDD-9149`), as an empty part under `or()` is. It names the whole item, not an attribute. 1.40.0 sent it as `( = :e0)` and DynamoDB rejected it with a `DynamoValidationError`. 1.39.0 did the same for a condition, and its filter died with a `TypeError`.

A sparse map renamed with `field:` (`{ storedAs: SparseMap(), field: "sr" }`) is stored whole as `sr` by `put` and as one attribute per entry by an update, and a read takes `sr` when the row holds it. An update of its entries on a row `put` wrote reported success and changed nothing a read sees (a `.subtract()` failed naming no attribute), on 1.39.0 and 1.40.0. An update that reads the row (a retained entity's, `clearMap`, any update in `Transaction.transactWrite`) now writes the entry where the row holds the map, inside `sr` or as its own attribute, and `clearMap` removes `sr` too, writing the map's entries as their own attributes. One that doesn't read the row, and a plain entity's `upsert` of the map's entries, is sent as before, guarded on the row not holding `sr`, and on a row that does it's refused with a `ValidationError` (`EDD-9150`) and nothing is written: through 1.40.0 such an `upsert` reported success and its entries were lost. A condition or `expectedVersion` the row doesn't meet fails as it did (`ConditionalCheckFailed`, `OptimisticLockError`), and on a row holding `sr` so does a condition the library can't judge from the row (a `size()` of text beyond ASCII whose answer depends on how its length is counted): the refusal answers only where they're known to hold. An update that reads the row and finds, when it writes, that another writer changed the map's form reads it again and writes again; where the form changes before each of three attempts it fails with `OptimisticLockError` (a versioned or retained entity) or `ConcurrentModification`, naming the map in `attributes`, an optional field new on `OptimisticLockError`. A copy from an entry (`pathSet` or `pathSubtract` with `isPath`) writes no entry and isn't guarded; spelled through the map (`counts.entry("a")`, `["counts", "a"]`) it reads where a read takes the entry when the update reads the row (a retained entity's, any update in `Transaction.transactWrite`), and is otherwise sent as before. A condition or filter on an entry (`t.counts.a`, `t.counts.entry("a")`) asks the row where it holds the map, so it holds on rows of either form: through 1.40.0, `.entry("a")` failed on a row `put` wrote, and `t.counts.a` on one an update wrote. `put`, `create`, a retained or unique entity's `upsert`, `Batch.write` and a map stored only as entries send what they sent.

A path below a struct that renames its keys as they're stored (`Schema.encodeKeys`) names the stored attribute when it's spelled by a property's own name, in path writes, conditions, filters (an aggregate `list` filter's on its root too) and selects alike: on `meta` encoding `amount` as `am`, `pathSet(["meta", "amount"])` and `t.meta.amount` name `meta.am`, and a select of it hands the value back as `meta.amount`. Through 1.40.0 such a path was sent as written: a write stored a stray `meta.amount` that no read saw, a condition or filter on it failed whatever the row held, and a select of it came back without it. A stray `meta.amount` such a write left stays on the row, unread, and a path of either spelling now names `meta.am`: `.set({ meta: { ... } })` writes the struct whole and drops it. A path spelled by stored names (`meta.am`) sends what it sent, including a name that is both one property's own name and another's stored name (`encodeKeys({ a: "b", b: "a" })`: `["swap", "a"]` names the attribute `a`, as before). Where the schema can't say what a segment is stored as (a union whose members don't name every key alike: one storing it renamed beside one that doesn't, or two renaming `x` and `y` crosswise), the path is sent as written from that union on, as before. A `pathRemove` of a property such a struct requires is refused with a `ValidationError` and nothing sent, by either spelling: 1.40.0 removed it by its stored name and left a row no read could decode.

A path operation's value written into a sparse map's entry by the entry's own attribute (`pathSet({ segments: ["counts#z"], value })`, a `pathAppend` to `["lists#k"]`, a path below an entry `.entry()` built) is checked against the map's value schema, as one written into a field is against the field's, and a value the schema refuses is refused with that `ValidationError` before anything is read or sent. Through 1.40.0 it was written as given: into an entry the row held, where every read of the row then failed; beside a map a `field:` rename stores whole, where no read took it and the update reported success; or DynamoDB refused it. A value a read takes as given is still written as given (a number on a map stored as text, which a read takes as earlier releases left it), and so is one below an opaque class, which the schema can't follow. In a field holding a custom declaration, a value its schema refuses is now refused as that operand (`update.pathSet`), naming what the schema refuses, where 1.40.0 refused it as a declaration's value no read takes (`EDD-9126`).

`.entry(key)` resolves the same way on every terminal that takes a path callback: an entity's query accessors, `scan()`, `.history()`, `versions()` and `deleted.list()`, a collection's accessors, a write's `.condition()`, and the entity's own `condition`, `filter` and `select`. Through 1.40.0 it threw ("not configured as a sparse map") in every query callback, and the entity's own `filter` and `select` (on an unbound query) named the entry of a map a `field:` rename stores whole, and a key below an entry that its struct renames as stored, as written, so they matched rows wrongly; they now name what a bound query names. A filter on an entry names the attribute a condition on it names. `.entry()` on a nested field that shares a sparse map's name (`t.inner.zones`), or on a field named like an `Object.prototype` member (`constructor`), is refused like any other field that isn't a sparse map: through 1.40.0 the first tested `inner.z#east`, which no row holds, and the second `undefined#k`. An update of a field named `valueOf` or `constructor` on an entity with a sparse map writes the field: through 1.40.0 it wrote `undefined#…` attributes and returned the old value. In a collection each member names the entry by its own prefix, and a member without the map reads every entry as absent: `eq` on one never matches its rows, `notExists` matches every one.

`.clearMap()` comes first, whatever order the update's combinators were written in, and one request never names an entry twice. Through 1.40.0 a clear with any other write to an entry the row held was sent as written: an entry held as its own attribute was named twice and DynamoDB refused the request; on a row holding a renamed map whole the clear removed nothing a read takes, and a `.subtract()`, `.append()` or path operation into an entry failed naming an attribute the row lacks; and a retained entity applied the `.set()` before the clear and stored `{}`. Now, wherever the row held the entry, a `.set()` of it replaces it, an `.add()` or `pathAdd()` starts it from nothing, a `pathIfNotExists()` sets it, and a `.removeEntries()`, `.deleteFromSet()` or `pathRemove()` below it is the clear's own; a `.subtract()`, `.append()`, or a path operation reading it or writing below it, which has nothing left to work on, is refused with a `ValidationError` (`EDD-9151`) before anything is written. One on an entry the row doesn't hold is still sent, and DynamoDB refuses it with a `DynamoValidationError`, as on 1.40.0. A retained entity's `.subtract()` and `.append()` still apply to the cleared map in memory, starting from nothing, as they did.

A time-series `.append()` whose payload carries entries of a sparse map without a `field:` rename is refused with a `ValidationError` before anything is sent, as its `.remove()` of the map is: through 1.40.0 it wrote the map whole under the field's name beside the row's entries, reported success, and every read returned the entries the row already held. Write a map's entries with `update().set(...)`; an empty map, and a renamed map (whose whole attribute a read takes), are appended as before.

A retained entity's `.removeEntries()` of a sparse map a `field:` rename stores whole no longer removes the entries from the version snapshot it writes: through 1.40.0 the snapshot of the version replaced lost them too, and `versions()` read it without them.

A `pathSet` into a member of a union is checked against every member that holds its path, not only the first. Through 1.40.0 the first member that held the path's next segment alone checked the value, so `pathSet(["tag", "kind"], "b")` on `Union([{ kind: "a", x }, { kind: "b", y }])` was refused with `Expected "a"` whatever the row held, as was a string on `Union([{ v: number }, { v: string }])`. A path write reads nothing of the row, so such a value is written, as the member that takes it stores it, only where what the update leaves reads whatever the row held, at every union its paths pass through or end at: every member there reads it, or the update writes every property of one member that does (a property holding a struct counts when it's set whole or every property of it is written). `tag.kind = "b"` beside `tag.y = 2` is written, and so is the string on `{ v: string }`. Anywhere else it stays refused as on 1.40.0: `tag.kind = "b"` alone would leave `{ kind: "b", x }` on a row holding `a`, and `pass.inner.v = "str"` on `Union([{ kind: "a", inner: { v: number } }, { kind: "b", inner: { v: string } }])` would leave `kind: "a"` beside a string, rows no read could decode. Beside an increment, an append, a `pathIfNotExists` or a copy in the field it stays refused too. Values the first member takes are sent as on 1.40.0, unless no member can read what the field's path writes and removals leave together: `tag.kind = "a"` beside `pathRemove(["tag", "x"])` is now refused with nothing sent, where 1.40.0 applied it and left a row no read could decode. Inside a union whose members rename their keys with `encodeKeys` alike, a path write names the stored keys only where what it leaves reads whatever the row held, and is refused with nothing sent otherwise (`renamed.kind = "b"` alone, or a `pathRemove` of a property one member requires), where 1.40.0 wrote the names given, which no read took. Members that rename them differently (crosswise, or a discriminator stored as `ka` in one and `kb` in the other) get the names given, as on 1.40.0, and the row reads as it did on 1.40.0. Left as 1.40.0 behaves: with a discriminator stored under different names, `kind = "b"` beside `y = 2` still reads as the member the row held; a discriminator set alone to another member's tag that the first member takes (`kind = "a"` on a row holding `b`, in a field or a sparse map's entry) is still sent, leaving a row no read takes; and a path through a recursive union (`Schema.suspend`) is written as on 1.40.0.
