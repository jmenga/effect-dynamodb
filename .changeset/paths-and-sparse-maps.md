A `.select()` naming a sparse map field returns the map. A `ProjectionExpression` can't name a map's entries (`<prefix>#<key>`), so the select projected the field's own name, which no row holds, and the map came back absent, on an entity's queries and scans and on a collection, as on 1.39.0. A select of the whole map now sends its request without a projection, rebuilds the map from each row's entries as a read does, and hands back every other path selected as its projection did, however it was spelled (a stored name, an entry's attribute, a key attribute), without unpacking, decompressing or checking anything the select doesn't name. It consumes the capacity a projected read consumes (DynamoDB charges by the items read, not what it returns) and returns every attribute of each row. A select of one entry (`t.f.entry("k")`, or `t.f.k`) projects the attributes the entry is stored under, both forms for a map a `field:` rename stores whole, and returns the map trimmed to that entry, `{ f: { k } }`. Two selected paths that overlap, a projection DynamoDB refuses, come back once beside the map. A select naming no sparse map sends the projection it always sent, and `.filterBy()` after any select is still refused (`EDD-9054`).

A model field whose own name holds `#` and is stored under another name (`field:`) is named by that name in path writes and conditions, as filters and projections already named it. A path write and a condition took such a first segment as a literal attribute name, so `pathSet(["a#b"])` on a field `a#b` stored as `stored` set a top-level `a#b` that no read looks at, and a condition on `t["a#b"]` tested an attribute `put` never stores, failing whatever the row held, as on 1.39.0. The refusal of a `pathRemove` of a sparse map's entry asks about the attribute the path names after that rename, as `.remove()`'s does, so a field named like an entry (`data#x#y`, stored as `counter`) is removed where it's stored. 1.39.0 removed the entry `x#y` instead, and 1.40.0 refused the removal. An entry named through its map (`.entry("b")`, `.set({ g: { b } })`, `removeEntries`, `clearMap`) is still the entry's attribute when a field carries the same name: only a bare segment the caller spells like an entry names the field. A path write on segments `.entry()` built, on an entity whose unique constraint names such a field, wrote the field on 1.40.0; it writes the entry.

A `pathRemove` that leaves a row no read can decode is refused in more places, with a `ValidationError` and nothing sent, and each was sent on 1.39.0 and 1.40.0:

- Below a sparse map's entry (`pathRemove(["data#2026-01", "views"])`): judged against the map's own schema, as a read rebuilds the map. A map a `field:` rename stores whole isn't judged.
- A list position whose removal moves a value where its position can't hold it: `f[0]` of a `[string, number?]` leaves the number where the string was.
- A list position whose shortened list only a member its tag rules out reads: `p[0]` of `{ kind: "a", p: [string, string] }` beside `{ kind: "b", p: [string] }`.
- Below a record with several index signatures, judged by the signatures its key matches: on `{ [open-*]: [string, string?], [fixed-*]: [string, string] }`, `["fixed-k", 0]` is refused and `["open-k", 0]` is sent. A record keyed by a template literal of strings is judged too.

Anything the guard can't model exactly is still sent, as before. A removal is judged against the update as a whole: where another clause of the same update writes or removes what a list position's judgement reads (another position of the list, a tag beside it), the position is judged as 1.40.0 judged it, so `f.kind = "b"` beside the removal of `f.p[0]` above is sent and reads back as `{ kind: "b", p: ["second"] }`, as on 1.40.0.

A condition or filter comparing the path builder itself (`eq(t, 1)`, `t.size()`) is refused with a `ValidationError` before anything is sent (`EDD-9149`), as an empty part under `or()` is. It names the whole item, not an attribute. 1.40.0 sent it as `( = :e0)` and DynamoDB rejected it with a `DynamoValidationError`. 1.39.0 did the same for a condition, and its filter died with a `TypeError`.

A sparse map renamed with `field:` (`{ storedAs: SparseMap(), field: "sr" }`) is stored whole as `sr` by `put` and as one attribute per entry by an update, and a read takes `sr` when the row holds it. An update of its entries on a row `put` wrote reported success and changed nothing a read sees (a `.subtract()` failed naming no attribute), on 1.39.0 and 1.40.0. An update that reads the row (a retained entity's, `clearMap`, any update in `Transaction.transactWrite`) now writes the entry where the row holds the map, inside `sr` or as its own attribute, and `clearMap` removes `sr` too. One that doesn't read the row, and a plain entity's `upsert` of the map's entries, is sent as before, guarded on the row not holding `sr`, and on a row that does it's refused with a `ValidationError` (`EDD-9150`) and nothing is written: through 1.40.0 such an `upsert` reported success and its entries were lost. A condition or filter on an entry (`t.counts.a`, `t.counts.entry("a")`) asks the row where it holds the map, so it holds on rows of either form: through 1.40.0, `.entry("a")` failed on a row `put` wrote, and `t.counts.a` on one an update wrote. `put`, `create`, a retained or unique entity's `upsert`, `Batch.write` and a map stored only as entries send what they sent.

A path below a struct that renames its keys as they're stored (`Schema.encodeKeys`) names the stored attribute when it's spelled by a property's own name, in path writes, conditions, filters and selects alike: on `meta` encoding `amount` as `am`, `pathSet(["meta", "amount"])` and `t.meta.amount` name `meta.am`, and a select of it hands the value back as `meta.amount`. Through 1.40.0 such a path was sent as written: a write stored a stray `meta.amount` that no read saw, a condition or filter on it failed whatever the row held, and a select of it came back without it. A path spelled by stored names (`meta.am`) sends what it sent, including a name that is both one property's own name and another's stored name (`encodeKeys({ a: "b", b: "a" })`: `["swap", "a"]` names the attribute `a`, as before). Where the schema can't say what a segment is stored as (a union whose members store it differently), the path is sent as written, as before. A `pathRemove` of a property such a struct requires is refused with a `ValidationError` and nothing sent, by either spelling: 1.40.0 removed it by its stored name and left a row no read could decode.

`.entry(key)` works in a query's, a scan's and a collection's `filter` and `select`, where it threw ("not configured as a sparse map") through 1.40.0. A filter on an entry names the attribute a condition on it names. In a collection each member names the entry by its own prefix, and a member without the map never matches.
