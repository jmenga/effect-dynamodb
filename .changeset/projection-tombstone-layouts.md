A read model fed by several projections keeps each projection's checkpoints across tombstones. Every projection now records the attributes it keeps on a row, each with its role, with or without `removal`. A tombstone keeps every projection's checkpoints that the row holds, not only the remover's, and so do the writes that replace it: another projection's row from `initial`, a second tombstone, and the entity's `create`, which never carries the table's TTL attribute. Each of those writes raises every projection's revision the row holds, so another projection's write that read its revision there fails its revision guard and retries; a revision the row didn't hold stays absent, as before. Before, `create` over a tombstone carried the fields of the projection defined last, and another projection's removal dropped the others' checkpoints, so a redelivered event or a late removal could apply again. On a read model one of whose projections has `removal`, a stored attribute that one projection uses in two roles (checkpoint, checkpoint map, checkpoint owner, revision) is now refused by the definition that completes the conflict, whatever order they are defined in (`EDD-9133`). Two projections keeping one attribute in different roles are not refused: each projection's writes take its own roles first, by stored name, so two writing disjoint rows run as before. Read models without `removal` are unchanged. An attribute stored as the table's TTL attribute while a projection's tombstones set it refuses the projections' writes with a `ValidationError`, before anything is sent. A tombstone write is refused for a checkpoint map key a sparse map can't store, as the row write already was. `drain` and `drainPending` run as before. A read model with one projection sends and stores exactly what it did before.
