An aggregate `update` deletes a custom `decompose`'s rows by the keys they're stored under. On a `many` edge whose `decompose` encodes its keyed field itself (`f / 10` on a field that multiplies by 10), removing an element left its row, and `get` still returned it. Changing the keyed value left the old row beside the new one. `update` worked out which rows to delete by decomposing the state it read once more, which keys such rows elsewhere. It now decomposes that state both as it was read and as a write's value is, and deletes the keys either gives that a row it read holds and the new state doesn't, in the transaction of the group that owns the edge. It sends no extra request, and deletes only a row it read. A row under a key the state as read gives is deleted by its key, as 1.39.0 deleted it. A key only the second decomposition gives isn't enough: it can be the key of a row another aggregate, or the entity itself, stored in the partition, so that row is deleted only if it holds what that decomposition writes there, every attribute but the keys and timestamps the library manages compared, as it's stored. Its `Delete` is sent on condition that the row still holds what was read: when another write replaced it in between, the transaction writes nothing and `update` runs again from a fresh read. Any other row of the same entity type is left alone.

`rekey` moves those rows with the aggregate, as stored. Under `escapeKeys`, such an edge's rows stayed under the old partition key, unreported, and `get` returned no lines. A row is the edge's on the same terms as for `update`. Each stored row is placed once, however many edges or aggregates reach it. An aggregate moves whole or not at all: when a row it would move to is held by a row it doesn't move, another aggregate's or one already there, it reports a `bothKeys` conflict and moves none of its rows, its root included, whichever aggregate the scan meets first. Each key is judged by the rows the run read: in a chain of keys across aggregates, where one's row belongs under another's key, a run moves what its dry run reports in any scan order, and the next run moves the next link. A run used to move more links than its dry run reported when one aggregate's move landed before another's read. A row the aggregate's value doesn't hold stays where it is. A `failed` conflict for an aggregate that doesn't decompose now names the reason in its `message`.

A `many` edge whose custom `decompose` returns a date field's stored form, such as the ISO text of a `Schema.DateTimeUtcFromString` or the epoch milliseconds of a number decoded to a `Date`, stores it as it is and keys it as 1.39.0 did. On 1.39.0 an array edge failed `create` with a defect, and so did an edge held as a `Schema.Record` with an `entity`. Since keyed edges took their element's encoders in this release, a keyed edge without one failed `create` and every `update` of its 1.39.0 rows too. A value in neither form is refused with a `ValidationError` (`EDD-9127`), and nothing is written.

A `Schema.Record` `many` edge now encodes its fields as an array edge does, where 1.39.0 stored what `decompose` returned. A `Schema.NumberFromString` is stored as its text, not the number, under the same key, and reads the same value. A field that multiplies by 10 on decode, returned by `decompose` as `f / 10`, reads back the value given, where 1.39.0 read ten times it and multiplied it again on every `update`. A row 1.39.0 wrote reads as it did.

Otherwise, an aggregate without a custom `decompose` sends the same requests as before.
