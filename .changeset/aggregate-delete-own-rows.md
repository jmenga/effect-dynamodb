**An aggregate's `delete` now deletes only its own rows.** It deletes the rows of its partition whose `__edd_e__` is one of the aggregate's entity types (its root's, each edge's and each sub-aggregate's, at any depth) and leaves every other row there: an entity's, another aggregate's, a row with no entity type. Up to 1.40.0, and on 1.39.0, it deleted every row its read returned, so an entity or another aggregate sharing the partition lost its rows too. If you relied on `delete` clearing the whole partition, delete those rows yourself. The read is the one sent before, a row of one of the aggregate's types is still deleted whoever wrote it, and a partition holding only the aggregate's rows gets the same requests as on 1.40.0. A partition holding rows but none of the aggregate's now fails with `AggregateAssemblyError` and deletes nothing, as an empty partition does; 1.40.0 deleted those rows and succeeded.

**An entity's `refs` fetch the referenced entity under its key.** `Entity.make({ refs })` fetched a referenced entity under its `DynamoModel.identifier`, while the `${field}Id` it takes is the entity's key composite, as aggregate edges have used since 1.40.0. A ref entity whose identifier is another field than its key failed every `put`, `upsert` and `update` naming the ref with a `ValidationError` (`get.decode`, `Missing key`, or `put.decode` for a number key), on 1.39.0 too; it is now fetched under its key composite, and `rekey`'s read-back of the ref, the `.within()` row check and cascades read that composite. A ref entity whose identifier is its key sends and stores what it did. A ref entity keyed by more than one composite can't be named by one id: a write naming it fails with a `ValidationError` (`EDD-9158`, operation `hydrateRefs`) before anything is fetched or written, where it failed with `get.decode` (or a defect, for a key composite with a default) before.

**A cascade from an entity keyed by a number finds the rows that reference it.** It queried the ref's index with the id as unpadded text (`teamid_5`), while a `put` stores the padded key text (`teamid_0000000000000005`), so it updated nothing, on 1.39.0 too. It now reads the key text the rows are stored under. Rows that an earlier cascade missed still hold the old copy of the referenced entity until the next update of that entity cascades to them. A cascade from an entity whose identifier isn't its key read the identifier and sent no query; it now cascades.

**What the library stores beside an edge's value stays out of it on a read.** A sub-aggregate's discriminator is stored on every row beneath it, a `one` edge's own discriminator on its row, and on every row the aggregate's partition key attribute (under a name other than `pk`, such as `PK`) and, with a collection index, the collection sort key's mirror. A value that keeps what it's given (`Schema.Unknown`, a declaration, or a union member that falls back to one, such as a member renaming a field whose row holds the field's domain name) came back with those attributes inside it, on 1.39.0 too. It now reads back as given. Nothing stored changes, and rows already stored read without them. A value that declares a field of one of those names, or a record, keeps it, a custom `assemble` is still handed the rows with them, and a value decoded through a struct, which drops an attribute it doesn't declare, reads as before.
