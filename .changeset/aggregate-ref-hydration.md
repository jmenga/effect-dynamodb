An aggregate `create` no longer dies or drops an id hydrating an edge with an `entity`, and a multi-item op finds an item whose key composite is a codec.

- **A `many` edge whose element is the entity's own model, given whole, is stored as given.** Its key field (`lineId` of a `Line`) was taken for an id to fetch because its name was `${field}Id`, and `create` died with `Missing composite attribute "lineId"`. An element that isn't a union is hydrated through `${field}Id` only when its field of the entity's name can hold the entity's record (an object or a class, optional, branded or not). A field declared a scalar (`line: Schema.String`) is never taken for one. For an entity whose model is a `Schema.Struct` (in a `DynamoModel.configure` wrapper or not) and whose `entityType` is a string literal, the input type takes the same field by id, and a field of another name whole, as `create` does. 1.39.0 typed a field of another name holding a value with an `id: string` as `${field}Id`, an id `create` never fetched. For any other model, a `Schema.Class` included, the type can't see the name `create` takes (a class's own name), so the element is typed as on 1.39.0.
- **Union elements hydrate as on 1.39.0.** A `many` element declared a union is hydrated when it's given a string `${field}Id`, whatever member the value is, at the root and in a sub-aggregate, and the input and create schemas take the union as declared. The one change is a string id of no type of the entity's key composite (`"5"` for a number key), which fails with `EDD-9131` as everywhere else.
- **An entity with no `DynamoModel.identifier` is fetched.** `create` fetched each id under the identifier, or under `id` without one, and died composing the entity's key. It now fetches under the entity's primary key's only distinct composite (an attribute in both halves of the key counts once). That covers `one` and `ref` edges, `many` elements given as ids and elements wrapping the entity, and an entity whose identifier names another field.
- **A number, bigint or `Date` id is fetched.** Only a string was collected, so a number or bigint id was dropped: a required edge failed decoding and an optional edge was created without the entity. An id is now a value of the key composite's type, or of its stored or JSON form (`"5"` of a `NumberFromString`, an ISO string of a `Date`), and the input type and schema take that type, outside a union element. A key composite that is a codec inside a wrapper (`Schema.optional(Schema.NumberFromString)`, a `NumberFromString` in a union with a literal) takes either form too, and is fetched by the key `put` wrote (`lineid_5`).
- **An id of no type of the key composite fails `create` with a `ValidationError` (`EDD-9131`), where it failed with `RefNotFound`.** `"5"` for a number key was fetched under `lineid_5`, a key no `put` writes. The error is now a `ValidationError`, on the error channel, and nothing is fetched. Code that catches `RefNotFound` for such an id no longer sees it: catch `ValidationError` instead, or pass an id of the key's type. An id `put` refuses fails the same way, before anything is fetched, by `put`'s own rule: one DynamoDB can't store (`Infinity`, alone or anywhere in a struct, an `Option` or a `Result` id), or one that doesn't encode as the key composite is stored (`Infinity` for a digits-only string codec). The error names an object id by its JSON. An id `put` stores is fetched as before, `"Infinity"` for a `NumberFromString` key included. Its key text could name an item of another value, which was fetched in its place.
- **An entity keyed by more than one composite fails `create` with a `ValidationError` (`EDD-9129`)** naming the edge. No one id names one of its items. It died the same way. Every edge is judged before anything is fetched or written.
- **`Batch.get`, `Batch.write` deletes, `transactGet`, and `transactWrite` deletes and condition checks compose the key `Entity.put` wrote** for a key composite that is a codec. For a codec whose `encode` takes its own output (a prefix), `put` encodes the composite twice and these paths encoded it once. For a codec inside a wrapper (`Schema.optional(Schema.NumberFromString)`, `Schema.optional(Schema.BigIntFromString)`, a `NumberFromString` in a union with a literal, an optional prefix codec), `put` keys the stored text (`id_5`) and these paths keyed the domain value (`id_0000000000000005`). Either way they found, deleted and checked nothing. Aggregate ref fetches go through the same path. Every other key composes exactly as before.

**Visible change: a caller's key is a domain value, as `get` takes it.** Given the *stored* text of a key whose codec's `encode` takes its own output (`Schema.StringFromBase64`, `Schema.StringFromHex`, `Schema.StringFromUriComponent`, a codec that prepends a prefix, alone or inside `Schema.optional` or a union), these multi-item ops and aggregate ref ids now address the item whose domain value is that text, as `get` does. 1.39.0 addressed the item stored under it. Pass the domain value: `{ docId: "MiX" }`, not `{ docId: "x:MiX" }`. A numeric codec (`NumberFromString`, `BigIntFromString`) still takes either form.

No stored key changes.
