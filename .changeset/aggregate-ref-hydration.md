An aggregate `create` no longer dies, drops an id or overwrites a value hydrating an edge with an `entity`, and a multi-item op finds an item whose key composite is a codec.

- **A `many` edge whose element is the entity's own model, given whole, is stored as given.** Its key field (`lineId` of a `Line`) was taken for an id to fetch because its name was `${field}Id`, and `create` died with `Missing composite attribute "lineId"`. Only an element whose field of the entity's name can hold the entity's record (an object, a class, a union holding one, optional or not) is hydrated through `${field}Id`. A field declared a scalar (`line: Schema.String`) is never taken for one. Union elements hydrate as they did, at the root and in a sub-aggregate.
- **A union element is read as the member the aggregate's input schema decodes it as, and hydrated when that member wraps the entity.** Unions are walked as declared, in their own mode, and an id is taken as a value of the entity's key composite. A member with a nullable discriminator (`kind: Schema.NullOr(Schema.Literal("a"))`) is named by `null`, nested unions count their members, and a member typing an id field of its own (`lineId: Schema.Number`) takes an id of that type. Where two members share a discriminator and the first declares the entity's field a string and an id field of its own, an element that member takes keeps both as given. 1.39.0 replaced that string with the fetched entity. Every other element 1.39.0 hydrated and stored is hydrated and stored as it was: a member that doesn't declare the entity's id field refuses one, and a union holding the member that wraps the entity runs its checks on the hydrated element, not on the id.
- **The input and create schemas take an id in a member of a nested union.** They transformed only a union's direct members, so they refused the element `create` took (`Missing key ["line"]`). Each union keeps its own annotations and mode, and its own checks unless it holds a member wrapping the entity: those run when `create` decodes the hydrated element. In such an element, a member that doesn't declare the entity's id field refuses one, keeping its class and checks. 1.39.0's schemas took that value, and `create` fetched the entity and failed decoding it. A `oneOf` union element given a value that both a member declaring the entity's id field and the member wrapping the entity take is now refused by the input schema as ambiguous. 1.39.0's input schema took it as the declaring member, and `create`, which stored it as the wrapping member, still does.
- **An entity with no `DynamoModel.identifier` is fetched.** `create` fetched each id under the identifier, or under `id` without one, and died composing the entity's key. It now fetches under the entity's primary key's only distinct composite (an attribute in both halves of the key counts once). That covers `one` and `ref` edges, `many` elements given as ids and elements wrapping the entity, and an entity whose identifier names another field.
- **A number, bigint or `Date` id is fetched.** Only a string was collected, so a number or bigint id was dropped: a required edge failed decoding and an optional edge was created without the entity. An id is now a value of the key composite's type, or of its stored or JSON form (`"5"` of a `NumberFromString`, an ISO string of a `Date`), and the input type and schema take that type. A key composite that is a codec inside a wrapper (`Schema.optional(Schema.NumberFromString)`, a `NumberFromString` in a union with a literal) takes either form too, and is fetched by the key `put` wrote (`lineid_5`).
- **An id of no type of the key composite fails `create` with a `ValidationError` (`EDD-9131`), where it failed with `RefNotFound`.** `"5"` for a number key was fetched under `lineid_5`, a key no `put` writes. The error is now a `ValidationError`, on the error channel, and nothing is fetched. Code that catches `RefNotFound` for such an id no longer sees it: catch `ValidationError` instead, or pass an id of the key's type. An id `put` refuses as DynamoDB can't store it (`Infinity`, alone or anywhere in a struct, an `Option` or a `Result` id) fails the same way, before anything is fetched, by `put`'s own rule, and the error names an object id by its JSON. An id `put` stores is fetched as before, `"Infinity"` for a `NumberFromString` key included. Its key text could name an item of another value, which was fetched in its place.
- **An entity keyed by more than one composite fails `create` with a `ValidationError` (`EDD-9129`)** naming the edge. No one id names one of its items. It died the same way. Every edge is judged before anything is fetched or written.
- **`Batch.get`, `Batch.write` deletes, `transactGet`, and `transactWrite` deletes and condition checks compose the key `Entity.put` wrote** for a key composite that is a codec. For a codec whose `encode` takes its own output (a prefix), `put` encodes the composite twice and these paths encoded it once. For a codec inside a wrapper (`Schema.optional(Schema.NumberFromString)`, `Schema.optional(Schema.BigIntFromString)`, a `NumberFromString` in a union with a literal, an optional prefix codec), `put` keys the stored text (`id_5`) and these paths keyed the domain value (`id_0000000000000005`). Either way they found, deleted and checked nothing. Aggregate ref fetches go through the same path. Every other key composes exactly as before.

**Visible change: a caller's key is a domain value, as `get` takes it.** Given the *stored* text of a key whose codec's `encode` takes its own output (`Schema.StringFromBase64`, `Schema.StringFromHex`, `Schema.StringFromUriComponent`, a codec that prepends a prefix, alone or inside `Schema.optional` or a union), these multi-item ops and aggregate ref ids now address the item whose domain value is that text, as `get` does. 1.39.0 addressed the item stored under it. Pass the domain value: `{ docId: "MiX" }`, not `{ docId: "x:MiX" }`. A numeric codec (`NumberFromString`, `BigIntFromString`) still takes either form.

No stored key changes.
