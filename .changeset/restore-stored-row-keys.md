A row read back from DynamoDB composes the keys `put` wrote, on every path that composes keys from a stored row.

- **`restore`, an update or `patch` of a `versioned: { retain: true }` entity, in a `transactWrite` too, and the updates that read the item first (a unique constraint, a vector index) no longer die with `EDD-9050`** on a `Schema.OptionFromNullOr(Schema.BigInt)` or a `Schema.BigInt` under a decoding default holding a value below 2^53. DynamoDB hands such a value back as a number, and neither form of the schema took one. The composite key form now takes it as the `bigint` it was stored from, so primary, index, history and sentinel keys are the ones `put` wrote, byte for byte. `aggregate.list` lists such an aggregate, and `rekey` moves such a row and repairs its index keys.
- **A delete releases the unique-constraint sentinel `put` reserved** on a `bigint` field below 2^53, `Schema.BigInt` included. It deleted a key composed from the number DynamoDB handed back, which `put` never wrote, and left the reservation in place, so the value couldn't be taken again. A reservation an earlier release left this way stays until you delete it with the raw `DynamoClient`.
- **A key composite storing both a `number` and a `bigint` is refused at load (`EDD-9128`).** That's `Schema.Union([Schema.Number, Schema.BigInt])`, a numeric literal or enum beside `Schema.BigInt`, and `Schema.Unknown` or `Schema.Any`, in an entity's primary key, a secondary index, a unique constraint, a vector partition or a time-series `orderBy`, or in an aggregate's partition, collection or list key or a `many` edge's sort key. DynamoDB stores `5` and `5n` alike and hands either back as the number `5`, whose key text isn't `5n`'s, and nothing on the row says which was written. So `restore`, the updates that read the item first, a delete releasing a unique-constraint sentinel, `rekey` and an aggregate's `update` and `list` composed the number's key for a `bigint`: a `restore` moved the item where nothing found it, an update moved its index key or vector partition, a delete left its sentinel behind, and an aggregate `update` wrote a second edge row. **A model declaring one no longer loads, and nothing moves its rows for you.** Declare the one kind the field holds. A row written with the other kind is stored under that kind's key text, which the new declaration doesn't compose: `get` doesn't find it and `rekey` counts it in `skipped.unrecognizedKey`, so rewrite such rows with the raw `DynamoClient`. A field no key reads may still store both. A union of one numeric kind and something else (`Schema.Union([Schema.String, Schema.BigInt])`) reads a stored number back as that kind.
- **`rekey` names a row whose values compose no key.** A row whose own key holds `NaN`, or one of whose key composites holds a value no form of its schema takes, is the conflict `uncomposable`, with the refusal in `message`. It was counted in `skipped.unrecognizedKey`.

What's stored doesn't change.
