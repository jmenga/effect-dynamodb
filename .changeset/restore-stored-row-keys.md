A row read back from DynamoDB composes the keys `put` wrote, on every path that composes keys from a stored row.

- **`restore`, an update or `patch` of a `versioned: { retain: true }` entity, in a `transactWrite` too, and the updates that read the item first (a unique constraint, a vector index) no longer die with `EDD-9050`** on a `Schema.OptionFromNullOr(Schema.BigInt)` or a `Schema.BigInt` under a decoding default holding a value below 2^53. DynamoDB hands such a value back as a number, and neither form of the schema took one. The composite key form now takes it as the `bigint` it was stored from, so primary, index, history and sentinel keys are the ones `put` wrote, byte for byte. `aggregate.list` lists such an aggregate, and `rekey` moves such a row and repairs its index keys.
- **A delete releases the unique-constraint sentinel `put` reserved** on a `bigint` field below 2^53, `Schema.BigInt` included. It deleted a key composed from the number DynamoDB handed back, which `put` never wrote, and left the reservation in place, so the value couldn't be taken again. A reservation an earlier release left this way stays until you delete it with the raw `DynamoClient`.
- **A `Schema.suspend(() => Schema.BigInt)` key composite keeps the keys `put` wrote.** Read back below 2^53 it was taken as a number, so `restore` put the item back under the number's key text, where `get` didn't find it, and an update reading the item first, a delete releasing its unique-constraint sentinel, `rekey` and an aggregate's `update` and `list` composed the same wrong key. A suspended schema is now read as the schema it suspends.
- **A key composite storing both a `number` and a `bigint` is refused at load (`EDD-9128`).** That's `Schema.Union([Schema.Number, Schema.BigInt])`, or a numeric literal or enum beside `Schema.BigInt`, in an entity's primary key, a secondary index, a unique constraint, a vector partition or a time-series `orderBy`, or in an aggregate's partition, collection or list key or a `many` edge's sort key. DynamoDB stores `5` and `5n` alike and hands either back as the number `5`, whose key text isn't `5n`'s, and nothing on the row says which was written. So `restore`, the updates that read the item first, a delete releasing a unique-constraint sentinel, `rekey` and an aggregate's `update` and `list` composed the number's key for a `bigint`: a `restore` moved the item where nothing found it, an update moved its index key or vector partition, a delete left its sentinel behind, and an aggregate `update` wrote a second edge row. **A model declaring one no longer loads.** Declare the one kind the field holds, then run `rekey`. A row written with the other kind is stored under that kind's key text, which `get` doesn't find under the new declaration. `rekey` moves it to the text of the value as it reads back, along with its index keys, unique-constraint sentinels, tombstone, time-series events and an aggregate's rows. Two items whose values read back as one, such as `3` and `3n`, are reported as the conflict `bothKeys` and left, and so are two rows of an aggregate's `many` edge that read back as one element. A row already under its key costs `rekey` nothing more, and one under the other kind's text is found with one composition per numeric key composite. A field no key reads may still store both. A dotted composite (`nested.n`) is checked through `Schema.optional`, `Schema.optionalKey`, `Schema.NullOr`, `Schema.suspend` and a class, and a time-series entity's `appendInput` is checked as its model is, including a field it declares as the other kind than the model's. A key whose kinds can't be read at load, a `Schema.Unknown`, a `Schema.Any`, an opaque `Schema.declare` or a transformation whose stored side is one of those, still loads, and keeps working for strings and numbers. It's judged at write: the value DynamoDB hands back is decoded through the field, and a value that reads back as something else fails with a `ValidationError` (`EDD-9128`) naming what it reads back as, and writes nothing. A `Schema.Unknown` given a `bigint` below 2^53, or a whole `number` past it, is refused; a `Schema.Unknown` decoded to a `Schema.BigInt` reads `5n` back as `5n`, and stores it as before. A row an earlier release stored with a `bigint` below 2^53 there reads back as a number, and `rekey` moves it to the number's key text. A union of one numeric kind and something else (`Schema.Union([Schema.String, Schema.BigInt])`) reads a stored number back as that kind.
- **`rekey` leaves a `Schema.BigInt` time-series event where `append` put it.** Under `escapeKeys: false` it composed the event's sort key from the number DynamoDB hands back for a `bigint` below 2^53, and moved the event to the number's key text, where `.history().where()` on the `bigint` didn't find it. It now composes the key from the `bigint`, and moves an event an earlier run moved back to it.
- **`rekey` names a row whose values compose no key.** A row whose own key holds `NaN`, or one of whose key composites holds a value no form of its schema takes, is the conflict `uncomposable`, with the refusal in `message`. It was counted in `skipped.unrecognizedKey`.

What's stored doesn't change.
